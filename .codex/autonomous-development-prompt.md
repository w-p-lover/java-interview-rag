## 自主判断

普通需求理解和技术选择由你自行决定，不向用户询问，包括类、方法、接口、表字段、包结构、局部依赖、测试方式、阶段内顺序、小范围重构以及是否参考外部项目。

存在多个合理方案时，选择符合项目定位、简单可维护、可逆、与现有技术栈一致且能被验证的方案。记录重要判断和理由后继续开发，不等待批准。

新增或修改的代码注释默认使用简体中文，只在业务意图、边界或原因不明显时添加必要注释。日志、异常和用户可见提示默认使用简体中文；标准协议、技术名词和外部接口固定格式除外。

也可以自主寻找其他活跃、文档清楚、许可证明确的相关项目，但是否采纳必须由当前真实需求决定。

## 开发粒度

默认选择中等规模、端到端、用户可感知的功能闭环。一个轮次应尽量完成同一业务目标直接需要的设计、后端、接口、前端、针对性测试和事实文档，不把能够一起集成验证的连续工作拆成多个只改一个字段、一个方法或一个按钮的微小轮次。

较大幅度开发不等于同时铺开多个无关功能。每轮仍只围绕一个明确业务目标，控制可审查范围并完成验证和提交。只有边界明确的局部缺陷、安全修复、迁移执行、重复验证，或外部依赖使端到端闭环无法完成时，才选择较小闭环。

## 每轮必须有功能进展

- 每轮必须交付实际功能成果或工程进展，至少包括一项：新增或改进用户可调用能力、完成可运行链路接入、修复明确缺陷、完成此前不存在的外部集成，或产生能够改变技术决策的全新量化结果。
- 只写文档、重复已有测试、重复检查同一服务、格式化代码或整理旧结论，都不算开发成果，不能作为本轮主要产出。
- 付费 Chat/Embedding 校验只能验证已完成的代码或数据变化；调用前必须定义验收指标、最大调用次数和失败后的动作。同一代码、同一数据集、同一模型版本不得为了寻找更好结果反复付费运行。
- 付费结果不达标时，明确记录不采用或回退，随后选择下一个能产生功能进展的任务；不得用重复调用代替开发。
- 最终输出先说明功能成果和工程进展，再说明文档、测试和遗留风险；文档只能证明成果，不能替代成果。

## 每轮闭环

1. 判断当前阶段、已完成能力、已知问题和可执行候选项。
2. 选择一个最重要、范围合理、能够完成并验证的主要任务。
3. 任务过大时自行拆分，避免多个无关半成品。
4. 必要时查阅官方文档或相关开源项目。
5. 完成直接相关的设计、代码、配置和文档。
6. 只执行与改动风险匹配的验证，不做无意义的大范围测试。
7. 更新 `docs/04-当前进度.md`。
8. 向 `docs/05-开发记录.md` 追加本轮记录，不覆盖历史。
9. 有重要选择时更新 `docs/07-技术决策记录.md`。
10. 有外部调研时更新 `docs/06-参考项目调研.md`。
11. 本轮改变核心技术栈、完成主要功能闭环或产生新的真实评估指标时，更新 `docs/08-项目技术栈与功能总结.md`；小型修复和未改变能力边界的改动不更新。

按正常 Git 开发流程工作：可以自主使用 `codex/` 开发分支，在完成一个可验证闭环后检查 diff、暂存并提交直接相关文件，提交信息使用小写类型前缀和简洁中文说明。远程仓库与上游分支已经明确配置时，可以正常 push 已验证的当前开发分支。

不得强制 push、重写历史、覆盖用户改动、把无关文件混入提交、擅自合并主分支、创建或合并 Pull Request，也不得部署或写入真实密钥和生产数据。

## 阻塞处理

普通歧义不是停止理由。选择保守、可逆方案，记录假设后继续。

局部任务被阻塞时，先尝试接口隔离、Mock、本地替代或拆分实现；仍无法推进则记录阻塞，选择同阶段其他安全任务继续。

只有缺少必须由用户提供的账号或密钥、产生真实费用、不可逆数据或生产操作、无法绕开的用户改动冲突、许可证不兼容、必须修改 `blog-springboot`、必须改变 Java 主路线或核心定位直接冲突，并且不存在其他安全工作时，才允许停止等待用户。
