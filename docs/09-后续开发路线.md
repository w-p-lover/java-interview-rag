# 后续开发路线

> 更新时间：2026-09-03。用于约束投递前冲刺和投递后的技术扩展，不记录开发流水账。

## 当前判断

项目的知识库、RAG、文本面试、证据化评分、复习 attempt 和受控 Tool Calling 已形成基础闭环。现阶段不再平均扩展功能，而是进入“投递前冲刺”：少数方向完整实现并验证，少数前沿方向只做隔离 POC，其余方向保留进入条件，不在主链路留下半成品。

角色对话已先完成有界运行时：会话上下文、SSE 阶段事件和状态重建已接入主链路；Graph 继续作为后续方向，等待真实的分支、修正循环、人工确认或跨进程恢复需求。

开发状态只有三种：

1. **实现并验证**：进入主业务，有代码、固定样本、运行结果和失败边界，可以写入简历成果。
2. **独立 POC**：只验证技术可行性，不影响主业务，简历和面试中必须明确表述为 POC。
3. **后续方向**：只有设计、进入条件和不采用理由，不写成已经掌握或已经实现。

## 执行原则

- 每日自主开发以解决项目问题和提升面试主讲能力为目标，默认必须落到业务代码、产品交互或运行链路；文档、测试、JAR/依赖版本、服务状态和外部调研只作为必要支撑，不能单独成为当天任务。
- 每日选题依次看：用户可见缺陷、RAG 主链路工程缺口、面试训练闭环缺口、必要部署收尾。已有明确问题时直接实现，不先进行全项目盘点、文档审计或重复基线复核。
- 每轮只设一个用户结果和一个最小验收标准。验证只覆盖本轮可达行为，文档通常只同步当前进度；没有改变路线、决策、核心能力或简历口径时，不扩散更新其他文档。
- 每轮只完成一个可验证闭环，投递价值和可讲深度优先于功能数量。
- 先建立简单方案和固定基线，再增加检索、Agent 或图工作流复杂度；没有收益就停止扩张。
- Java/Spring AI 继续作为主业务与 Agent 开发平台，DashScope 提供模型，MySQL/Qdrant 保存业务事实与知识资料。
- Codex 可以承担主要实现，但每个闭环必须留下调用链、技术取舍、指标、失败场景和面试追问材料。
- 简历和 JD 默认不持久化，不把模型推断包装成用户事实，不从模型自然语言直接生成写操作。
- 没有完成固定验证的技术只能写“调研”或“POC”，不能进入简历核心成果。

## 一、现在开发：投递前必须收口

本路线的验证原则：测试、构建、浏览器检查和外部数据核验只用于证明当前功能的关键边界，不把重复测试矩阵、重复审计或单纯增加覆盖率作为独立开发目标。每轮必须先完成一个用户可调用的功能闭环或明确缺陷修复，再按风险做最小必要验证。

### 1. RAG 查询拆分真实对照

当前查询拆分 + RRF 对照代码已经完成，但真实对照显示排序退化，因此不接入生产检索。

开发内容：

- 在费用授权上下文明确时运行固定 20 题真实对照。
- 比较基线与候选的 Hit@1、Recall@5、MRR、标题路径召回和无答案拒答准确率。
- 记录拆分题数、额外查询次数、耗时和失败题，不只记录总分。
- 只有多证据召回改善、排序和拒答不退化时，才评估接入生产；否则保留实验结论并停止扩张。

涉及技术：确定性查询规划、Multi-query Retrieval、Reciprocal Rank Fusion、Qdrant、Embedding、离线评估。

完成结果：已产生 `2026-08-27-rag-query-decomposition-comparison.json`。候选 Hit@1 `0.9412`、MRR `0.9706`，低于原查询的 `1.0000`；明确不采用。

### 1.1 同来源相邻 Chunk 上下文扩展

状态：已实现并完成确定性回归；一次授权固定集 Embedding 对照已完成，因无证据收益且上下文噪声上升，生产回答默认关闭扩展。

- 初始向量检索命中后，按同一来源、同一文档版本和相邻 `chunk_order` 补充前后一段资料。
- 每次最多处理 3 个种子、最终最多 8 条资料；按来源/版本/顺序去重，初始无命中时不扩展。
- 只接入 RAG 回答上下文，裸检索、查询评估和面试知识绑定继续使用原始 topK/阈值语义。
- `GET /api/knowledge/evaluations/retrieval/adjacent-context` 复用同一批 Hybrid 候选输出基线/候选报告，并额外统计完整上下文的来源、Chunk、回答要点证据召回、噪声、逐题新增 Chunk 和向量查询次数。
- 评估脚本要求显式 `--max-embedding-calls`；历史相邻上下文对照按 23 题、8 份语料计算的最坏预算为 100 次逻辑 Embedding 调用，且不调用 Chat。只有证据召回至少一项改善、Top5 Precision 与拒答准确率不退化、上下文噪声增幅不超过 0.15 才保留生产扩展，否则关闭回答链路扩展。
- 2026-09-04 真实结果：12/23 题新增 22 个上下文、额外 51 次向量查询；来源召回、Chunk 召回和回答要点证据召回均无变化，上下文噪声由 `0.5647` 升至 `0.6075`，因此 `storage` RAG 默认关闭扩展。扩展器与对照端点保留，后续仅在新的脱敏失败样本证明需要时重开。

### 1.2 PDF 知识资料上传与页面级结构化入库

状态：上传、页面/章节结构化 Chunk、独立结构检索评估代码和一次真实结构检索基线均已实现；当前固定样本不支持增加结构权重或章节聚合。

- 上传接口和资料准备页支持 `.pdf`，返回页数、OCR 候选页和版面解析告警。
- PDF 优先识别真实标题、正文、列表、代码、表格和跨页章节，无标题时才按页回退；Qdrant、检索与回答上下文保留页码和块类型。
- 独立 3 题合成 PDF 结构集覆盖代码、表格和跨页正文，报告统计标题路径、页码、块类型与完整结构召回；不改变生产检索排序，也不加入 20 题 Chat 回答评估。
- 2026-08-31 真实 `text-embedding-v3` 基线在 3 道结构题上取得来源、Hit@1、标题路径、页码、块类型和联合结构召回 `1.0000`；结果见 `evaluation/results/2026-08-31-pdf-structure-retrieval-baseline.json`。固定问题没有证明结构字段不足，因此不接入块类型权重、章节聚合或轻量文档结构图。当前不自动 OCR。

### 1.3 Dense、BM25 与 Hybrid-RRF 真实召回对照

- 评估入口：`GET /api/knowledge/evaluations/retrieval/hybrid`，同一 20 题固定集分别运行 Dense-only、BM25-only、Hybrid-RRF，不调用 Chat。
- 2026-09-02 使用 `text-embedding-v3`、8 份语料和 18 个 Chunk 完成一次对照。三策略 Hit@1 均为 `1.0000`、Mean Recall@5 均为 `0.9706`、MRR 均为 `1.0000`；Hybrid 标题路径召回 `0.9565`，Dense `0.9130`，补回 `java-ambiguous-map-performance` 的一个标题路径。

- 独立 Sparse 拒答策略、字段化 BM25（正文/标题/代码/Java 标识符权重）、Hard Negative 与 Chunk 级标注，以及 Precision@5、nDCG@5、上下文噪声和检索 P95 延迟指标均已接入并通过定向测试；新字段的授权 storage 固定集复核结果见下一行，在真实证据前不引入 Cross-Encoder Rerank 或新搜索基础设施。

### 2. 简历证据审计官基线

这是投递前最重要的新功能。第一版使用普通 Spring AI 编排，不提前依赖图框架。

开发内容：

- 复用现有简历文本输入，结构化提取项目、技术、职责、时间和结果等事实。
- 每个事实携带简历中的逐字证据，由 Java 服务端执行字面包含校验。
- 输出严格区分已确认事实、信息缺失、风险判断和表达建议。
- 固定样本覆盖完整简历、缺少量化结果、时间冲突、技能堆砌、项目空泛和简历内提示注入。
- 日志只记录角色、Prompt、模型版本、token、耗时、状态和失败类型，不记录简历正文。

涉及技术：Spring AI Structured Output、Prompt 版本、服务端证据验真、Agent Evaluation、Prompt Injection 防护、隐私日志。

完成标准：固定样本能够输出稳定结构；模型引用全部通过服务端验真；无证据内容不会被包装成事实；攻击样本不能改变系统规则和工具边界。

### 5. 工程化 RAG 专项补齐

本节是工程化缺口的权威清单。它记录当前代码做到了什么、还缺什么以及什么证据才算完成；未完成项不能写入简历成果，也不代表需要一次性实现全部内容。

#### 召回与回答准确性主线（P0）

召回与准确性是当前 RAG 的核心主线，优先级高于缓存、GraphRAG、多 Agent、MCP 和 Kubernetes。BM25 只负责候选召回中的稀疏检索，不等于完整的召回质量，更不能代表最终回答准确。完整链路必须分层判断：

| 层次 | 当前已有 | 当前缺口 | 主要验收证据 |
| --- | --- | --- | --- |
| 查询理解 | 生产链路使用原始问题；已有确定性查询拆分对照，但真实结果退化后未接入 | 指代、多意图、同名概念和省略上下文仍可能让正确语料无法进入检索；不能把所有失败都归因于向量模型或 BM25 | 单意图、跨章节多意图、指代、同名概念分别标注；对比原查询与改写查询的召回、排序、拒答和额外调用成本 |
| 候选召回 | Dense Embedding、字段化 BM25、Hybrid-RRF；Chunk 保留来源、版本、标题路径、顺序、页码和块类型 | 语料缺失、Chunk 边界破坏语义、标题/代码/表格字段错误、多版本混杂都会造成漏召回；Sparse 只是其中一个通道 | 来源 Recall@5、Chunk Recall@5、标题路径与结构字段召回；失败样本必须定位到语料、解析、切分、索引或查询中的具体一层 |
| 融合与排序 | Dense/Sparse 分别取候选并按稳定 Chunk 身份去重，使用 RRF 融合；已有 Precision@5、nDCG@5、Hard Negative 和噪声指标 | RRF 只能融合已有候选，不能补回两路都没找到的资料；相邻 Chunk 扩展可能补上下文，也可能把无关内容送入模型 | 同时比较 Hit@1、MRR、nDCG@5、Precision@5、Hard Negative 避免率和上下文噪声；相邻扩展必须做开启/关闭对照 |
| 可靠拒答 | Dense/Hybrid 使用余弦阈值；Sparse 使用 `technical_anchor_coverage_v2` 的英文技术锚点和已确认中文 Hard Negative 短语门控，再按候选存在性拒答；固定开发集 17 道可回答题保留候选、9 道无答案题拒答 | 纯中文近域门控仍是样本化短语规则，Hybrid 两路冲突仍缺稳定判定；召回更多候选可能降低拒答准确率 | 分开统计可回答题保留率和无答案拒答准确率；继续补充真实中文近域失败样本，记录误答和误拒答，不只报一个总分 |
| 生成与引用准确性 | 无可靠资料时不调用 Chat；`rag-answer-v5` 禁止输出拆解/覆盖计划；Java 校验引用编号、相邻两句证据、技术锚点和相关否定短语；2026-09-04 真实 23 题引用精确率 `0.9055`、无依据陈述率 `0.1016`、冲突率 `0.0234`，15 题保留可靠或部分可靠回答 | 字面引用召回率仍只有 `0.0952`，主要受期望要点与回答改写不完全一致影响；确定性规则仍不能覆盖同义表达和隐含语义 | 保留确定性门槛作为低成本线上保护；同义表达校准进入真实失败样本回流，不再阻塞 Chunk/上下文主线，也不能用本次结果宣称完整语义正确率 |

指标口径必须分开，不能用某个满分指标替代整条链路：

| 指标 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| Hit@1、MRR、nDCG@5 | 正确来源或 Chunk 是否靠前，排序是否合理 | 回答是否正确、引用是否支持结论 |
| Recall@5、Chunk Recall@5、标题/结构召回 | 期望证据是否进入候选集合 | TopK 是否混入大量噪声、模型是否使用了证据 |
| Precision@5、Hard Negative 避免率、上下文噪声率 | 候选集合是否干净，错误上下文是否受控 | 缺失的正确资料能否被找回 |
| 无答案拒答准确率 | 语料没有答案时能否停止生成 | 可回答题是否被误拒答，以及有候选时回答是否正确 |
| 回答要点覆盖率 | 预期字面要点是否出现在回答中 | 同义表达、事实矛盾、错引和资料外陈述；当前 `normalized-literal-containment-v1` 不能替代语义审核 |
| 引用精确率、引用召回率、无依据陈述率 | 回答中的结论与证据是否真正对应，必要结论是否都有依据 | 检索系统对所有潜在问题的通用效果 |

当前证据边界：固定开发集已扩为 26 题，包含 17 道可回答题和 9 道应拒答题，语料为 8 份文档、18 个 Chunk；历史 Dense 基线和 2026-09-02 字段化三策略基线仍只覆盖旧的 20/23 题结果。2026-09-03 的 Sparse 技术锚点验收证明英文近域题的确定性门控；2026-09-07 的 3 道纯中文近域题证明表面重词候选会被 `technical_anchor_coverage_v2` 过滤，但尚未形成新的 storage 三策略付费基线。这些结果不能据此声称任意知识库的拒答或回答质量已经解决。

后续开发按以下顺序推进，每一步必须以业务代码闭环为主体，评估和文档只作为证据：

1. **回答引用合法性与事实一致性（已关闭当前门禁）**：已完成引用编号、逐句覆盖、相邻句证据、相关否定短语、逐要点诊断、生成/检索责任区分、SSE 句级门控和 claim 级部分答案净化；`rag-answer-v5` 真实 23 题结果达到引用精确率 `0.9055`、无依据陈述率 `0.1016`、冲突率 `0.0234`。字面引用召回 `0.0952` 继续作为评估语义边界记录，但不通过反复 Chat 调用追分。
2. **召回失败分层诊断（已完成首版）**：`RagRetrievalFailureLayer` 已接入当前来源登记、目录 `chunkCount` 和索引编排状态，可区分语料不存在、解析/切分零 Chunk、索引未就绪、候选未召回、排序过低和拒答门控过滤；回答要点诊断增加 `RETRIEVED_NOT_USED` 与 `RETRIEVAL_EVIDENCE_MISSING`，补齐生成未使用证据和检索证据缺失的责任边界。
3. **Chunk 与相邻上下文质量对照（已完成当前门禁）**：Markdown 代码围栏和带分隔行表格已进入 `CODE/TABLE` Chunk；相邻扩展真实 A/B 没有改善来源、Chunk 或回答要点证据召回，且噪声上升，因此生产回答默认关闭扩展。
4. **多存储失败补偿与主动巡检（已完成首版）**：新版本索引写入失败时按 `source + documentVersion` 补偿 Qdrant/Lucene 并撤销登记；旧版本清理失败时保留新版本，通过同版本重传只重试清理并让 `FAILED` 收敛到 `READY`。单来源只读巡检已直接比较 MySQL 目录期望数、Qdrant/Lucene 当前版本与来源总数，并报告缺失、超额、历史版本残留和存储不可用；进程重启后的持久化状态恢复与自动修复仍属于后续治理。
5. **Sparse/Hybrid 可靠拒答（样本化维护）**：纯中文近域门控首版已完成，暂只覆盖已确认 Hard Negative 短语；后续仅在出现真实误答/误拒答样本时调整，不把扩充样本或重复基线作为当前主线。
6. **简历表达教练（已完成）**：只消费审计确认事实，生成可复制但必须人工核对的候选改写；候选不进入简历存储、不自动投递，也不把模型表达视为新增事实。
7. **真实解析失败修复（按样本进入）**：仅在出现脱敏真实复杂版式或跨页表格失败时，修复页面顺序、结构块、Chunk 或检索中的具体一层，并晋升为回归样本；PDF 不再作为默认开发重点，也不以单纯扩题作为成果。

只有固定集出现排序瓶颈且 Dense/Sparse 已经召回正确候选时，才评估 rerank；只有原问题确实存在多意图或指代且简单改写有稳定净收益时，才重新考虑查询拆分。两路都没有召回、语料本身缺失或引用与结论不一致时，RRF、rerank 和增加 TopK 都不是正确答案。

## 二、随后开发：投递前有余量则推进

### 1. 图工作流、HITL 和 checkpoint

进入条件：普通证据审计已经稳定出现证据失败修正、条件分支、人工确认暂停或进程恢复需求。

候选流程：

```text
提取简历事实 -> Java证据校验 -> 证据失败时最多修正一次
               -> 生成诊断和建议 -> 暂停等待用户确认
               -> 从checkpoint恢复 -> 输出最终结果
```

涉及技术：Spring AI Alibaba Agent Framework/Graph、状态图、条件边、有界循环、Human in the Loop、checkpoint、节点级日志。

完成标准：与普通 Spring AI 基线使用同一批样本比较修正成功率、完成率、恢复率、模型调用次数、费用和 P95 延迟。版本升级或持久化不稳定时，只保留隔离 POC，不改主链路。

### 2. Agent 调用链可观测性（单实例业务中心已完成）

开发内容：当前已用 Actuator + Spring AI Observation 提供单实例 HTTP、JVM、Chat/VectorStore 指标，并完成业务观测中心：`X-Request-Id`、稳定路由成功/失败/耗时聚合、`/api/observability/overview` 和 Vue 运行观测页面。Prompt、简历和回答正文默认不采集。后续只有在出现跨服务或长期告警需求时，才使用 Micrometer Tracing/OpenTelemetry 串联检索、Chat、Tool 和图节点，统一 requestId/traceId，观测 token、费用、延迟和错误类型。

完成标准：能够定位一次请求在检索、模型、工具或图节点中的具体失败位置，并说明敏感数据和高基数标签的控制方式。

### 3. 岗位匹配顾问和项目深挖面试官

进入条件：简历证据审计官已经稳定，且相同的证据、日志和评估治理模式经过验证。

- **岗位匹配顾问**：已实现并完成一次真实脱敏验收。只用已验真事实和用户提供的 JD 做匹配，不把“简历未写”判断为“候选人不会”；匹配引文由服务端验真，请求元数据独立记录且不保存正文。当前单次样本返回 `MATCHED`、`PARTIAL`、`MISSING` 三类状态，后续不为同一输入重复付费寻找更高分。
- **项目深挖面试官**：完整训练闭环已实现。只接受审计确认的 `PROJECT` 事实，由 Java 固定生成基础、取舍、故障和扩展四类问题；知识检索默认关闭，显式开启后只返回答题背景来源，不参与项目事实推断。四题已作为 `PROJECT_DEEP_DIVE` 模式接入现有会话、逐题评分、报告和最近会话恢复，题数上限禁止动态追问；共享 MySQL 已执行并核验 `017_interview_session_mode.sql`。
- **简历表达教练**：已实现。只消费目标岗位和审计确认事实，服务端校验事实编号、候选长度和新增数字；前端展示依据与人工核对项，支持复制候选，不覆盖、持久化或投递简历。当前未把模型候选当作事实，也未执行付费批量质量基线。

| 结构化 Agent Memory | 建立用户身份、数据归属、冲突、过期和删除规则 | 只保存有来源的学习事实，不向量化全部聊天记录 |
| Hybrid Search、Sparse + Dense、rerank | Hybrid-RRF v1、字段化 BM25、Hard Negative/Chunk 级指标和拒答策略已接入；字段化真实复核只证明局部排序质量，Sparse 拒答准确率仍为 `0` | 先扩充 Hard Negative 和无答案题并改进 Sparse 可靠性过滤；无稳定收益不增加 rerank |
| 多模型路由和降级 | 固定任务证明不同模型存在稳定质量/费用差异 | 低成本模型做抽取，强模型做复杂评价，并记录降级结果 |
| DOCX | 出现真实 DOCX 简历输入需求 | 只做本地文本提取和格式提示，不与 OCR 绑定 |
| 主题学习路径和间隔重复 | 现有题目、attempt 和复习日期能够形成跨会话学习事实 | 先做确定性推荐，再判断是否需要模型规划 |
| 回答证据问题转为针对性复习 | claim 级证据状态和来源定位稳定，且用户明确需要从问答问题进入训练 | 只将 `EVIDENCE_INSUFFICIENT`、`EVIDENCE_CONFLICTING` 或合法引用缺口转成候选复习项；保留原问题、claim 状态和来源编号，用户确认后再进入复习计划，不把模型失败自动当作用户知识薄弱 |
| 公网部署 | 本地演示稳定并具备安全配置 | 增加反向代理、TLS、备份恢复和最小访问控制 |

## 四、明确延后或不进入主项目

- **OCR**：当前不开发；扫描件使用带文本层文件或手动粘贴，除非后续真实样本证明需求足够高。
- **A2A**：当前没有两个独立 Agent 系统，只保留协议学习或最小 POC。
- **Temporal**：只有出现跨分钟、跨重启的长任务且图 checkpoint 不足时再评估。
- **GraphRAG/Neo4j**：只有多文档、多实体、多跳固定样本证明向量 RAG 稳定失败时进入。
- **自由多 Agent、通用 Agent Runtime、AI Gateway**：当前不建设，不为了技术名称提前抽象平台。
- **语音视频、防作弊、多租户招聘平台、复杂权限后台**：与个人 Java 面试训练产品的当前定位不一致。
- **模型训练、微调、LLM Infra、Kubernetes**：不作为本项目主线，不在简历中包装相关生产经验。

## 开发停止规则

- 一个候选技术不能改善质量、恢复能力、成本或可解释性时，停止接入并保留实验结论。
- 同一时间只允许一个主要功能闭环和一个隔离 POC，不并行留下多个半成品。
- 投递前不再因为“技术更新”临时插入新框架；新方向先记录进入条件，投递后再评估。
- 已实现能力和未来路线必须分开维护；简历成果只引用 [项目技术栈与功能总结](08-项目技术栈与功能总结.md)。
- 项目掌握程度、学习范围和面试自测标准见 [面试准备与项目掌握要求](10-面试准备与项目掌握要求.md)。
