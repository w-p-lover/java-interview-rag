## firecrawl/pdf-inspector

- 地址：https://github.com/firecrawl/pdf-inspector
- 定位：面向 PDF 文本、版面、Markdown 和解析质量的快速检查工具。
- 本轮采纳：把 PDF 知识资料解析拆为页面文本、阅读顺序、图片/OCR 候选、Markdown 化和解析告警，而不是只判断“是否上传成功”；导入结果保留页数和告警，Qdrant 保留格式与页码。
- Java 实现：继续使用仓库已有 PDFBox `PdfDocumentAnalyzer` 和确定性基线，将页面结果适配到现有 Markdown/Chunk/版本/Qdrant 链路，不引入 Rust/Python 运行时。
- 未采纳：不把通用 Markdown/Table benchmark 当作当前 RAG 业务准确率，不直接替换现有解析器，不在首个闭环实现 OCR、复杂表格恢复或通用文档理解。
- 许可证边界：本轮只采纳公开设计思路，没有复制源码、模型或测试样本；后续若引入二进制或具体代码，必须重新核对届时仓库许可证和分发要求。

### 三条候选路线

1. **任务清单化**：先增加计划复习日期、筛选和提醒。优点是紧接现有复习任务且改动小；缺点是只能证明任务被安排或勾选，不能证明回答质量有变化。
2. **再答—对比—复盘**：为复习任务增加独立的再次作答 attempt，保存评分上下文与版本，比较原回答和历次回答，再汇总历史与趋势。该路线直接补上当前“知道遗漏但无法重新练习”的产品断点，是本轮推荐路线。
3. **平台治理先行**：先建设用户身份、全局历史、Prompt 中心、统一观测和管理后台。优点是长期结构完整；缺点是当前缺少多用户与规模数据，会提前扩大权限、迁移和前端范围。

决定采用路线 2。计划复习日期没有取消，而是调整到 attempt 数据形成之后；否则日期只会管理静态待办，无法指向一次可比较的训练行为。

### hiring-agent 的源码结论

1. **分段结构化简历而非一次性自由摘要**：其流程先把 PDF 转为 Markdown，再按 basics、work、education、skills、projects 等 section 分别使用模板提取为 JSON Resume。当前项目后端只保证 PDF 正文顺序，并由一次画像 Prompt 生成候选人摘要、证据和关注领域。可借鉴的是“结构化证据层”，但近期仍保留 `resumeText` / `jobDescription` 请求契约，不把 Python 解析器或 ATS 数据模型搬进来。
2. **岗位清单驱动评分结构**：其 [`role.json`](https://github.com/interviewstreet/hiring-agent/blob/main/roles/software_engineering_intern/role.json)、`criteria.jinja` 和 `system_message.jinja` 共同决定评分维度、上限、结构化 Schema 和证据字段。当前项目固定使用技术、完整性、表达三项分数，适合首个闭环，但还没有可持久化的 rubric 版本。
3. **评分必须可解释且承认方差**：其 README 已收录同一简历多次评分波动、公平性和提示注入风险；代码使用结构化 Schema、低温度、类别上限和 evidence，但这些措施仍不等于确定性。对本项目的直接启示是先保存 Prompt、rubric、模型与知识来源快照，并建立固定面试回答样本，而不是先做漂亮趋势图。
4. **不采纳范围**：不建设 ATS 排名、自动淘汰、GitHub 候选人加权、招聘公平性决策或 Python 主链路。GitHub 数据可验证性是另一项隐私和授权问题，当前不进入候选人画像。

### aural-oss 的源码结论

1. **session 与 attempt 分离**：[`004_interview_prep.sql`](https://github.com/1146345502/aural-oss/blob/main/supabase/migrations/004_interview_prep.sql) 分别保存练习会话和逐题 attempt；同一道题可以有多个 `attemptNumber`，每次保存回答、反馈、分数和时间。当前项目把每题唯一回答保存在会话 JSON 中，完成后不可再次作答，正是阶段 7 的首要缺口。
2. **再次作答使用历史上下文**：[`prep.ts`](https://github.com/1146345502/aural-oss/blob/main/src/lib/ai/prompts/prep.ts) 会把此前回答、分数、反馈摘要和改进项交给下一次评价；评价不只判断当前答案，还能检查是否真正吸收反馈。当前项目的复习任务只展示遗漏，没有下一次回答入口。
3. **评分规则与运行时保护配合**：[`answer-rubric.ts`](https://github.com/1146345502/aural-oss/blob/main/src/lib/prep/answer-rubric.ts) 统一参考答案和评分锚点；[`answer-quality.ts`](https://github.com/1146345502/aural-oss/blob/main/src/lib/prep/answer-quality.ts) 对测麦、占位提示、复述教练建议和无实质回答执行确定性分数上限。可借鉴“模型评分之后仍由服务端守住不可能的高分”，但不复制其针对美妆 BA 和语音场景的正则，也不在模型失败时伪造成功评价。
4. **历史建立在 attempt 事实之上**：`prepRouter` 先聚合尝试次数、平均分、最好分和弱项，再由 `practice-sessions-dashboard` 提供状态、时间范围和排序。当前项目没有用户身份或跨会话查询边界，因此先做单会话/单任务 attempt 时间线，跨会话看板必须等待明确的数据归属。
5. **每次反馈必须导向下一动作**：[`practice-next-move.tsx`](https://github.com/1146345502/aural-oss/blob/main/src/components/prep/practice-next-move.tsx) 在反馈后提供重答、查看示例、下一题或进入真实面试等动作。当前项目最适合先采纳“重答本题”，参考答案、答案库和真实面试模式在评分可靠性与用户事实校验建立后再评估。
6. **可观测性围绕反馈链路**：反馈接口记录解析、上下文加载、Prompt 构建、首个 token、评分和持久化阶段，并在反馈已展示但保存失败时返回独立警告。当前项目已有 RAG 召回日志，但面试评价没有 Prompt 版本、模型、耗时和失败类型记录；该缺口应在 attempt 闭环后补齐。
7. **不采纳范围**：不复制 Next.js、Supabase、RLS、语音视频、录音、反作弊、团队/组织、候选人邀请、白板、答案库和商业配额。它们不符合当前 Java 单体、个人求职训练和轻量 Agent 边界。

### 推荐的阶段 7 线路

1. **复习任务二次作答 attempt**：按复习任务创建多次回答，保留原面试答案；每次保存 attempt 序号、评价、实际知识来源、Prompt 版本、rubric 版本、模型和时间，并返回与原回答及上次 attempt 的差异。
2. **评分质量与评价日志**：建立固定面试回答样本，覆盖空回答、无关回答、复述建议、合格回答和知识不足；增加不保存原文的评价日志，记录版本、耗时、状态和失败类型。
3. **单会话历史与进步趋势**：基于真实 attempt 聚合尝试次数、首次/最好/最近分数、仍未解决遗漏和已解决遗漏；没有用户身份前不开放全库跨会话查询。
4. **计划复习日期与查询**：任务支持可选计划日期，按状态和日期查询；第一版不做提醒、定时器或间隔重复算法。
5. **Tool Calling 与执行记录**：只把已经稳定的“查询待复习任务、开始一次重答、安排日期”暴露为工具；工具结果和失败可追踪后，再判断是否需要图工作流或 MCP。

GraphRAG 的门槛保持不变：先有足够的 attempt、薄弱项、知识来源和跨文档问题，再用评估数据证明普通 RAG 无法处理的关系缺口。

### 暴露的当前差距

- 原 `/interview` 用大 Hero、技术英文标签和产品说明占据首屏，用户需要先理解系统再开始面试。

## 2026-08-12：AI 应用前沿技术与本项目采纳分层

### 已进入工程主流，值得持续投入

- **混合检索与多阶段重排**：Dense Embedding、Sparse/BM25、元数据过滤、RRF/加权融合和 Cross-Encoder/ColBERT 重排已经形成清晰工程路径。Qdrant Query API 支持 dense/sparse 融合、多阶段查询、RRF、DBSF 和多向量重排，但权重与策略必须由本项目评估集决定。
- **上下文化检索**：从固定长度切片转向结构化切片、标题路径、父子索引、相邻扩展、Contextual Embedding 和 Contextual BM25。当前项目已有 `headingPath`，应先投影章节树与稳定主题引用，再比较检索收益。
- **模块化 RAG**：查询改写、检索、后处理、去重、压缩和重排拆成可单独评估的模块。Spring AI 已提供 Query Transformer、Document Retriever 和 Document Post-Processor 等边界，项目无需为了使用这些模式切换主框架。
- **持续评估**：检索 Recall@K/MRR/nDCG、回答完整性、Groundedness、引用正确性、拒答、延迟、token 和跨版本方差共同组成质量闭环。项目现有固定检索集、评分基线和日志是正确基础，应继续用真实失败样本扩展。
- **受控 Tool Calling**：模型负责识别意图和选择有限工具，服务端负责参数校验、会话隔离、幂等、人工确认和审计。当前复习助手已经落在这一方向，不扩展为无限自主循环。

### 正在快速成熟，适合有门槛地验证

- **Agentic RAG 与 Context Engineering**：Agent 按需决定是否检索、拆分查询和继续补充证据，并通过轻量标识逐步加载上下文。只有出现确定性单次检索不能覆盖的任务时才增加有次数、成本和工具范围限制的循环。
- **多模态文档理解**：版面、阅读顺序、表格、公式、图表、OCR 和视觉语言模型正在替代“所有文件转纯文本”的粗粒度入口。当前先建立真实 PDF 质量样本，再决定增强 Java 解析、接独立服务还是引入 OCR。
- **持久化工作流与 Agent Memory**：长任务恢复、人工介入、上下文压缩和结构化外部记忆逐渐成为 Agent 工程重点。当前项目缺少用户身份和跨会话数据归属，只维持单会话事实，不提前建设长期记忆中心。
- **MCP**：适合标准化外部客户端对资源和工具的复用。项目已有 Spring AI 工具回调，但没有明确跨应用消费方，因此继续保留为后续集成选项。

### 研究和平台热度较高，当前不重仓

- **GraphRAG**：适合跨实体、多跳和全局归纳；先建立多文档、多实体、多跳固定样本，证明普通向量 RAG 稳定失败后再选型。
- **A2A 与多 Agent**：A2A 解决不同 Agent 的发现和长任务协作，MCP 解决模型应用连接工具和数据，两者不是同一层。当前单体面试训练业务没有多 Agent 必要性。
- **通用 AI Gateway、自我进化 Agent、无限记忆和完全 RAG-free 长上下文**：缺少多供应商故障、成本、权限和效果数据前，不进入当前开发路线。
