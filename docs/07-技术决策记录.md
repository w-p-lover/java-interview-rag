# 技术决策记录

## 记录格式

重要决策按“背景、选项、决定、理由、影响、回看条件”记录。普通类名和局部实现不需要单独建条目。

## ADR-001：主项目与新项目保持独立

- 背景：`blog-springboot` 已经具备内容平台、RAG 和 AI 任务治理能力，并在持续修改。
- 决定：`java-interview-rag` 使用独立仓库，主项目仅允许只读参考。
- 理由：避免并发修改冲突和重复建设，使新项目专注 RAG 评估与面试训练能力。
- 影响：所有写入和自动开发只发生在本仓库。
- 回看条件：无；这是长期项目边界。

## ADR-002：采用有边界的自主开发

- 背景：定时任务需要持续推进，不因普通技术选择频繁申请用户意见。
- 决定：允许自主选择可逆、简单、符合定位的方案；只有真实费用、密钥权限、不可逆操作、许可证冲突和核心定位冲突等硬阻塞才等待用户。
- 理由：提高持续开发效率，同时控制安全和方向风险。
- 影响：重要选择必须记录，局部阻塞优先绕开并推进其他安全任务。
- 回看条件：自主修改连续造成方向偏离或无法验证的改动时。

## ADR-003：允许正常 Git 开发流程

- 背景：自主开发需要为每个已验证闭环保留清楚、可回溯的版本记录。
- 决定：允许自主使用 `codex/` 分支、暂存和提交直接相关改动；远程配置明确时允许正常 push 当前开发分支。
- 理由：让定时开发形成小而完整的提交，便于检查、回退和持续推进。
- 限制：禁止强推、重写历史、覆盖用户改动、自动合并主分支、擅自创建或合并 Pull Request。
- 回看条件：项目接入明确的分支保护或 Pull Request 工作流时。

## ADR-004：阶段 0 使用最小 Spring Boot 依赖基线

- 背景：阶段 0 只要求建立可运行骨架，Web 接口、Spring AI、数据库和向量存储尚无已实现业务。
- 选项：一次性引入后续候选依赖，或只引入 Spring Boot 基础启动与测试依赖。
- 决定：使用 Java 17、Spring Boot 3.5.16、Maven Wrapper 3.9.14，只引入 `spring-boot-starter` 和 `spring-boot-starter-test`。
- 理由：满足最小启动和上下文验证，同时避免在需求与环境未确定前锁定无用依赖；3.5.16 是实施时 Maven Central 可用的最新 Spring Boot 3.x 稳定版，符合既定 Boot 3 边界。
- 影响：后续每项能力在出现真实业务和针对性测试时再增加所需依赖。
- 回看条件：进入需要 HTTP 接口、持久化、Spring AI 或向量存储的具体任务时。

## ADR-005：Markdown 内容版本使用规范化换行后的 SHA-256

- 背景：阶段 1 需要稳定识别文档内容版本，并避免 Windows 与 Linux 换行符差异导致相同内容被当成新版本。
- 选项：使用时间戳、对原始字节直接摘要，或先统一换行符再计算内容摘要。
- 决定：保留独立的文档来源；将 `CRLF` 和 `CR` 统一为 `LF` 后，按 UTF-8 内容计算 SHA-256 作为版本标识。
- 理由：结果确定、跨平台稳定、无需新依赖；来源不进入摘要，后续以“来源 + 版本”判断同一来源的重复导入。
- 影响：只有换行风格不同的内容版本相同；空格、标题和正文等其他内容变化仍会生成新版本；不同来源即使内容相同也保持为不同文档。
- 回看条件：实际语料出现需要忽略 BOM、尾随空格或其他格式差异的重复导入问题时。

## ADR-006：第一版标题解析使用 ATX 逐行扫描

- 背景：阶段 1 需要为 chunk 切分保留标题层级和正文顺序，Java 面试 Markdown 中又包含大量围栏代码块，不能用简单正则分割整篇文档。
- 选项：直接按标题正则切割、引入完整 CommonMark AST 库，或实现能识别代码围栏的最小逐行扫描器。
- 决定：第一版不新增依赖，逐行识别 1 到 6 级 ATX 标题，并跟踪反引号和波浪线围栏代码块；解析结果保存来源、顺序、实际标题级别、标题路径和正文。
- 理由：比整篇正则切割更可靠，能够覆盖当前知识库最常见的标题和代码示例；同时比提前引入完整 AST 更小、更容易验证。
- 影响：当前不识别 Setext 标题、HTML 块和其他完整 CommonMark AST 结构；正文只统一换行并裁剪 section 边界空行，内部段落顺序保持不变。
- 回看条件：真实语料出现较多 Setext 标题或后续解析需要列表、表格等块级 AST 信息时。

## ADR-007：第一版 chunk 使用段落优先的字符长度上限

- 背景：标题解析已经得到有序 section，阶段 1 需要继续生成长度可控且能够追踪来源与标题路径的 chunk。
- 选项：只按段落切分、完全按固定长度切分，或优先保留完整段落并对超长单段执行定长切分。
- 决定：按输入 section 顺序处理正文，优先将相邻完整段落合并到最大 Java 字符长度；单个段落超过上限时连续定长切分；chunk 单独保存全局顺序、原 section 顺序和标题元数据。
- 理由：兼顾段落语义边界与严格长度上限，能够直接验证顺序和边界；当前尚未选择 Embedding 模型，不提前引入 tokenizer、overlap 或第三方依赖。
- 影响：空正文不产生 chunk，段落间用两个换行符连接；超长单段可能在句子或代码中间切开，当前长度依据是 Java `String.length()`，不是模型 token 数。
- 回看条件：接入具体 Embedding 模型后，根据 token 上限、实际语料和 RAG 评估结果决定是否改为 token 预算、增加 overlap 或优化长段落边界。

## ADR-008：第一版导入登记使用来源与版本联合键

- 背景：阶段 1 已具备稳定内容版本，需要避免相同文档版本被重复解析和切分，同时不能把同内容的不同来源合并为一个文档。
- 选项：只保存每个来源的当前版本、保存历史“来源 + 版本”联合键，或直接接入数据库持久化登记。
- 决定：第一版使用进程内集合保存结构化的来源与版本联合键；首次登记返回成功，历史上已登记过相同联合键时返回重复。
- 理由：联合键能够覆盖相同版本不重复导入、同来源内容更新和不同来源内容相同三种核心语义；进程内实现无需提前确定阶段 2 的数据库与持久化结构。
- 影响：进程重启后登记状态丢失，当前也不承诺并发登记安全；这些限制不会被包装为持久化导入能力。
- 回看条件：实现持久化文档元数据、完整导入流水线或出现并发导入需求时。

## ADR-009：文件导入使用显式逻辑来源和结构化结果

- 背景：文档模型、重复登记、标题解析和 chunk 切分已经独立可用，需要提供最小文件入口把它们串联起来，同时避免本机路径污染后续来源引用。
- 选项：直接把文件绝对路径作为来源、只返回 chunk 列表，或由调用方传入逻辑来源并返回包含导入状态的结构化结果。
- 决定：第一版固定按 UTF-8 读取单个文件，文件路径只负责定位内容，逻辑来源由调用方显式传入；结果返回文档、是否首次导入和不可修改的 chunk 列表。
- 理由：逻辑来源不依赖部署机器，能够稳定用于去重和后续引用；独立导入状态可以区分重复导入与成功但没有 chunk 的空文档。
- 影响：相同物理文件可以按不同逻辑来源分别登记；重复版本直接返回空 chunk，不再解析和切分；当前不扫描目录、不校验扩展名，文件读取异常由调用方处理。
- 回看条件：引入上传接口、对象存储、批量目录导入或持久化文档来源模型时。

## ADR-010：首个 Web 闭环采用 Spring MVC 与独立 Vue 子项目

- 背景：阶段 1 的文件导入链路已经可调用，用户需要先看到真实功能并搭建参考 `shoka-blog` 分层方式的 Vue 界面。
- 选项：将页面打包进 Spring Boot、建立独立 Vue 子项目，或提前建设完整管理后台。
- 决定：后端增加 Spring MVC multipart 接口；前端在仓库内建立独立的 Vue 3、Vite、TypeScript 子项目，通过开发代理调用 `/api`。后端开发端口使用 `18080`，前端使用 `5173`。
- 理由：独立前端便于保持 API、路由、视图、组件和样式边界，也能复用现有导入核心；`18080` 避开本机已有 Tomcat 对 `8080` 的占用，不需要停止或修改用户服务。
- 影响：当前需要分别启动前后端；页面只展示已实现的导入与切分能力，不引入 Pinia、UI 框架、持久化、Embedding、向量库或 RAG 问答。
- 回看条件：进入正式部署、需要同源静态资源交付，或出现多个页面共享复杂状态时。

## ADR-011：首页表达求职面试产品主线而不是资料处理管线

- 背景：首个 Web 页面把 `SOURCE → HASH → SECTION → CHUNK` 作为主视觉，能够展示阶段 1 技术闭环，但用户难以理解系统与简历解析、求职方向和模拟面试的关系，视觉也呈现常见生成式模板特征。
- 选项：继续把资料导入作为首页、提前伪造完整面试数据，或用真实可用能力承载求职面试产品主线。
- 决定：首页定位为“求职面试工作台”，表达“求职目标 → 资料准备 → 模拟面试 → 训练复盘”；当前 Markdown 导入与 chunk 检查作为资料准备区域保留，未实现模块只说明状态，不提供假结果。
- 理由：产品价值来自针对求职方向的简历理解和训练闭环，RAG 文档处理只是支撑能力；真实能力与未来主线同时可见，既不误导用户，也不让阶段开发偏离长期定位。
- 影响：前端采用中性浅色、单一 UI 字体、标准控件和语义状态色；当前页面不再自动跟随系统暗色偏好，后续有真实主题需求时再提供明确主题设置。
- 回看条件：候选人画像与文本模拟面试完成后，根据真实工作流重新划分首页、求职档案、资料库、面试训练和训练记录路由。

## ADR-012：存储接入复用技术方式但隔离数据

- 背景：阶段 1 的进程内版本登记在后端重启后丢失，阶段 2 也需要确定 Embedding 与向量数据库接入边界；用户要求参考 `blog-springboot`。
- 选项：直接复用主项目数据库和 collection、重新选择完全不同的存储栈，或复用接入方式但使用独立数据空间。
- 决定：使用 MySQL、Druid、MyBatis-Plus、Spring AI Alibaba DashScope Embedding 和 Qdrant；数据库固定为 `java_interview_rag`，collection 默认为 `java-interview-rag-chunks`，私有配置使用 `JAVA_INTERVIEW_RAG_` 前缀。
- 理由：技术方式与已有 Java 项目一致，学习和部署成本可控；数据隔离避免两个持续开发项目互相污染，也不需要读取主项目凭据。
- 影响：默认 `local` profile 继续使用内存登记且不依赖外部服务；`storage` profile 使用 MySQL 登记并装配向量客户端。Druid 使用与 Boot 3.5 兼容的专用 Starter 1.2.28，而非参考项目的旧 Starter 1.2.14。
- 限制：当前只持久化版本登记，不自动创建 Qdrant collection 或写入 chunk 向量；真实连通需要 Docker 服务和 DashScope API Key。
- 回看条件：完成向量新增、重复、更新、删除和重建闭环时，扩展文档状态和向量生命周期字段。

## ADR-013：复用服务器连接配置但不复用业务数据空间

- 背景：实际 MySQL、Qdrant 和 DashScope 服务运行在主项目 `.env` 所指向的服务器上，新项目需要接入该服务器，而不是连接本机默认地址。
- 选项：复制主项目 `.env` 到新项目、直接使用主项目数据库与 collection，或只读导入主项目 `.env` 的连接信息并重写数据空间。
- 决定：`application-storage.yml` 只在 `storage` profile 下只读导入 `D:/IdeaProjects/blog/blog-springboot/.env`；复用其中的 MySQL 主机、端口、账号、密码、Qdrant 地址和 DashScope Key，但数据库名强制使用 `java_interview_rag`，collection 强制使用 `java-interview-rag-chunks`。
- 理由：避免复制和提交敏感配置，同时利用已经运行的服务器基础设施；数据隔离保证新项目不会写入主项目 `blog` 数据库或 `blog-articles` collection。
- 影响：服务器 `.env` 的 `BLOG_DB_URL` 不直接使用，防止继承 `blog` 数据库名；只拆出 `BLOG_DB_HOST`、`BLOG_DB_PORT` 等连接字段构造新 URL。当前项目自己的 `JAVA_INTERVIEW_RAG_` 变量仍可覆盖服务器 `.env` 的默认值。
- 限制：服务器必须预先存在 `java_interview_rag` 数据库并执行初始化 SQL；本轮不自动执行远程建库或生产数据变更。
- 回看条件：后续部署方式改变，或主项目 `.env` 不再作为服务器连接配置来源时。

## ADR-014：chunk 使用稳定向量 ID 并在写入失败时撤销版本登记

- 背景：版本登记已经能够跨进程拒绝重复导入，但如果在登记后写入 Qdrant 失败，保留登记会让相同文档永久短路，无法重试；随机向量 ID 也会在重试时生成重复点。
- 选项：先写向量再登记、登记后写向量但不补偿，或登记后使用稳定 ID 写向量并在失败时撤销登记。
- 决定：保持 MySQL 唯一键作为并发去重入口；每个向量 ID 由来源、文档版本和 chunk 顺序稳定生成。Qdrant 批量写入失败时删除同一来源与版本的登记，再抛出原异常。
- 理由：先登记保留数据库唯一键的原子去重语义；稳定 ID 让重试覆盖同一批点；撤销登记避免外部服务短暂失败后文档无法再次导入。
- 影响：`local` profile 使用空索引器，现有纯文档导入调用不依赖外部服务；`storage` profile 写入正文和可追踪元数据。MySQL 与 Qdrant 之间仍没有分布式事务，极端部分写入且撤销失败时需要后续重建能力处理。
- 回看条件：实现文档状态机、异步向量任务或手动重建后，考虑用明确的 `PENDING/SUCCESS/FAILED` 状态替代同步补偿。

## ADR-015：同来源更新先写新向量再清理旧向量

- 背景：首次导入已经能够写入 Qdrant，但同一来源的新内容会与旧版本同时保留，文档删除也无法清理向量和历史登记。
- 选项：先删旧向量再写新向量、先写新向量再删旧向量，或立即引入完整文档状态机。
- 决定：新版本先登记并使用稳定 ID 写入向量，成功后按来源相等、版本不等的结构化过滤条件删除旧向量；显式删除先清理来源下全部向量，再删除该来源全部历史登记。
- 来源语义：来源按 Java 精确字符串区分大小写并拒绝首尾空白；MySQL `source` 使用 5.7/8 均支持的 `utf8mb4_bin`，删除语句额外使用 `BINARY` 比较，使关系登记与 Qdrant 元数据过滤保持一致。
- 理由：先写后删能在 Embedding 或新向量写入失败时保留旧资料可用性；保留历史登记继续阻止已处理版本被重复向量化，显式删除则提供重新导入任意历史版本的明确入口；当前无需为同步闭环增加状态字段和异步恢复复杂度。
- 影响：旧向量清理失败时撤销本次新版本登记，稳定 ID 允许重试收敛；显式删除的 Qdrant 步骤失败时数据库保持不变。MySQL 与 Qdrant 仍无分布式事务，向量删除成功但数据库删除失败时接口会报错，调用方需要重试幂等删除。现有环境需要执行 `002_source_exact_collation.sql`，新建数据库由初始化脚本直接获得精确排序规则。
- 回看条件：实现手动重建、异步索引、版本回滚或需要展示当前版本状态时，引入明确的文档当前版本和 `PENDING/SUCCESS/FAILED` 状态。

## ADR-016：手动重建由调用方重传已登记版本正文

- 背景：普通导入会在已登记“来源 + 版本”处短路，无法修复 Qdrant 点缺失或残留；当前版本表只保存元数据，没有可供服务端独立恢复的 Markdown 正文。
- 选项：重传来源和文件并校验登记、扩展 MySQL 保存原始正文，或删除登记后复用普通导入。
- 决定：增加同步 multipart 重建接口，由调用方重传来源与 Markdown 文件；服务端计算版本并确认精确联合键已登记后重新解析、切分和写向量。重建不改变登记，失败原样抛出并允许同一请求重试。ADR-069 进一步收紧为只允许当前登记版本，历史登记不能直接激活。
- Qdrant 顺序：非空文档先写入或覆盖全部稳定 ID 预期点，再删除同来源其他版本，最后删除同来源同版本且 `chunk_order` 大于等于当前 chunk 数量的残留点；空文档直接删除该来源全部向量。
- 理由：在不扩大正文存储、隐私和迁移边界的前提下补齐可验证恢复能力；先写后删保留写入失败时的旧向量可用性，稳定 ID 和结构化过滤使重试可以收敛。
- 影响：调用方必须保留并重新提交当前版本原文件；未登记内容不能借重建入口创建登记，历史版本回滚需要未来明确的正文与当前状态模型，不能通过重建旁路完成。
- 回看条件：正式建立简历与资料正文存储、异步索引任务、批量自愈或需要无需原文件恢复时，引入文档内容与明确的 `PENDING/SUCCESS/FAILED` 状态模型。

## ADR-017：资料准备页采用任务导向的 Hallmark Workbench

- 背景：现有页面能够完成 Markdown 导入，但视觉语言较为朴素，且把长期求职路线放在导入输入与结果之间，造成中间内容与左右任务缺少直接关系。
- 选项：继续局部调整旧样式、改为展示型营销页面，或保留真实功能并使用任务导向 Workbench 重建视觉和信息关系。
- 决定：采用 Hallmark `modern-minimal + Workbench + Coral`；用集中式 OKLCH 令牌管理颜色、字体、间距、动效和圆角，保留真实上传与结果组件。主工作区固定为输入与结果两栏，其上只展示真实导入链路；长期能力放入页面说明与能力边界。
- 理由：Workbench 适合当前已经可操作的产品页面；Coral 比初稿 Cobalt 更柔和但仍保持克制。真实处理链能够解释左右数据流，避免为了视觉结构插入与本次任务无关的中间栏。
- 影响：新增 N13 命令面板和 Ft2 单行页脚；不引入 UI 框架、Pinia 或动效库。所有未实现模块继续只说明边界，不提供假入口和假数据。
- 回看条件：进入文本模拟面试阶段并形成多页面导航后，重新评估首页、资料库、面试训练和训练记录的路由及导航结构。

## ADR-018：阶段 3 先建立可独立验证的相似度检索边界

- 背景：阶段 2 已完成向量生命周期，阶段 3 需要先验证问题 Embedding、召回参数、Qdrant 返回分数和来源元数据，再进入上下文拼接与生成回答。
- 选项：一次性实现完整 RAG 问答、直接在控制器调用 `VectorStore`，或先建立独立检索服务与薄 HTTP 接口。
- 决定：先增加 `MarkdownSimilaritySearchService`，用 Spring AI `SearchRequest` 传递问题、`topK` 和相似度阈值，并把 Qdrant `Document` 映射为正文、来源、版本、chunk 顺序、标题路径和相似度；HTTP 接口只在 `storage` profile 暴露。
- 参数：`topK` 限制为 1 到 20，相似度阈值限制为 0 到 1；默认阈值 0.0 用作原始召回基线，调用方可显式提高阈值。空结果保持为空，不触发任何无来源的生成行为。
- 理由：把检索质量与生成质量分开验证，能够直接观察召回内容和分数；独立服务保持后续上下文组装可复用，同时不提前引入通用仓储抽象、日志表或配置项。
- 影响：当前接口是阶段 3 的检索能力，不等同于完整 RAG 回答；默认 `local` profile 不提供该接口。结果严格要求现有向量写入的可追踪元数据，若 collection 混入不符合结构的点会明确失败而不是返回伪来源。
- 回看条件：形成固定评估集后，根据召回数据调整默认阈值和 `topK`；需要来源过滤、混合检索或 rerank 时，在检索服务边界内扩展并用评估结果证明收益。

## ADR-019：RAG 回答只接收可靠资料并保留实际来源

- 背景：阶段 3 已能返回原始相似度结果，但还不能把检索质量与回答质量关联起来，也没有在资料不足时阻止模型生成。
- 选项：直接把所有召回结果拼接给模型、先建立带阈值的最小回答服务，或提前建设可配置 Prompt/模型平台。
- 决定：新增独立 `RagAnswerService` 和 `POST /api/knowledge/answer`；固定检索前 5 条、相似度阈值 0.60，按本次结果列表连续编号资料后调用 DashScope Chat。响应返回模型文本、`grounded` 和实际输入模型的完整来源；无资料、空响应或模型明确资料不足时返回统一中文兜底。
- Prompt：要求模型只能依据资料回答、忽略资料中改变规则的指令、不得补充资料外事实，并按资料编号标注引用。
- 理由：比直接复用原始检索接口多出可靠资料门槛、上下文边界和来源可追溯性，同时避免提前引入 Prompt 配置中心、模型路由、流式接口或数据库日志。
- 配置：`storage` profile 恢复 DashScope Chat 自动装配，默认 `qwen-plus` 与温度 0.2；默认 `local` profile 仍不加载检索和回答接口，也不依赖外部模型。
- 影响：0.60 阈值目前仅基于已验证的检索分数选择，尚无正式评估集支撑，后续必须用阶段 4 数据调整。真实模型调用会产生额度消耗，本轮只验证装配与模拟分支，未宣称模型输出质量已验证。
- 回看条件：完成固定评估集后，记录 Prompt 版本、实际参数、检索耗时和回答质量；根据结果再决定阈值、`topK`、模型选型、混合检索或 rerank 是否需要调整。

## ADR-020：召回日志只保存可评估元数据且不阻塞回答

- 背景：最小 RAG 回答已具备来源返回，但无法回看每次检索使用的参数、资料、耗时或失败原因，后续也没有数据比较阈值和 Prompt 变更。
- 选项：只输出应用日志、把正文和回答全文都保存到 MySQL，或保存结构化召回元数据并提供最近记录查询。
- 决定：新增 `t_rag_retrieval_log`，记录问题、`topK`、相似度阈值、Prompt 版本、状态、可靠依据、来源元数据 JSON、总耗时和失败类型；来源只保留来源、版本、chunk 顺序、标题路径和相似度。提供 `GET /api/knowledge/retrieval-logs` 查询最近记录。
- 失败语义：日志写入故障只输出警告，不得影响已生成回答；模型异常则记录 `FAILED` 与异常类型后原样抛出。资料不足记录 `INSUFFICIENT`，成功回答记录 `ANSWERED`。
- 理由：结构化数据足以支持阶段 4 的定位、分析和评估，又避免日志表无边界保存资料正文、模型回答和潜在敏感内容；日志不可用不应降低核心问答可用性。
- 影响：当前迁移脚本需要在独立 `java_interview_rag` 数据库手动执行，未建表时回答继续可用但日志查询不可用。当前没有固定评估题集，0.60 阈值和 `rag-answer-v1` Prompt 版本尚不能用数据判断优劣。
- 回看条件：建立评估集并积累真实调用日志后，增加批量评估结果、来源命中率和回答要点评分；必要时再决定是否保存模型名、token 用量或引入更细粒度的日志表。

## ADR-021：Chat 模型独立切换为 qwen3.7-plus

- 背景：当前项目继续使用阿里百炼，用户指定将默认 RAG Chat 模型从 `qwen-plus` 切换为 `qwen3.7-plus`；OpenAI 兼容中转改造暂不进入当前阶段。
- 选项：同时替换 Chat 与 Embedding、仅替换 Chat，或提前接入中转协议。
- 决定：仅将 `storage` profile 的 DashScope Chat 默认模型切换为 `qwen3.7-plus`，温度保持 0.2；Embedding 保持 `text-embedding-v3`，Qdrant collection 和已有向量保持不变。
- 理由：Chat 与 Embedding 在当前链路中职责独立。仅切换生成模型不会改变向量语义空间，改动最小；若同时切换 Embedding，则必须重建所有向量，不符合当前“先开发评估功能、后处理供应商迁移”的优先级。
- 影响：未定义 `JAVA_INTERVIEW_RAG_DASHSCOPE_CHAT_MODEL` 时使用新默认值；部署环境仍可通过该项目级变量覆盖。此前 `qwen-plus` 的 HTTP 403 仅代表当时调用与额度状态，`qwen3.7-plus` 的真实回答质量和额度可用性需要后续受控验证。
- 回看条件：固定评估题集完成后，根据回答质量、额度和稳定性再决定是否切换 OpenAI 兼容中转、DeepSeek Chat 或其他模型；届时若更换 Embedding，必须安排向量重建。

## ADR-022：固定评估题集先以只读代码基线落地

- 背景：阶段 4 已记录召回日志，但缺少稳定的问题、期望来源和回答要点，无法在改变阈值、Prompt 或模型后进行可重复对比；当前模型额度不适合先建设依赖真实模型调用的批量评估。
- 选项：立即新增 MySQL 评估表和管理接口、将题目仅写入文档，或以内置只读题集加查询接口先建立基线。
- 决定：新增 `RagEvaluationCase` 和 `FixedRagEvaluationDataset`，以 6 条不可变 Java/RAG 基线题目提供 `GET /api/knowledge/evaluation-cases`；每题保存稳定标识、问题、期望逻辑来源与预期回答要点。
- 理由：代码基线可直接被后续批量服务消费并由单元测试固定，不增加评估管理、数据库迁移或外部调用复杂度；HTTP 查询使前端与后续工具可以读取同一份定义。期望来源采用与现有导入接口一致的逻辑来源字符串，能够直接比较来源是否命中。
- 影响：题集不自动导入资料，也不生成模型回答、评分或持久化结果；进行真实评估前必须按预期来源导入对应 Markdown。题集扩大、用户自定义或历史结果管理出现真实需求后，再引入 MySQL 持久化。
- 回看条件：实现批量检索评估后，根据题集覆盖度和实际偏差决定是否扩充到 20 至 50 题、增加分类/难度，或增加回答要点评分与结果表。

## ADR-023：qwen3.7-plus 使用阿里百炼官方兼容 Chat 端点

- 背景：用户指定默认 Chat 模型为 `qwen3.7-plus`。模型在阿里百炼官方兼容接口的账号可见列表中存在，但 Spring AI Alibaba 原生 DashScope Chat 路径调用返回 HTTP 400 URL 错误。
- 选项：继续使用原生 Chat 路径、退回旧模型，或保留阿里百炼账号和 Embedding 但让 Chat 使用官方 OpenAI 兼容端点。
- 决定：增加 Spring AI OpenAI Starter，关闭 DashScope Chat 自动配置；应用入口全局排除 OpenAI 自动配置，`storage` profile 以 `https://dashscope.aliyuncs.com/compatible-mode` 和同一 DashScope API Key 手动创建 `qwen3.7-plus` Chat 模型。原生 DashScope 继续负责 `text-embedding-v3`，不会更换或重建已有向量。
- 理由：兼容端点是阿里百炼官方接口，不引入第三方中转；它已通过受控资料的真实回答、资料引用与 `ANSWERED` 日志验证。保留原生 Embedding 避免改变向量语义空间和生命周期。
- 影响：OpenAI Starter 包含当前不需要的图像、音频、Embedding 与审核自动配置，应用入口统一排除这些能力；以手动 Bean 避免私有 local profile 覆盖 YAML 排除列表后意外装配音频模型，继续保持无密钥启动。
- 回看条件：模型、官方端点或 Spring AI 版本变动时重新验证兼容性；若后续切换 Embedding 供应商，必须独立安排全量向量重建。

## ADR-024：批量评估先衡量检索来源命中率

- 背景：固定题集已定义期望来源和回答要点，但真实 Chat 批量调用有额度与耗时成本；检索质量应先独立于生成质量比较。
- 选项：直接执行全部模型回答并评分、只保留题集定义，或先批量执行检索并比较来源命中。
- 决定：增加 `RagRetrievalEvaluationService` 和 `GET /api/knowledge/evaluations/retrieval`，固定使用 `topK=5`、相似度阈值 0.0，输出每题实际来源、期望来源匹配标记、总命中数与命中率。
- 理由：复用现有检索服务保持与线上搜索相同的向量化和来源映射语义；阈值 0.0 作为召回基线，先观察原始来源命中，再以数据调整阈值或引入 rerank。该接口不调用 Chat，不产生回答费用或召回日志噪声。
- 影响：执行真实批量评估仍会为每题调用 Embedding，且必须先按期望来源导入完整评估语料；当前不保存评估历史，也不对回答要点自动评分。
- 回看条件：取得真实批量来源命中率后，增加结果持久化、回答要点对比、分类指标和必要的阈值/`topK` 对照实验。

## ADR-025：固定评估语料作为仓库内可复现基线

- 背景：固定题集和批量检索接口已经实现，但没有与 `expectedSources` 对应的稳定 Markdown，真实评估依赖临时手工资料，无法复现或比较后续改动。
- 选项：每次临时生成并删除资料、应用启动时自动导入，或在仓库保存语料并通过显式运行器导入。
- 决定：在 `evaluation/corpus/` 保存 5 份 UTF-8 Markdown，逻辑来源精确匹配固定题集；提供 Python 标准库运行器，通过现有 HTTP 接口幂等导入并执行批量检索。真实响应按日期保存在 `evaluation/results/`。
- 理由：仓库语料可审查、可版本化，显式运行不会在普通启动时污染知识库；复用 HTTP 接口保证评估经过与真实资料相同的版本、切分、Embedding 和向量写入链路，不增加直接操作 MySQL/Qdrant 的旁路。
- 影响：基线资料作为项目独立知识库的稳定输入保留，不自动清理。首轮 6 道题全部首位命中期望来源，但题量较小且语料针对性明确，该结果只用于后续同题集对照，不能代表复杂生产知识库的总体质量。
- 回看条件：题集扩充、需要多套语料版本、CI 环境不能访问外部 Embedding，或需要把评估结果迁移到数据库管理时。

## ADR-026：回答评估先使用可解释的标准化字面覆盖

- 背景：固定题集已定义预期回答要点，真实检索也已全部首位命中期望来源；阶段 4 需要继续比较模型回答是否覆盖这些要点，但额外模型裁判会增加费用和评分不确定性。
- 选项：增加模型裁判做语义评分、直接按原始字符串精确匹配，或先对大小写、空白和标点归一化后比较完整要点。
- 决定：第一版使用 `normalized-literal-containment-v1`；回答和预期要点转为小写并移除非字母数字字符，再判断回答是否包含完整要点。`POST /api/knowledge/evaluations/answers` 逐题复用现有回答服务，返回实际来源、来源命中、命中与未命中要点及汇总覆盖率。
- 理由：标准化字面匹配确定、可复现、无额外模型费用，能够先暴露明显遗漏；接口使用 `POST`，准确表达执行 6 次 Chat 调用和写入召回日志的副作用，避免被浏览器或缓存当作普通查询。
- 影响：指标只表示字面覆盖，不能识别同义改写，也不能替代语义正确性、事实一致性或人工评审。任一题调用失败时沿用现有回答服务异常语义并终止批量请求；当前不保存评估报告。
- 回看条件：真实回答基线显示大量正确同义改写被误判，或需要稳定比较不同 Prompt 与模型的语义质量时，再评估结构化模型裁判、人工标注或结果持久化。

## ADR-027：用户面试准备画像与内部固定评估集隔离

- 背景：固定 RAG 评估集用于比较系统检索和回答质量，不代表用户实际面试题来源；用户明确需要理解简历、求职方向和岗位描述后开展个性化面试。
- 选项：继续扩张固定题集、直接让模型生成整套题目，或先生成可确认的证据化面试准备画像。
- 决定：新增 `POST /api/interviews/preparations`，通过一次结构化模型调用生成候选人摘要、简历证据、岗位要求和面试关注领域。输入只包含目标岗位、简历和可选 JD，不读取 `FixedRagEvaluationDataset`；画像阶段不生成题目、评分或录用判断。
- 理由：先形成可检查的中间画像，能够在出题前暴露简历解析和岗位理解偏差；固定评估集继续保持稳定，避免系统质量基线与用户面试内容相互污染。一次模型调用也比同时解析、出题和评分更容易控制费用与验证边界。
- 影响：接口仅在 `storage` profile 暴露，复用现有 ChatClient，Prompt 版本固定为 `interview-preparation-v1`。第一版不持久化简历、JD 或画像，不调用 Qdrant；真实模型质量尚未验证。阶段 5 暂不引入没有评估收益证据的混合检索或 rerank，阶段 6 从面试准备画像开始。
- 回看条件：画像需要跨会话确认、修改或审计时增加持久化；生成正式面试题时必须绑定考察目标和知识来源，不得退回无约束模型自由出题。

## ADR-028：首轮面试题分离画像依据与知识依据

- 背景：面试准备画像已经能够说明候选人经历和岗位关注点，但直接让模型自由出题无法追溯题目选择原因，也不能说明知识库是否有资料支撑后续答案和评分。
- 选项：按目标岗位自由出题、只根据画像生成题目，或先根据画像生成结构化题目再逐题绑定真实知识来源。
- 决定：`POST /api/interviews/questions` 接收目标岗位和已确认画像，以 `interview-question-v1` 恰好生成 3 道题；每题保存考察目标、画像依据类型和知识检索查询，再以 `topK=3`、阈值 `0.60` 调用现有相似度检索并返回实际 chunk 来源。
- 理由：画像依据回答“为什么问这个候选人”，知识依据回答“知识库是否能支撑后续训练”，两者不能混为一种证据。复用现有检索服务可保留真实来源，又无需提前建设题库、会话状态机或评分链路。
- 影响：模型依据类型必须属于画像关注领域已经出现的来源类型；没有可靠知识命中时仍可保留由画像支撑的问题，但 `knowledgeGrounded=false` 且来源为空。当前题目、画像和来源不持久化，不生成参考答案、评分或动态追问。
- 回看条件：建立面试会话后，根据真实题目质量和回答评分需求调整题数、检索参数或知识来源选择；任何调整需要保留画像依据与知识依据的独立表达。

## ADR-029：文本面试会话使用单行 JSON 聚合与乐观锁

- 背景：画像和首轮题目已经可生成，但请求结束后无法恢复状态；逐题回答需要持久化已确认输入、当前题号和历史回答，同时避免并发重复提交覆盖数据。
- 选项：只使用进程内 Map、把会话/题目/回答拆成三张表，或在一张会话表保存 JSON 快照并使用独立状态列。
- 决定：新增 `t_interview_session`，以 UUID 为主键，画像、3 道题和回答保存为 JSON 文本快照；当前题号、状态、版本和时间使用独立列。回答更新必须匹配旧版本与 `IN_PROGRESS` 状态。
- 理由：单行聚合足以支持当前固定 3 题的创建、恢复和顺序回答，减少尚无查询需求的表与事务复杂度；独立状态列和乐观锁又能保证并发提交不会静默覆盖。
- 影响：会话只允许按顺序回答，第三题后自动完成；影响行数为 0 时返回冲突。当前不能按单题字段做复杂 SQL 查询，也不支持改答案、跳题、用户归属、评分或追问；迁移脚本需在真实 `storage` 使用前显式执行。
- 回看条件：出现可配置题数、逐题独立评分查询、题目版本变更、用户历史列表或单题重答需求时，再拆分会话、题目与回答表。

## ADR-030：动态面试保持单行聚合并使用双重请求校验

- 背景：用户明确指出固定三题不符合真实面试，并要求当前功能一次形成完整闭环。现有 ADR-028 的固定三题和 ADR-029 的第三题完成语义需要扩展，但当前仍没有单题 SQL 查询、用户历史或改答案需求。
- 选项：立即拆分会话、题目、回答和评价多张表，或继续使用单行 JSON 聚合并让题目队列可动态追加。
- 决定：首轮题数允许 3 到 8 道，整场上限允许到 12 道；题目、带评价回答和最终报告继续保存为单行 JSON 快照。每次回答必须携带 `questionIndex` 与 `expectedVersion`，先在模型调用前校验，再由更新 SQL 使用旧版本和进行中状态完成乐观锁校验。
- 评分与追问：模型输出技术、完整性、表达、优点、遗漏、建议和可选追问；综合分及最终平均分由服务端确定性计算。知识可靠状态只来自题目实际来源；追问必须再次检索真实来源，重复题目或达到整场上限时不追加。
- 理由：双重校验能够避免延迟重试在模型调用后被误当作下一题，也避免并发提交覆盖已保存回答；动态 JSON 快照足以支持当前队列和报告，不需要提前引入多表事务、题目状态机或额外基础设施。
- 影响：`004_interview_session.sql` 与 `005_expand_interview_session.sql` 已按顺序执行到服务器独立数据库，执行后会话表为 0 行，因此没有需要兼容的真实旧会话数据。前端本地只保存会话 UUID，不保存简历或回答全文。
- 回看条件：出现用户历史列表、单题重答、按薄弱项查询、评价审计或旧会话迁移需求时，再将题目、回答与评价拆表，并设计向后兼容迁移。

## ADR-031：资料库文件与面试输入文件使用独立业务入口

- 背景：资料库页面能够上传 Markdown 并执行版本登记、切分和向量化；文本面试后端接收简历文本和可选 JD。前端为了先打通面试闭环直接暴露文本框，旧资料库文案又曾把简历、JD 和面试资料放在同一上传语境中，使用户误以为两类文件共用一个入口和存储方式。
- 选项：继续让所有文件先进入资料库、让资料库导入后自动触发面试，或分离资料库与模拟面试入口但复用底层文件读取能力。
- 决定：资料库只负责需要长期检索的 Java 学习资料、项目技术说明和知识文档；简历与可选 JD 在 `/interview` 独立上传，提取正文后进入画像与出题链路，默认不执行知识库版本登记、Chunk 向量化或长期原文保存。文本粘贴保留为备用方式，不作为主交互。
- 文件范围：先接通现有能力最清楚的 Markdown/TXT；PDF/DOCX 必须在具备可靠正文提取、格式校验和中文错误提示后再开放，不实现只接受文件但无法保证解析质量的假上传。
- 理由：知识资料和个人求职材料的用途、隐私、生命周期与更新语义不同。分离入口能够让用户明确“资料用于长期知识依据”还是“文件只用于本场个性化面试”，同时仍允许复用文件大小、类型校验和文本读取组件。
- 影响：资料库页面文案与面试文件入口已完成分离；当前 `resumeText` 与 `jobDescription` API 继续作为解析后的内部文本契约，无需为了上传改变画像服务。若以后需要保存长期简历档案，应建立独立档案模型和用户确认，不复用知识库表。
- 回看条件：出现跨会话简历版本管理、多人账号、简历修改审计或用户明确选择“加入个人知识库”的需求时，单独设计求职档案持久化与授权边界。

## ADR-032：GraphRAG 只在多跳评估证明收益后引入

- 背景：当前普通向量 RAG 已完成文档切分、来源引用、召回日志和固定评估基线，6 道现有检索题均首位命中。GraphRAG 可以表达候选人、项目、技能、岗位要求、题目、回答、薄弱项、资料和复习任务之间的关系，但也会增加实体抽取、消歧、关系更新、图查询和一致性治理成本。
- 选项：立即引入 Neo4j 建设知识图谱、完全排除图增强检索，或把 GraphRAG 作为由评估数据触发的长期优化候选。
- 决定：当前不引入 GraphRAG 或图数据库。先扩充跨文档、多实体和多跳关系评估题，确认普通 RAG 存在可重复的召回或解释缺口；随后优先用轻量关系模型或 MySQL 节点/边表验证局部图检索，只有相对普通 RAG 获得明确收益后才评估 Neo4j。
- 候选图谱：第一批关系只围绕真实学习闭环，例如“候选人—项目—技能—岗位要求”和“面试题—回答—薄弱项—知识资料—复习任务”，不建设大而全的通用知识图谱。
- 验收：至少比较多跳来源命中率、回答依据路径、更新一致性、构建成本与查询延迟；没有稳定收益、没有足够关系数据或普通 RAG 已能满足问题时，维持现有向量检索。
- 影响：近期仍按“简历文件入口 → 真实文本面试验证 → 错题与复习计划”推进。GraphRAG 不阻塞当前功能，也不提前增加 Neo4j、中间件或图谱抽取任务。
- 回看条件：错题、复习任务和跨会话记录形成足够真实关系数据，或多跳评估持续暴露普通向量检索无法解决的问题时。

## ADR-033：Markdown/TXT 面试文件在浏览器本地提取正文

- 背景：面试后端已经稳定接收 `resumeText` 和可选 `jobDescription`，当前缺口只是文件主入口。新增后端 multipart 会扩大临时文件、清理和隐私治理范围，但 Markdown/TXT 可以由浏览器可靠读取。
- 选项：新增后端文件解析接口、在面试表单内分别实现两套读取逻辑，或封装一个浏览器本地文本文件字段并复用既有字符串 API。
- 决定：新增 `InterviewTextFileField`，只接受 `.md`、`.markdown` 和 `.txt`，使用 `File.text()` 在浏览器本地读取，校验空正文和现有字符上限后更新可编辑文本。读取失败或类型不支持时保留原文本并显示中文错误。
- 隐私边界：文件和正文不进入知识库 multipart 导入、不执行版本登记或向量化，也不写入 localStorage；只有用户开始面试时，文本才按既有 JSON 请求发送给后端。
- 理由：该方案复用已经验证的画像与会话契约，改动最小，且让个人求职材料与长期知识资料保持不同生命周期。PDF/DOCX 不适合用同一纯文本读取方式，继续等待可靠解析能力。
- 回看条件：需要 PDF/DOCX、服务端病毒扫描、跨设备文件档案或可审计原文件存储时，再设计独立上传与解析服务，不扩展当前文本组件承担这些职责。

## ADR-034：可选追问字段异常不得使主评价整体失败

- 背景：真实 `qwen3.7-plus` 评价返回了有效分数、优缺点、追问题目和追问目标，但在 `followUpNeeded=true` 时遗漏 `followUpKnowledgeQuery`，结构化草稿构造直接抛出异常，导致整个回答接口返回 400 且有效主评价无法保存。
- 选项：任何追问字段缺失都拒绝整次评价、完全丢弃不完整追问，或对缺失的独立查询使用追问题目兜底。
- 决定：追问题目和追问目标仍必须非空；只有独立检索查询为空时，使用追问题目本身作为查询。Prompt 同时明确需要追问时三个字段必须全部非空，运行时兜底负责模型偶发不遵循格式的情况。
- 理由：追问题目本身已经表达检索意图，可安全用于同一 `topK=3`、阈值 `0.60` 的检索；即使没有可靠命中也会返回空来源和 `knowledgeGrounded=false`。可选增强字段不应使已经有效的主评分、优缺点和改进建议全部丢失。
- 影响：观察到的真实失败可以用原会话版本重试并成功保存；未放宽分数范围、追问题目、追问目标、来源可靠性或乐观锁校验。
- 回看条件：如果后续模型经常遗漏多个追问字段，改为显式丢弃不完整追问并记录模型输出质量指标，而不是继续增加字段级猜测。

## ADR-035：文本层 PDF 在浏览器使用 PDF.js 提取

- 背景：用户实际简历以 PDF 为主，Markdown/TXT 入口不能覆盖主要使用场景；个人简历仍要求只用于本场面试，不默认进入知识库或长期文件存储。
- 选项：浏览器 PDF.js、本项目后端 PDFBox multipart，或立即引入 OCR 服务。
- 决定：使用固定版本 `pdfjs-dist 5.4.624` 在浏览器本地解析文本层 PDF，解析模块按需加载，worker 由 Vite 输出为独立资源。继续复用 `resumeText` 与 `jobDescription`，不新增后端文件接口。
- 校验：PDF 最大 10 MiB，按页提取并保留页面边界；没有文本层、加密、损坏和正文超限均返回明确中文错误，解析失败不回退为读取二进制字符串。
- 理由：文本型简历无需上传即可可靠提取，保持了个人材料的隐私和现有 API 边界。PDFBox 会增加后端临时文件治理，OCR 会增加模型、成本、语言和质量评估范围，当前都没有必要。
- 影响：用户可直接选择常见文本型 PDF 简历或 JD；扫描件继续明确不支持 OCR，不能宣称所有 PDF 都可解析。PDF.js 为 Apache-2.0 许可证，Node 版本要求不高于项目现有 Vite 基线。
- 回看条件：真实扫描件占比足够高时，先建立 OCR 样本与准确率验收，再选择浏览器 OCR、后端 OCRmyPDF/Tesseract 或外部服务；DOCX 另行评估，不并入 PDF 解析器。

## ADR-036：面试 PDF 改由后端通用正文提取工具处理

- 背景：用户实际使用中更关注复杂简历版式的正文顺序，浏览器 PDF.js 的文本项拼接缺少集中治理和服务端回归边界；OCR 已明确暂缓。
- 选项：继续增强浏览器 PDF.js、后端 PDFBox 临时解析，或同时接入 OCR。
- 决定：以 `InterviewDocumentTextExtractor` 作为面试输入的通用正文提取边界，当前仅实现 `PdfInterviewDocumentTextExtractor`。`POST /api/interviews/documents/extract` 接收不超过 10 MiB 的 PDF，由 PDFBox `3.0.5` 启用位置排序后返回正文和页数；Markdown/TXT 保持浏览器本地读取。
- 隐私与存储：业务代码不保存原文件、不写 MySQL、知识库、向量库或 localStorage，解析完成即关闭 `PDDocument`。Servlet multipart 在请求生命周期内可能使用框架临时缓冲，不构成业务文件档案。
- 理由：后端解析让库版本、错误边界、位置排序策略和真实样本回归集中在 Java 工程中，且不改变既有 `resumeText`、`jobDescription` 和面试会话契约。只增加一个当前 PDF 实现，不提前建设格式插件、DOCX 或 OCR。
- 影响：加密、损坏、非 PDF、超限和无文本层均返回中文 400；扫描件仍明确提示 OCR 未支持。位置排序不是版面语义理解，复杂双栏、表格、图形化简历不能承诺完全准确。
- 回看条件：积累足够的真实脱敏样本后比较位置排序、列检测或专用版面解析的顺序准确率；扫描件需求稳定后再单独建立 OCR 准确率和成本验收。ADR-035 保留为历史决策，本 ADR 替代其浏览器 PDF.js 实现。

## ADR-037：复习任务按逐题遗漏确定性生成

- 背景：文本面试已经保存逐题评价、题目知识来源和最终薄弱项，但完成后没有可独立查询、可继续推进的学习任务。第一步需要把已有证据沉淀下来，又不应再次调用模型或提前建设完整复习调度系统。
- 选项：只在会话响应中即时展示薄弱项、为错题/知识点/计划立即拆多张表，或先按原题生成独立复习任务单表。
- 决定：只允许已完成会话显式生成任务；每道评价 `gaps` 非空的回答生成一条 `PENDING` 任务，无遗漏回答跳过。任务保存原题、考察目标、遗漏项、改进建议和实际知识来源元数据，不复制 chunk 正文，不使用总分阈值或二次模型判断。
- 幂等：任务 UUID 由“会话 ID + 题号”稳定生成，`t_interview_review_task` 再以同一组合建立唯一键；插入使用 `ON DUPLICATE KEY`，重复请求和部分失败后的重试不会生成重复任务。
- 理由：逐题遗漏是当前已经持久化且最直接的复习证据，来源元数据可以追溯到真实知识资料；独立单表支持后续状态与日期查询，又避免现在拆分错题、知识点、计划和执行记录多套模型。
- 影响：第一版只提供按会话生成和查询。`006_interview_review_task.sql` 已在 MySQL 5.7.36 执行，并以受控完成会话验证重复生成不增行和应用重启后查询。前端在最后一题完成后调用 `POST`，恢复完成会话时只调用 `GET`，并把任务错误与最终报告隔离；暂不支持任务完成、重开、复习日期、跨会话合并、提醒或 Tool Calling。
- 回看条件：真实使用需要按用户/状态/日期查询、同知识点跨会话合并或间隔复习时，再增加任务状态流转、计划日期和用户归属；在此之前不引入调度器或 Agent Runtime。

## ADR-038：复习任务单向完成并保留首次时间

- 背景：复习任务已经可以生成、恢复和展示，但用户无法记录某条遗漏是否已经复习；第一步需要形成可执行闭环，同时避免提前引入重开历史、提醒和完整日程模型。
- 选项：只在前端保存勾选状态、建立可反复切换的完成/重开状态机，或由后端持久化单向完成状态与首次完成时间。
- 决定：新增任务级 PATCH 接口，按会话 ID 与任务 ID 联合定位任务，只允许 `PENDING -> COMPLETED`。MySQL 使用可空 `completed_at`；更新通过 `COALESCE` 保留首次完成时间，因此网络重试和重复点击保持幂等。
- 理由：服务端状态可以跨刷新和应用重启恢复，联合定位避免用其他会话路径操作任务；保留首次时间比每次覆盖更适合作为最小审计事实。当前没有重开和执行历史需求，不引入版本列或单独事件表。
- 影响：`007_complete_interview_review_task.sql` 已在 MySQL 5.7.36 执行，真实临时行验证重复完成保留首次时间并在结束后清理。前端只替换完成的单条任务，操作错误不隐藏清单。计划复习日期、重开、提醒、跨会话查询仍未实现。
- 回看条件：需要误操作撤销、重复复习次数、间隔学习统计或并发状态流转时，再增加重开语义、版本控制或独立执行记录，而不是覆盖 `completed_at`。

## ADR-039：阶段 7 先建立二次作答事实再扩展日程与看板

- 背景：复习任务已经能生成、展示和标记完成，原路线准备继续增加计划日期和跨会话汇总；用户同时要求成熟参考项目主动扩展功能设计和工程质量，而不只是验证预选方案。
- 参考结论：`aural-oss` 以独立 session/attempt 保存同题多次回答，并在此基础上计算平均分、最好分和弱项；`hiring-agent` 用岗位清单、结构化 Schema、证据与模型参数约束评分，同时公开承认模型评分方差。当前项目没有二次作答，也没有评价 Prompt、rubric、模型和知识来源版本快照。
- 选项：先做计划日期和提醒、先做用户/历史平台，或先让复习任务产生可比较的二次作答 attempt。
- 决定：下一闭环优先新增复习任务 attempt；原正式面试答案保持不可变，每次 attempt 独立保存序号、回答、评价、知识来源、Prompt/rubric/model 版本和时间，并返回相对原回答及上次回答的变化。评分质量基线和评价日志随后完成，再基于真实 attempt 构建历史/趋势，最后增加计划日期。
- 理由：日期和看板只能组织已有事实，不能替代练习行为；先有可比较 attempt，才能判断复习是否有效，也能为评分方差、Prompt 变更和后续 Tool Calling 提供可审计输入。
- 影响：计划复习日期被调整到 attempt、评分质量和单会话趋势之后，但没有取消。跨会话查询在没有用户身份和数据归属前不开放。第一版不实现重写正式答案、答案库、语音、提醒调度器或通用 Prompt 管理平台。
- 回看条件：如果真实用户只需要待办管理而不使用二次作答，或 attempt 数据证明日期驱动明显更重要，可以提前计划日期；否则继续按“attempt -> 质量 -> 趋势 -> 日期 -> Tool Calling”推进。

## ADR-040：复习 attempt 独立保存评价快照并保持正式答案不可变

- 背景：复习任务已经可以标记完成，但只保存任务事实无法验证复习回答是否改善；直接覆盖正式会话答案又会破坏报告和历史可解释性。
- 选项：更新原 `InterviewSessionAnswer`、只在浏览器暂存复习回答，或新增按任务和序号独立持久化的 attempt。
- 决定：新增 `t_interview_review_attempt`，每次复习回答使用 1-based `attempt_number` 独立保存回答、评价、知识来源元数据、Prompt/rubric/model 版本、原分数、上次分数及分差。服务读取正式会话和历史 attempt 后再调用复习评价器，复习评价关闭动态追问；序号由客户端预期值校验并由数据库唯一键兜底。
- 理由：独立事实既保留正式面试报告的不可变语义，又能支撑同题多次比较、评价版本审计和后续训练趋势；先保存真实练习行为，再决定质量日志和日程聚合，符合阶段 7 的路线。
- 影响：新增 `GET/POST .../review-tasks/{taskId}/attempts`，`/interview` 任务卡片可提交回答并查看历史；任务完成状态不因 attempt 自动重开。`008_interview_review_attempt.sql` 使用 MySQL 5.7 兼容结构，不复制知识 chunk 正文。
- 回看条件：出现跨会话用户归属、评分方差基线或需要按知识点聚合时，再增加质量日志、趋势查询和计划日期；不在本 ADR 中引入 Tool Calling、语音或认证。

## ADR-041：固定评分样本与评价日志不保存输入正文

- 背景：复习 attempt 已保存每次评价快照，但不同回答和不同版本混在真实会话中，无法重复比较同一输入的模型波动；评价失败也没有独立的耗时、状态和失败类型事实。
- 参考结论：`hiring-agent` 使用明确 rubric、结构化 evidence 和类别上限，但仍承认模型评分方差；`aural-oss` 将反馈模型耗时与持久化故障分开诊断。当前项目应先获得可重复样本和最小运行日志，再绘制训练趋势。
- 选项：直接从真实简历与回答建立评估集、建设完整 Prompt/模型观测平台，或以内置脱敏样本和轻量 MySQL 日志建立第一版基线。
- 决定：内置空回答、无关回答、部分回答、完整回答和无知识来源回答五类合成样本；`POST /api/interviews/evaluations/answers` 通过 `BASELINE` 模式执行，不生成动态追问。空回答预期在服务端拒绝，其余样本按宽松分数区间和知识依据状态报告结果，区间外只标记未通过，不伪装成模型或接口异常。
- 日志边界：使用 `ObservableInterviewAnswerEvaluator` 包裹正式、复习和基线三种模式，记录 Prompt/rubric/model、四项分数、知识依据、总耗时、状态和失败类型。`t_interview_answer_evaluation_log` 不保存会话 ID、简历、题目、回答、知识正文或来源；日志写入失败只告警，不改变评分结果与异常语义。
- 理由：固定合成输入可在不暴露个人材料的前提下重复运行；调用级分数与版本事实足以先量化方差和失败，不需要提前引入链路追踪、token 统计、用户查询或 Prompt 管理平台。
- 影响：一次完整基线最多产生 4 次 Chat 调用，并为 5 个样本记录评价尝试。`009` 已在独立数据库 `java_interview_rag` 的 MySQL 5.7.36 上执行并验证结构；真实模型重复基线尚未运行，当前代码与迁移验证仍不能证明评分稳定性。
- 回看条件：重复基线证明需要区分 Prompt 构建、首 token、解析和持久化阶段时再细化耗时；需要按会话解释单次评分时，先确认隐私和数据归属，再决定是否增加不可逆散列或关联标识。

## ADR-042：面试训练页采用任务优先界面并隐藏实现术语

- 背景：`/interview` 已具备文件输入、动态题目、逐题评分、最终报告和复习 attempt，但早期页面仍使用营销 Hero、英文技术标签、编号区段和大段实现说明。用户进入页面后不能立即开始任务，内部术语也降低了面向求职者的可信度。
- 参考结论：Linear、LeetCode、Teal Job Tracker 和 Readwise Reader 的公开界面共同强调稳定应用框架、单一主任务、辅助信息侧置和渐进披露。该结论用于发现结构差距，不用于复制其页面或品牌资产。
- 选项：只替换颜色和字体、保留 Hero 但压缩文案，或在现有组件与状态边界内重组为任务优先界面。
- 决定：`/interview` 使用 Split Studio 结构。未开始时首屏直接展示材料与本场设置；进行中使用会话状态条和题目/反馈双栏；完成后按报告、复习题目的顺序展示。知识来源、备用文本和评价版本使用原生 `details`，营销页脚不进入任务界面。
- 文案边界：主路径只描述用户动作和结果，不出现 RAG、chunk、Prompt/rubric/model、英文 eyebrow、装饰编号和解释实现的句子。技术字段继续保留在 API 与持久化模型中，必要的评价版本信息只在折叠区展示。
- 工程边界：保留 Vue 3 Composition API、typed props/emits、`useInterviewSession`、路由和所有后端载荷；只增加 `InterviewSessionBar` 和维护中的 `@lucide/vue`，不引入 UI 框架、Pinia、动画库或新的接口。
- 影响：资料库页仍可保留自己的 Workbench 结构，面试页形成更紧凑的产品工作区；两页共享设计令牌和导航，但不强求相同的页面结构。后续新增面试功能应优先放入现有任务流或渐进展开层，不恢复营销式说明区。
- 回看条件：出现多种训练模式、跨会话历史或账号级工作区后，重新评估导航与信息架构；在此之前不增加侧边栏、仪表盘或大型招聘管理界面。

## ADR-043：评价日志按模式与版本分组汇总

- 背景：`009` 已提供正式、复习和基线评价日志，但只有写入没有查询；继续执行付费固定基线前，需要先确认日志能按评价版本核对状态、分数、知识依据、耗时和失败类型。
- 参考结论：`hiring-agent` 的 rubric 和模型方差说明要求评分统计带版本上下文，`aural-oss` 的反馈诊断说明评价状态、耗时与持久化问题应可独立检查。两项目 main 提交在本轮只读复核中均未变化。
- 选项：直接查询并返回原始日志、由 SQL 构建固定聚合视图，或在有上限的最近日志上由 Java 按版本确定性汇总。
- 决定：新增 `GET /api/interviews/evaluations/logs`，按 `INTERVIEW`、`REVIEW` 或 `BASELINE` 查询最近 1 到 100 条记录，默认 `BASELINE` 和 20 条；Java 按 Prompt/rubric/model 分组，返回成功/失败、知识依据成功数、总分范围与平均值、耗时和失败类型，同时保留原始无正文日志。
- 理由：复用现有表和索引即可完成零费用查询闭环，版本分组避免把模型或规则变更前后的结果直接混算；Java 汇总容易用单元测试固定口径，也不提前增加视图、监控系统或前端看板。
- 限制：本 ADR 落地时日志没有固定样本 ID 和运行批次 ID，多个不同样本的分数不能解释为同一样本方差；该结构限制已由 ADR-044 与 `010` 迁移解决，但真实重复评分仍未执行，本接口当前仍不计算或宣称方差。
- 回看条件：日志量超过最近 100 条查询的人工诊断范围时，再考虑时间窗口、数据库聚合或离线报表；出现跨用户查询前必须先明确身份与数据归属。

## ADR-044：固定评分基线使用运行 UUID 和稳定样本 ID

- 背景：评价日志已经能够按模式和版本查询，但五类固定样本共用 `BASELINE` 模式且没有运行批次；直接汇总会把不同输入混合，无法比较同一样本的重复评分。
- 参考结论：`hiring-agent` 对同一输入的模型方差分析要求输入和评价版本可稳定关联，`aural-oss` 将 session 与 attempt 分离后再聚合历史。两项目 main 提交在本轮只读复核中均未变化。
- 选项：把样本正文散列写入日志、根据日志插入顺序推断五条一组，或显式生成非敏感运行 UUID 并保存已有稳定样本 ID。
- 决定：每次固定基线请求生成一个 UUID `baselineRunId`，五个样本使用数据集中已有 `caseId`；两个标识成对进入 `BASELINE` 日志并随批量响应返回。正式和复习模式禁止携带基线标识，迁移列保持可空以兼容既有模式和历史数据。
- 理由：显式标识不依赖日志顺序或输入正文，既能把一次运行的五条评价关联起来，也能跨运行按同一样本比较；复用稳定样本 ID 比保存正文散列更直接，不引入不可逆个人数据关联。
- 影响：新增 `010_identify_interview_answer_evaluation_baseline.sql` 和组合查询索引；脚本已在 MySQL 5.7.36 的独立数据库执行，表内仍为 0 行。真实模型重复基线尚未执行，当前只完成可比较结构，不能声称已有方差结果。
- 回看条件：需要并发基线执行状态、部分重试或历史报告时，再评估独立运行表；当前一次同步请求和调用级日志不需要新增表。

## ADR-045：按稳定样本和评价版本统计跨运行评分

- 背景：基线日志已有运行 UUID 和稳定样本 ID，但查询仍只按版本聚合全部输入；用户要求进一步整体实现后，需要直接支持运行/样本定位和同一样本跨运行统计，同时不能在没有真实数据时伪造稳定性。
- 选项：在 MySQL 建聚合视图或新统计表、离线导出后计算，或扩展现有有上限查询并由 Java 确定性聚合。
- 决定：现有查询增加可选 `baselineRunId` 与 `baselineCaseId` 等值筛选，且只允许 `BASELINE` 使用。Java 按 `baselineCaseId + promptVersion + rubricVersion + modelName` 分组；同一运行有多条日志时按当前倒序结果保留最新一条，原始日志数和去重运行数分别返回。
- 统计口径：样本汇总返回成功/失败运行、知识依据、总分最小/最大/平均/范围、平均/最大耗时和失败类型。`overallScorePopulationVariance` 是去重后成功总分的总体方差，四舍五入到两位小数；少于两次成功时返回 `null`。迁移前无标识日志只计入 `unidentifiedBaselineCount`。
- 理由：评价版本进入分组可以避免 Prompt、rubric 或模型切换前后混算；按运行去重避免同一次重试放大样本量；总体方差描述当前已观察结果，不冒充对模型总体分布的无偏估计。复用现有表和最近 100 条边界，不增加统计基础设施。
- 影响：接口仍返回原始无正文日志和原版本汇总，同时新增样本汇总；真实 `storage` 空表与联合筛选已验证，不调用模型。当前没有真实成功评分，因此方差字段尚无业务数据。
- 回看条件：出现超过 100 条的长期基线历史、需要完整时间窗口或并发运行状态时，再增加数据库聚合或独立运行表；当前不为零数据提前建设。

## ADR-046：复习历史以单会话持久化 attempt 为统计边界

- 背景：复习任务已经支持多次独立 attempt，但前端只逐条展示回答和分差，缺少本场已练题数以及每题首次、最近、最好分数；直接在浏览器计算会让刷新、并发提交和后续客户端产生不同口径。
- 参考结论：`aural-oss` 在 session/attempt 事实之上汇总练习历史，`hiring-agent` 要求评分比较保留评价版本语境。当前仓库已有持久化 attempt，但没有用户身份或跨会话数据归属。
- 选项：由前端临时聚合现有列表、增加数据库统计表，或在后端按单会话读取任务与 attempt 后确定性聚合。
- 决定：新增单会话历史接口，返回任务总数、已练任务数、总 attempt 数和最近分数高于正式回答的任务数；每题返回完整时间线、正式/首次/最近/最好分数、最近相对正式回答的分差和最近评价遗漏。未作答任务分数字段为空，并保留原任务遗漏。
- 理由：现有单场任务数量有限，读取既有索引数据即可得到一致口径，不需要新增迁移、缓存或统计表。服务端聚合保证刷新和不同客户端读取同一事实，前端只负责展示。
- 限制：遗漏是自由文本，本轮不以字符串或模型再次判断已解决条目；分数比较仍受 Prompt/rubric/model 版本影响，接口不宣称因果进步或模型稳定性；没有用户归属前不跨会话汇总。
- 影响：`/interview` 恢复和提交 attempt 后都读取会话历史，显示本场概览及每题评分摘要；旧的单任务 attempt API 保留。计划复习日期仍是下一项零费用候选，真实固定评分基线仍需费用授权。
- 回看条件：单场任务和 attempt 数量增长到影响响应，或明确用户身份后需要跨会话趋势时，再增加批量查询、时间窗口或数据库聚合；在此之前不建设历史统计基础设施。

## ADR-047：计划日期附着复习任务并保持单会话查询

- 背景：复习任务已经支持完成、独立 attempt 和单会话历史，但用户仍只能看到静态清单，不能安排下一次复习；当前没有用户身份、全局数据归属或真实提醒需求。
- 参考结论：`aural-oss` 继续以 session/attempt 事实支撑练习历史，没有要求为日期引入调度器；`hiring-agent` 的真实评分方差仍依赖付费重复运行，与任务日期属于不同问题。
- 选项：建立用户级日历和提醒服务、只在浏览器保存日期，或把可选日期直接保存到现有复习任务并在会话内查询。
- 决定：`t_interview_review_task` 增加可空 `planned_review_date DATE`；任务级 PATCH 使用具体日期设置、使用 `null` 清除。现有会话级 GET 增加可选状态、开始日期和结束日期筛选，日期反向返回 400；所有 SQL 首先使用 `session_id` 限定数据范围。
- 理由：日期属于任务当前安排而不是新的练习事实，直接附着现有任务最简单；MySQL `DATE` 避免把没有时刻含义的安排绑定到时区。服务端筛选和前端重新读取保证刷新及不同客户端口径一致，不需要新表、调度器或缓存。
- 影响：新增 `011_schedule_interview_review_task.sql` 和 `(session_id, status, planned_review_date)` 索引，已在独立 MySQL 5.7.36 数据库执行并确认任务表仍为 0 行；`/interview` 增加状态/日期筛选与任务行内日期控件。完成任务保留原计划日期作为历史信息。
- 限制：当前只查询浏览器已恢复的单个面试会话，不提供用户级全局待办、跨会话趋势、逾期提醒、自动重排或间隔重复算法；日期不会自动触发模型或后台任务。
- 回看条件：明确用户身份和数据归属后再评估跨会话待办；真实用户要求提醒后再选择调度机制；在此之前可以把现有查询和日期更新作为受控 Tool Calling 的候选工具。

## ADR-048：产品界面不承载开发进度并使用真实状态形成视觉反馈

- 背景：现有工作台为避免营销化和 AI 模板感，使用了克制的中性界面；实际使用反馈表明，重复白色卡片、等权指标和深色静态设置板又走向了死板。资料库额外展示“当前能力边界”和“下一步开发”，用户无法判断它是功能还是项目进展。
- 选项：继续保持所有区域同等克制、增加装饰性渐变和动画，或保留现有设计令牌并通过布局主次、真实准备度和任务状态增强视觉反馈，同时移除工程进展说明。
- 决定：共享品牌使用单行 `Java 面试台`；面试准备页以开放材料区为主、石墨设置台为辅，准备度只由目标岗位和简历真实输入计算；复习历史以连续进度替代三块等权指标。资料库删除能力边界、下一步开发和当前阶段页脚，工程进展只保留在文档。
- 理由：产品界面的设计应帮助用户理解当前任务和状态，不应因为排斥模板化而排斥层级、颜色和反馈，也不应把开发路线暴露为用户功能。复用现有珊瑚、石墨和语义状态色可以增强辨识度而不扩张设计系统。
- 影响：本轮只修改 Vue 结构和局部样式，不改变 API、路由、状态管理或数据生命周期。文件读取成功、必要材料齐备和复习进度都获得更明确反馈；装饰性大动画、渐变、玻璃效果和新依赖仍未引入。
- 回看条件：后续两个工作台继续出现视觉不一致时，可使用 `$impeccable init` 固化 `PRODUCT.md` 与 `DESIGN.md`；在此之前优先依据真实用户反馈迭代现有令牌和组件。

## ADR-049：进行中面试使用单一答题工具与教练反馈侧栏

- 背景：面试准备页完成视觉层级优化后，进行中状态仍由进度白卡、答题白卡和反馈灰卡依次组成。三个同等矩形边界削弱了当前问题的优先级，评分也只是数字排列，无法快速比较技术、完整性和表达差异。
- 选项：继续仅调整间距和边框、为每个分数增加独立彩色卡片，或将题目与反馈收敛为一个双栏工具面板并通过浅色主画布、石墨反馈侧栏和原生进度条建立层级。
- 决定：`InterviewView` 只提供单一面板边界；`InterviewQuestionPanel` 继续负责题目、来源和回答提交；`InterviewFeedbackPanel` 继续纯展示最近评价，但使用石墨表面、数值与原生 `progress` 同时表达三项分数。会话进度移除独立卡片外观，反馈的优势、遗漏和建议使用语义图标及分隔线，不再使用彩色侧边竖条。
- 理由：颜色和对比直接对应当前任务与真实评分，比增加更多装饰卡片更容易扫描；原生进度条保留无障碍语义，现有珊瑚、绿色、蓝色和石墨令牌已经足够，不需要扩张设计系统或增加图表依赖。
- 影响：所有 props、emits、`useInterviewSession`、API、路由和后端行为保持不变；桌面保持题目/反馈双栏，窄屏按题目、反馈纵向排列。此次视觉调整不影响完成报告与复习任务结构。
- 回看条件：真实使用表明反馈侧栏过长影响进入下一题时，再考虑在小屏对上一题反馈使用可控折叠；在没有该证据前不默认隐藏评分和关键遗漏。

## ADR-050：Tool Calling 先暴露单会话只读复习任务查询

- 背景：阶段 7 已具备复习任务、计划日期、attempt、评价日志和单会话历史。进入 Tool Calling 时，若直接让模型生成计划、提交回答或修改任务，会放大误操作和数据归属风险；当前也尚未建立工具执行日志。
- 参考结论：`hiring-agent` 的评分和运行事实边界要求 Agent 先消费可追踪事实，不替代未验证的评价；`aural-oss` 的 session/attempt 分离要求练习查询先限定在明确会话内。两项目 main 提交在本轮只读复核中均未变化。
- 选项：先做写入型计划工具、先封装通用 Agent Runtime，或先把现有单会话复习任务查询暴露为只读 Spring AI 工具。
- 决定：新增 `InterviewReviewTools.list_review_tasks`，使用 Spring AI `@Tool` 描述工具；`storage` profile 通过 `MethodToolCallbackProvider` 显式注册。工具参数只包含会话 ID、状态和计划日期范围，内部复用现有 `InterviewReviewTaskService` 的会话存在性、状态和日期范围校验。
- 数据边界：工具返回任务摘要、遗漏、改进建议、状态、计划日期和知识来源元数据，不返回候选人回答正文、复习回答正文或 chunk 正文；当前不自动接入真实 ChatClient 调用，也不新增 MCP 或图工作流。
- 理由：只读查询可以验证 Spring AI 工具描述、参数 schema、Bean 注册和安全返回结构，不产生模型费用或数据库写入风险；它也为后续“安排计划日期”这类受控写入工具提供稳定输入。
- 回看条件：完成工具执行日志、真实 ChatClient 工具调用验证和错误可观测后，再增加写入型工具；明确跨会话数据归属前不暴露全局复习任务工具。

## ADR-051：工具执行日志只记录单会话元数据并隔离存储故障

- 背景：`list_review_tasks` 已成为第一个 Spring AI 工具回调，但此前无法区分模型或调用方是否真正执行工具、返回多少任务、耗时多久以及因何失败。直接增加计划日期写入工具会在缺少审计事实时放大误操作风险。
- 选项：依赖应用文本日志、保存完整工具参数与返回 JSON，或建立不含正文的结构化 MySQL 执行记录并提供单会话查询。
- 决定：每次具有有效会话 ID 的工具调用生成执行 UUID，记录工具名、会话 ID、`SUCCEEDED/FAILED`、成功结果数量、耗时、异常类型和时间。参数 JSON、回答正文、知识 chunk、返回正文和异常消息均不保存；空会话 ID 在形成有效执行上下文前直接拒绝。
- 故障语义：工具业务失败先尽力写入 `FAILED` 后继续抛出原异常；日志写入失败只告警，不得让可用的只读查询失败，也不得替换原业务异常。`GET /api/interviews/sessions/{sessionId}/tool-executions` 只允许查询单个会话最近 1 到 100 条记录，不开放跨会话聚合。
- 理由：这些字段足以验证调用是否发生、成功率、结果规模和耗时，同时避免复制敏感回答与知识正文；执行日志是观察工具的旁路能力，不能反向改变主工具语义。
- 影响：新增 `t_interview_tool_execution_log` 和 `012_interview_tool_execution_log.sql`。领域、MyBatis Store、工具记录、查询接口与针对性测试均已完成；`012` 已在独立 MySQL 5.7.36 数据库执行，确认 9 个字段、预期索引和 0 行业务数据。
- 回看条件：下一步可增加受控计划日期写入工具；真实 ChatClient 自动调用验证需要在可接受模型费用的环境进行。出现跨会话审计需求前，先明确用户身份和数据归属。

## ADR-052：固定评分双运行只作为初始波动基线

- 背景：固定样本、运行/样本标识和跨运行统计已经完成，但此前没有真实模型数据。用户明确允许付费测试后，需要验证宽松评分边界、日志关联和样本级方差是否能在真实调用中成立。
- 决定：对同一五类脱敏样本使用 `qwen3.7-plus` 连续执行两轮，每轮空回答在服务端拒绝，其余四项各调用一次 Chat；共 8 次付费调用。使用 `interview-answer-evaluation-v2`、`interview-answer-rubric-v1` 和稳定 `caseId` 分组，不混入其他模型或评价版本。
- 结果：四个可评分样本两轮均符合预期分数和知识依据状态。无关回答 `17/17`、部分回答 `60/68`、完整回答 `93/93`、无知识来源回答 `55/65`，对应描述性总体方差为 `0/16/0/25`；空回答两轮均以 `IllegalArgumentException` 预期拒绝。
- 解释边界：两次成功观测足以验证跨运行统计实现并发现部分样本存在波动，但样本量不足以估计长期模型稳定性、置信区间或 Prompt 优劣。方差为 0 只表示本次两轮分数相同，不能解释为模型确定性。
- 运行边界：第二轮客户端命令超时后没有重复提交，服务端继续完成并由持久化日志恢复结果。完整汇总固化到 `evaluation/results/2026-08-05-interview-answer-baseline.json`，不保存回答正文。
- 回看条件：只有在比较新 Prompt、rubric、模型版本或诊断具体不稳定样本时才继续增加重复次数；不为追求表面稳定数字无目标地增加付费调用。

## ADR-053：首个写入工具只允许按会话和任务设置明确日期

- 背景：只读复习任务工具、执行日志和真实评分基线已经完成；继续验证 Tool Calling 需要一个真实但可逆的写入动作。直接开放任务完成、提交回答或自由计划生成会扩大误操作和数据归属风险。
- 决定：新增 `schedule_review_task`，强制要求调用方提供明确 `sessionId`、`taskId` 和 `yyyy-MM-dd` 日期；内部只调用现有 `InterviewReviewTaskService.schedule`。重复设置同一日期保持幂等，第一版不允许清空日期，不自动选择任务或计算日期。
- 助手边界：`POST /api/interviews/review-assistant` 只绑定查询和改期两个工具。系统提示要求缺少任一标识或明确日期时不调用写入工具，不得猜测或替换参数；消息最长 2000 字符，不保存对话历史。
- 真实验证：`qwen3.7-plus` 在合成会话上分别正确选择查询和改期工具，两次工具各执行一次并记录成功日志，计划日期真实写入 `2026-08-12`。验证后精确清理全部合成行，不影响其他会话或既有评分日志。
- 已知问题：首次查询回答在正确结果后无依据提到输入可能乱码，说明工具事实正确不等于最终文案完全可靠；系统提示已增加禁止无依据编码判断的约束，但没有为该文案再次付费验证。
- 可观测限制：当前记录工具执行，不记录一次助手请求内部的模型回合、token 用量或 provider 调用次数。因此只能确认两次 HTTP 助手请求和两次工具执行，不能准确声明实际计费调用次数。
- 回看条件：先补助手调用级/模型回合可观测性，再根据真实失败决定重试和对话关联；没有证据前不增加通用 Agent Runtime、图工作流或更多写入工具。

## ADR-054：复习助手先记录请求级累计 token，不推算 provider 回合数

- 背景：工具执行日志只能说明某个工具是否进入和业务结果，不能把一次 HTTP 助手请求与最终响应、token 用量、多个工具执行关联起来；但直接推算 provider 调用次数可能误导计费认知。
- 框架证据：Spring AI 1.0.0 的 `MethodToolCallback` 支持把 `ToolContext` 注入 `@Tool` 方法且不暴露到工具 schema；`OpenAiChatModel` 在工具调用后递归继续模型请求，并通过 `UsageCalculator.getCumulativeUsage` 将前序 `ChatResponse` usage 累加到最终响应。
- 决定：为每个通过参数校验的复习助手请求生成 UUID，写入 `t_interview_assistant_request_log`，并通过 `toolContext` 传给工具执行日志的可空 `assistant_request_id`。请求日志记录模型、状态、工具进入次数、累计 prompt/completion/total token、总耗时、最终响应是否存在和异常类型。
- 隐私边界：请求日志不保存用户消息、助手回答、工具参数 JSON、工具结果正文或异常消息；工具日志继续只保存元数据。日志存储失败只告警，不改变助手最终响应或工具执行语义。
- 语义边界：当前 `promptTokens/completionTokens/totalTokens` 表示 Spring AI 最终 `ChatResponse` 中的累计 usage；provider/model 回合数没有公开业务接口，字段不落库、不推算、不用 HTTP 请求数替代。
- 真实验证：一次 `qwen3.7-plus` 请求中，随机会话不存在导致 `list_review_tasks` 工具日志记录失败，但助手最终回答有效，整体请求为 `SUCCEEDED`；同一 `requestId` 贯穿响应、请求日志和工具日志，累计 token 为 `1971`。验证日志随后精确清理。
- 回看条件：当需要区分多轮模型调用、成本拆分或重试策略时，再引入 Spring AI Observation/Micrometer 或模型网关层观测；在此之前不建设通用 Agent Runtime、图工作流或 MCP。

## ADR-055：改期写入使用单请求精确人工确认

- 背景：`schedule_review_task` 已要求明确会话、任务和日期，但此前只有系统提示约束模型“信息不足不写入”。提示不能作为服务端授权边界，也不能阻止模型产生与用户意图不一致的工具参数。
- 选项：只增加“已确认”布尔值、建立持久化审批表与对话状态，或让当前请求携带完整确认三元组并在工具端精确匹配。
- 决定：`POST /api/interviews/review-assistant` 增加可选 `scheduleConfirmation(sessionId, taskId, plannedReviewDate)`。服务把确认对象放入模型不可见的 `ToolContext`；`schedule_review_task` 必须在调用现有 schedule 服务前确认三项实际参数完全一致。缺少确认或任一不一致都拒绝写入，并按现有执行日志记录失败类型。
- 理由：完整三元组能说明用户确认的具体动作，避免通用布尔值被复用于另一任务或日期；当前改期可逆且没有跨请求审批、多人协作或延迟执行需求，持久化审批状态属于过度设计。
- 安全边界：确认只对单次 HTTP 请求有效，不向模型工具 schema 暴露，不保存用户确认正文，也不替代会话存在性、任务归属和日期格式校验。请求方仍需负责把真实用户确认转换为结构化字段；当前项目没有用户身份，因此不宣称身份级授权。
- 验证：21 个助手、工具和控制器测试覆盖未确认拒绝、不匹配拒绝、精确匹配放行、隐藏上下文和 JSON 请求转发；未进行付费模型调用或数据库写入。
- 回看条件：前端接入助手时复用该结构化确认；只有出现跨请求待审批、多人操作或不可逆工具时才评估确认令牌、审批表或更强权限模型。

## ADR-056：前端确认参数来自结构化选择而不是模型回答

- 背景：复习助手后端只返回自然语言回答和请求 ID。若前端从回答中解析任务、日期或“是否已确认”，模型措辞变化、幻觉或编码差异都可能生成错误写入参数；要求用户手工复制会话和任务 ID 又会破坏正常使用流程。
- 选项：解析助手回答、把内部 ID 暴露给用户手工填写，或由页面使用当前会话和任务事实生成结构化确认。
- 决定：查询模式由页面自动注入当前会话 ID。调整计划模式只允许用户从当前待复习任务中选择任务并使用日期控件输入日期；第一次助手请求不带确认，成功后前端展示同一结构化三元组对应的题号、题目和日期，用户再次点击才发送 `scheduleConfirmation`。
- 理由：当前页面已经拥有可信的会话与任务对象，复用这些事实比解析不稳定文本更简单可靠；显式确认区也让用户能在写入前看到最终操作，不需要模态框、聊天历史或额外审批状态。
- 状态边界：助手异步状态放入独立 composable，`useInterviewSession` 继续单独拥有复习任务服务端状态；确认成功后由 `InterviewView` 触发现有筛选查询重新读取任务，不在组件内猜测或局部修补任务。
- 隐私与文案：主要界面不显示请求 ID、ToolContext、工具名或其他内部实现；回答只按纯文本渲染，不使用 `v-html`。
- 验证：前端构建通过；Playwright 夹具确认第三次请求携带精确三元组，任务日期由后端响应后的重新查询更新。桌面和移动视口无横向溢出，错误状态可见。
- 回看条件：需要服务端生成可机器读取的待确认动作时，应扩展正式响应契约，不能在前端增加自然语言解析器。

## ADR-057：模型重试限定在单次 HTTP 调用层

- 背景：复习助手已经包含查询和经过人工确认的写入工具。若在 Controller、助手服务或完整 ChatClient 调用外层重试，模型已经执行工具但最终回答失败时可能重复进入写工具；同时 Spring AI 1.0.0 的 `OpenAiChatModel` 已自带最多 10 次的 HTTP 重试，额外套层会形成叠加重试和不可控等待。
- 框架证据：本地依赖字节码确认 `OpenAiChatModel` 的 RetryTemplate 直接包裹 `OpenAiApi.chatCompletionEntity`；工具执行发生在取得模型响应之后，工具后的下一轮模型请求拥有独立 HTTP 重试，不会回放上一轮工具。
- 决定：只在 `DashScopeCompatibleChatConfiguration` 配置模型 HTTP 重试，最多 2 次（首次加一次）、固定退避 500ms。连接失败、连接/读取超时、HTTP 429 和 5xx 视为瞬时错误；其他 4xx、SSL 握手失败、业务异常、空响应和工具异常不重试。
- 理由：该边界覆盖当前明确可恢复的网络/上游错误，同时把默认 10 次收敛到可预测等待；不解析异常消息，不在业务服务复制模型请求，不需要为工具额外增加幂等令牌或审批状态。
- 影响：该策略作用于 `storage` profile 共享的 OpenAI 兼容 ChatModel，因此 RAG 回答、面试生成/评分和复习助手使用相同模型 HTTP 边界；Embedding 与 Qdrant 不受影响。
- 验证：3 个配置测试覆盖最多一次重试、连接异常白名单、SSL/非瞬时异常拒绝以及 429/5xx/400 分类；未调用真实模型或数据库。
- 回看条件：只有真实日志显示一次重试仍不足，或需要区分 provider 回合/重试次数时，才评估 Spring AI Observation/Micrometer；不得在工具调用外层增加通用重试。

## ADR-058：复盘助手直接消费单会话持久化历史

- 背景：页面已经展示单会话 attempt 历史，但复习助手只能查询任务清单或改期，无法回答练习次数、分数变化和仍未解决的遗漏；在助手内重新计算会形成两套口径。
- 选项：让模型根据任务清单自由总结、为助手新增专用统计查询，或复用现有 `findAttemptHistory(sessionId)` 并映射为脱敏工具结果。
- 决定：新增只读 `get_review_progress`，以现有单会话历史为唯一事实源。汇总任务、练习、提升和未解决数量，逐题只暴露正式/最近/最好分数、分差、未解决遗漏和最近练习时间；前端以独立“复盘进展”模式发送包含当前会话的明确指令。
- 理由：复用持久化聚合可保证页面和助手口径一致，也避免把回答正文或完整 attempt 交给模型。未练习题的分数保持为空，并通过系统提示禁止描述为退步或猜测分数。
- 边界：该工具只读、单会话、无需人工确认，不新增数据库、跨会话聚合、聊天历史或自动训练计划；改期仍必须经过现有结构化人工确认。
- 验证：22 个后端相关测试、前端类型检查与生产构建通过；浏览器夹具验证精确请求体、桌面/移动布局和控制台。未进行付费真实模型或数据库验证。
- 回看条件：受控真实模型基线确认工具选择与解释质量后，再决定是否把复盘结论与选题再练串成连续操作；没有用户身份前不扩展跨会话趋势。

## ADR-059：复盘后的下一题由持久化事实确定

- 背景：复习助手已经能够说明练习次数、分数变化和未解决遗漏，但用户仍需离开复盘区后自行在任务列表中找到下一题。让模型返回任务 ID 或由前端解析自然语言，会把不稳定文本变成导航依据。
- 选项：扩展助手响应为模型生成的结构化推荐、自动选择并提交下一题，或由页面复用当前任务与单会话历史确定下一动作。
- 决定：只在复盘请求成功后显示确定性入口。候选限制为当前筛选可见且 `unresolvedGaps` 非空的任务；未练习题优先，同组按最近分数或正式回答分数升序，再按原题顺序稳定排序。入口直接锚定已有再次作答文本框。
- 理由：页面已持有任务 ID 和服务端聚合历史，直接复用这些事实最简单，也不会把模型措辞、幻觉或工具选择转化为客户端控制流。当前筛选范围同时保证推荐目标真实可见。
- 调用边界：attempt 提交后继续由现有 composable 刷新持久化历史；用户返回助手后显式点击刷新才产生新的模型请求，不自动付费、不新增聊天历史或第二套状态。
- 验证：Vue TypeScript 检查、Vite 生产构建、Impeccable 静态检测和差异检查通过；未调用模型、数据库或后端服务。
- 回看条件：只有真实使用表明单题推荐不足时，才评估服务端结构化训练计划；在此之前不让模型生成可执行任务标识。

## ADR-060：单次真实复盘只作为工具选择与解释基线

- 背景：`get_review_progress` 的代码、测试和前端夹具已经通过，但尚未验证真实模型是否会选择该工具，以及是否会把空分数任务误写为退步。用户明确授权后，可以用最小脱敏数据建立首个真实证据。
- 决定：只发送一次复习助手 HTTP 请求，输入绑定一个具有 2 条复习任务和 1 条 attempt 的脱敏完成会话；客户端不自动重试。验收同时检查工具名、结果数、分数解释、未练习措辞、请求/工具日志关联、累计 token 和清理计数。
- 结果：`qwen3.7-plus` 正确执行 `get_review_progress`，将 `60 -> 75` 解释为提升 15 分，将另一题解释为尚未练习且无最近分数；请求和工具均成功，累计 token 为 `3228`，合成数据与日志最终清理为 0。
- 解释边界：一次成功只证明当前 Prompt、模型和这组持久化事实下的工具选择与表达符合预期，不代表长期稳定性；provider/model 回合数没有业务证据，继续保持未知，不把一次助手 HTTP 请求写成一次模型计费调用。
- 环境边界：共享 MySQL `max_allowed_packet=2048`，初始合成会话 SELECT 在 `2076` 字节时失败。本轮不修改数据库全局参数，只缩短合成文本完成验证；该限制属于部署环境风险，不通过业务代码规避正常会话体量。
- 回看条件：先由运维侧提高 MySQL 包上限，再用正常体量会话做完整链路验证；只有真实复盘反馈暴露稳定错误时，才调整 Prompt、增加固定复盘样本或扩展结构化响应。

## ADR-061：复习助手会话由结构化请求强制绑定

- 背景：前端此前把当前会话 ID 拼入助手消息，模型再把该 ID 填入工具参数。写入工具还有结构化人工确认保护，但 `list_review_tasks` 和 `get_review_progress` 只依赖模型参数；模型抄错、替换或受消息内容影响时可能读取错误会话。
- 选项：继续只用系统提示约束模型、从工具参数直接信任会话 ID，或由顶层请求结构化携带当前会话并在模型不可见上下文中强制校验。
- 决定：`POST /api/interviews/review-assistant` 要求必填顶层 `sessionId`。助手服务规范化该值，在调用模型前拒绝与其不一致的改期确认，并把会话写入 `InterviewAssistantRequestContext`；三个工具在进入 `InterviewReviewTaskService` 前都要求实际参数匹配该上下文，缺少上下文或跨会话时失败并记录执行日志。
- 理由：页面和 API 已经拥有确定的当前会话，应用绑定比依赖模型复制更可靠；保留工具参数可以维持现有清晰 schema 和结果结构，同时隐藏上下文提供不可绕过的最终边界。
- 写入边界：会话作用域不能代替人工确认。`schedule_review_task` 仍必须精确匹配同一请求中的会话、任务和日期确认，确认只在单次请求内有效。
- 验证：25 个助手 Controller、Service 和工具测试通过，覆盖缺失顶层会话、跨会话确认前置拒绝、三个工具跨会话拒绝、失败日志和既有成功路径；前端类型检查与生产构建通过。未调用模型或外部存储。
- 回看条件：只有未来出现多个并列会话上下文或正式用户授权模型时，才将该作用域扩展为独立授权对象；当前不建设通用权限或 Agent Runtime。

## ADR-062：评分证据必须经过服务端字面验真

- 背景：结构化评分已经保存分数、优缺点、改进建议和知识可靠状态，但用户无法判断模型究竟依据回答和资料中的哪段原文给分；只要求模型返回 evidence 又会允许它改写或伪造引文。
- 选项：只展示完整回答与完整 chunk、让模型自由返回解释文本，或让模型返回有限候选引文并由 Java 服务端映射和验真。
- 决定：`interview-answer-evaluation-v3` 要求 1 到 3 条当前回答引文和最多 3 条 `sourceIndex + quote` 知识引文。服务端逐字校验回答证据属于当前回答；知识序号必须位于当前题目的可靠来源列表，知识引文必须属于对应 chunk，随后映射为完整来源元数据并随评价保存。
- 无资料边界：有可靠资料时至少需要一条知识证据；无可靠资料时知识证据必须为空。回答证据始终至少一条，避免评分只剩无法追溯的总结。旧评价 JSON 缺少证据字段时恢复为空列表，但新的模型评价不能绕过验真。
- 理由：模型适合选择可能相关的文本片段，应用服务适合执行来源范围和字面归属约束；两者分工能提高可解释性，又不引入第二次模型调用、向量检索或复杂裁判系统。
- 解释限制：通过验真只能证明“引文真实存在且来自允许来源”，不能证明引用充分、评分正确或 rubric 完美。真实模型能否长期稳定满足新结构仍需单独基线验证。
- 验证：18 个评价、JSON、MySQL 会话快照和复习 attempt 测试通过；前端类型检查/生产构建以及零费用正式反馈与复习 attempt 浏览器夹具通过。未调用付费模型或外部存储。
- 回看条件：获得 `v3/v2` 真实模型基线后，再判断是否需要收紧引文长度、按评分维度拆分证据或调整 rubric；没有数据前不增加第二模型裁判。

## ADR-063：证据基线先记录数量并保持正文最小化

- 背景：证据验真代码可以拒绝伪造引文，但原固定基线响应只返回分数和知识依据状态，真实运行无法确认模型实际生成了多少条回答与知识证据。把引文正文写入基线结果又会扩大敏感输入和知识内容的复制范围。
- 决定：固定基线成功结果增加 `answerEvidenceCount` 与 `knowledgeEvidenceCount`；空回答等拒绝样本保持空值。计数来自已经通过服务端验真的评价对象，不新增模型调用、数据库字段或第二套证据校验。
- 真实结果：`v3/v2` 两轮共 8 次 Chat，8 次成功评价全部通过验真并落入宽松分数区间。完整回答为 `93/93`；无关回答为 `3/17`，总体方差 `49`。第二轮四个成功样本均返回回答证据，有资料样本各 1 条知识证据，无资料样本为 0。
- 隐私与解释：结果文件不保存 Prompt、回答、知识正文或引文。结构验真成功只说明引用真实存在且来源合法，不能推出分数稳定；旧版和新版均只有两次观测，平均分差异不能归因于 Prompt/rubric 变化。
- 可观测限制：现有评分服务通过结构化 `entity()` 获取结果，评价日志不记录 token。本轮不根据 HTTP 请求数推算 provider 回合，也不为一次基线扩展通用模型观测框架。
- 回看条件：真实使用需要成本比较时，优先为评分链路补充不含正文的 token/调用观测；需要调整 rubric 时，先扩充固定样本和重复次数，避免围绕单个无关回答的两次波动过拟合。

## ADR-064：最近会话入口使用浏览器 UUID 索引

- 背景：页面原先只在浏览器保存一个 active 会话 ID；用户主动开始新面试后无法回到较早的进行中会话或完成报告。现有数据库会话没有用户身份或归属字段，直接开放全量列表会把其他会话暴露为公共历史。
- 选项：新增后端全量会话列表、在浏览器缓存完整会话摘要，或只保存当前浏览器接触过的会话 UUID 并逐项恢复服务端事实。
- 决定：`localStorage` 最多保存 8 个去重 UUID；创建、回答和恢复成功后把会话置顶，页面复用 `GET /api/interviews/sessions/{sessionId}` 获取岗位、状态、进度和更新时间。404 会话从最近索引和匹配的 active ID 淘汰；连接失败、超时和其他非 404 错误保留 UUID。
- 理由：UUID 索引能在不引入用户体系、数据库字段或新接口的情况下恢复当前浏览器的真实工作流；服务端仍是状态唯一事实源，浏览器不复制简历、回答、评分、报告或知识正文。
- 影响：清理浏览器数据或更换浏览器后最近入口不可恢复；知道会话 UUID 的调用方仍受现有单会话接口边界约束。本决策不声称提供账号级历史、跨设备同步或数据授权。
- 验证：Vue 类型检查与生产构建通过；合成 API 浏览器验证进行中/完成恢复、404 淘汰、503 保留后刷新恢复，以及桌面/375px 无横向溢出和控制台无 warning/error。未调用模型或外部存储。
- 回看条件：只有引入正式用户身份与会话归属后，才设计后端分页历史、跨设备同步和整体统计；在此之前不以数据库全量查询替代浏览器索引。

## ADR-065：资料库问答先采用无状态单次请求与显式来源

- 背景：`POST /api/knowledge/answer` 已经能够返回可靠状态、回答和完整来源，但前端只有资料导入和面试训练，用户无法直接消费项目的 RAG 核心能力。现有接口没有对话 ID、历史存储或上下文裁剪模型。
- 选项：直接建设聊天会话与历史、把问答嵌进资料导入页面，或新增独立单次问答入口并完整展示现有服务端证据。
- 决定：新增 `/answer` 独立路由，复用现有无状态回答接口。页面显示 `grounded`、回答和与 `[资料 N]` 对齐的来源；来源默认展示逻辑来源、标题路径和相似度，展开后展示文档版本、chunk 顺序与原文。模型回答和来源正文均按纯文本渲染。
- 理由：独立入口让导入和提问成为两个清楚任务，又不需要复制检索参数、Prompt 或召回日志。显式证据把“引用真实存在”变成用户可核对事实；在没有连续追问和用户归属前，聊天历史只会增加隐私、上下文长度和状态一致性问题。
- 客户端边界：当前问题最多 2000 字符，回答请求超时 60 秒；开始新请求时清除旧结果，失败时展示服务端错误。浏览器不持久化问题、回答或来源，不解析模型 Markdown/HTML。
- 验证：Vue 类型检查和生产构建通过；合成 API 浏览器验证可靠回答、两条来源、原文展开、资料不足、503 错误、错误后重试、命令入口以及桌面/375px 响应式。未调用模型或外部存储。
- 回看条件：真实使用持续需要基于上一轮回答追问，并且已经明确用户归属、历史保留和上下文裁剪规则后，再设计对话会话；在此之前不以浏览器缓存伪装聊天记忆。

## ADR-066：资料发现复用原始相似度检索并与问答隔离

- 背景：`/answer` 已能生成带来源的可靠回答，但用户要浏览知识库内容仍必须产生一次 Chat 调用；后端已有返回真实 chunk、来源和相似度的 `GET /api/knowledge/search`，前端尚未使用。
- 选项：增加文档目录与全文阅读器、让问答接口同时返回检索预览，或在现有入口增加独立的零模型费用检索模式。
- 决定：`/answer` 使用“查资料/问资料库”分段模式。检索调用现有接口并固定沿用 `topK=5`、相似度阈值 `0.0`；结果按服务端顺序展示来源、标题路径、相似度、版本、chunk 顺序和原文。检索与问答各自拥有输入、加载、错误和结果状态。
- 理由：原始检索已经具备真实来源契约，直接接入能完成资料发现闭环且不增加模型费用、后端接口或第二套来源组件；状态隔离避免切换模式时把相似资料误当作可靠回答。
- 边界：检索结果只表示当前向量配置下的相似排序，不使用 `grounded` 文案、不新增未经评估的阈值、不保存检索历史或正文。第一版不增加文档目录、全文阅读器、搜索筛选、聊天历史或从模型自然语言生成操作。
- 验证：Vue 类型检查和 Vite 8 生产构建通过；Playwright CLI 合成响应覆盖成功、来源展开、空结果、503 与恢复，桌面和 `375px` 无横向溢出。未调用 Chat、Embedding、Qdrant、MySQL 或后端服务。
- 回看条件：真实使用需要先确认已导入来源时，再增加资料目录与版本查询；需要从检索继续提问时，只使用当前检索词或显式来源事实确定性传递，不解析模型文本。

## ADR-067：资料目录以当前成功登记版本为事实源

- 背景：`/answer` 已能检索和问答，但用户只能在产生命中后看到来源；版本表为去重保留同一来源的历史登记，直接列出全部行会把已经退出向量库的旧版本误写成当前资料。
- 选项：扫描 Qdrant 聚合来源、扩展版本表增加当前状态，或从现有成功登记顺序确定每个来源当前版本。
- 决定：`GET /api/knowledge/documents` 对每个大小写敏感来源只返回最后一条仍保留的登记。MySQL 使用最大自增 ID，进程内实现显式维护当前键；新版本索引失败并撤销登记时，当前键恢复为上一已登记版本。
- 理由：正常导入只有在向量写入和旧版本清理成功后才保留新登记，现有登记顺序已经能表达当前成功版本；复用该事实不需要新表、状态机、Qdrant 聚合或正文存储。
- 返回边界：目录只包含来源、完整 SHA-256 版本、内容字符数和登记时间，不返回历史版本、Markdown 正文、chunk、向量数量或健康状态；前端只缩写展示版本，完整值保留在提示中。
- 一致性限制：目录反映登记事实，不声称独立证明 Qdrant 点完整；MySQL 与 Qdrant 极端跨存储不一致仍由现有重建/删除机制处理。默认内存 profile 的目录会随进程重启清空。
- 验证：内存当前版本与失败回退、MySQL 查询契约和 HTTP 响应共 20 个测试通过；前端类型检查、生产构建和桌面/移动合成目录通过，未调用外部存储或模型。
- 回看条件：真实资料规模需要历史对比、回滚、索引健康或分页时，再引入明确的当前状态和一致性检查；在此之前不把目录扩展为运维后台。

## ADR-068：检索到问答只传递当前检索词

- 背景：`/answer` 已把资料目录、零 Chat 费用检索和可靠问答隔离为三个模式，但用户确认检索结果后仍需在问答模式重复输入同一问题；自动提交又会产生不透明的模型费用和不可编辑输入。
- 选项：点击来源后从正文生成问题、点击检索结果后自动发起回答，或只把当前检索响应中的归一化 `query` 作为问答草稿。
- 决定：检索成功且存在命中时显示显式衔接按钮。结果面板通过类型化事件上报 `result.query`；父视图清除旧问答结果、预填问题并切换到问答模式，用户可以继续编辑且必须主动提交。
- 理由：当前检索词是已有确定性用户输入，直接传递不会解析模型文本、来源正文或相似度结果，也不需要路由参数、全局状态、后端接口或第二次检索。清除旧回答可以避免新草稿与旧答案并列造成误读。
- 状态与费用边界：检索输入和结果继续保留，空结果、加载和错误状态不提供衔接；点击本身不调用 Chat、Embedding 或后端回答接口，不保存问题或历史。
- 验证：Vue TypeScript 检查和 Vite 8 生产构建通过；Playwright CLI 合成响应验证归一化预填、继续编辑、零回答 POST、`375px` 无横向溢出和控制台 0 warning/0 error。未调用模型或外部存储。
- 回看条件：只有真实使用需要限定具体来源问答时，才增加结构化来源选择与对应后端契约；在此之前不从 chunk 正文自动拼接 Prompt，也不把相似度命中包装成可靠答案。

## ADR-069：资料详情复用版本登记并限制当前版本重建

- 背景：目录只展示每个来源当前版本，用户无法核对历史登记或理解新版本替换、人工删除的差异。进一步检查发现，原重建允许已登记历史版本重新写入并删除其他版本向量，但当前版本仍由最大登记 ID 决定，可能造成目录显示新版本、实际检索旧版本。
- 选项：新增完整文档状态表和软删除、从 Qdrant 反查详情，或复用现有登记事实并收紧重建边界。
- 决定：新增按精确来源查询的元数据详情，返回当前版本和按登记顺序倒排的历史版本；重建只接受详情首项对应的当前版本。前端详情展示当前/历史状态，整来源淘汰复用现有 DELETE 并要求二次确认。
- 理由：版本登记已经是重复判定和当前版本的事实源，复用它不需要迁移或把向量库当作文档库。当前版本约束使重建只能修复目录所声明的生效版本，避免隐式回滚和跨存储错位。
- 淘汰语义：自动替换在新向量成功写入后删除其他版本向量，但保留历史登记；人工淘汰先删除来源全部向量，再删除全部登记。前一步失败时数据库不变；后一步失败时调用方可以重试幂等删除。
- 数据边界：详情不返回 Markdown 正文、chunk、向量数量或健康状态；当前不提供软删除、保留期、历史原文预览或在线回滚。DELETE 成功后任意历史版本可以通过普通导入重新建立新的生命周期。
- 验证：33 个登记、导入、MySQL Mapper 和 HTTP 测试通过；Vue TypeScript 检查与 Vite 8 构建通过。Playwright 合成链路覆盖详情、两条版本历史、取消不删除、确认后单次删除、目录刷新和 375px 无横向溢出，控制台 0 warning/0 error。未调用外部存储或模型。
- 回看条件：真实需求需要误删恢复、保留期或无原文件回滚时，再增加正文对象存储、显式当前状态与软删除字段；在此之前不把历史登记包装成可直接恢复的文档快照。

## ADR-070：当前版本重建在资料详情中显式重传原文件

- 背景：后端已有 `POST /api/knowledge/documents/rebuild`，且已限制为当前登记版本，但资料目录详情只能查看、淘汰，用户无法从产品界面修复已知的向量缺失或残留。
- 选项：允许页面从历史登记恢复正文、在浏览器缓存导入文件，或要求用户为当前来源重新选择原 Markdown 文件后调用既有重建接口。
- 决定：资料详情增加独立的“选择原文件并重建”操作。前端仅携带当前详情的 `source` 与用户新选择的文件；服务端继续根据文件内容计算版本并拒绝未登记、历史或内容不一致版本。重建期间禁用目录切换、淘汰与关闭，成功后重新读取当前来源详情并展示实际切片数。
- 理由：登记表只保存版本元数据，无法安全还原 Markdown 正文；重传原文件保持内容事实由用户确认，复用后端版本校验和向量生命周期，不需要正文存储、文件缓存、新状态表或回滚语义。
- 边界：当前入口只接受 `.md` / `.markdown` 文件，不修改版本登记、不让历史版本重新生效，也不对 Qdrant 健康状态作额外承诺。服务端失败时详情仍保留并显示原始中文错误。
- 验证：Vue TypeScript 检查和 Vite 8 生产构建通过，共转换 1938 个模块。Playwright 合成接口确认成功重建后重新读取详情，版本不一致时显示服务端原始错误且清除旧成功提示；`375px` 错误状态无横向溢出。未调用 Chat、Embedding、Qdrant、MySQL 或真实后端。
- 回看条件：真实使用出现原文件不可得但需要恢复的场景时，再设计正文对象存储、版本回滚权限与审计；当前不将历史登记扩展为可恢复快照。

## ADR-071：章节目录作为版本登记的无正文快照

- 背景：解析、切片和向量元数据已经保存标题路径与顺序，但详情只读版本登记且不应依赖 Qdrant；若在线扫描向量或重新生成摘要，详情会受外部存储、Embedding 和模型费用影响。
- 选项：从 Qdrant 聚合标题、持久化 Markdown 正文后按请求解析、用模型生成摘要目录，或在导入时把确定性章节结构保存到版本登记。
- 决定：为版本表增加可空 `outline_json MEDIUMTEXT`。目录只保存标题、级别、首个直属 chunk 顺序、直属 chunk 数和子节点；忽略标题前导正文，跳级标题挂到最近有效父级，空正文标题保留且 chunk 定位为空。
- 一致性：新导入先解析和构建目录，再通过原有唯一键原子登记；重复导入仍在 Embedding 前短路。当前版本重建先完成向量收敛，再更新目录，避免失败响应留下部分成功状态。旧行保持 `null`，由用户重传当前原文件补齐，不伪造历史目录。
- 边界：详情只返回当前版本目录，历史项仍为元数据；不保存正文、不查询 Qdrant、不生成 AI 摘要/术语表/速查表，也不提供章节级在线阅读或历史回滚。
- 验证：41 个后端相关测试、Vue 类型检查与生产构建通过；浏览器合成数据覆盖嵌套、跳级、空正文、旧数据空态和移动端溢出。未执行真实存储迁移或外部模型调用。
- 回看条件：真实使用需要从章节直接检索时，优先传递确定性标题或结构化章节定位；只有需要原文预览或历史恢复时才设计正文对象存储。

## ADR-072：章节入口只生成可编辑的全路径检索草稿

- 背景：章节树已经让用户看见资料结构，但要查相关原文仍需切换模式并重复输入标题。现有搜索接口不接受来源或 Chunk 范围，直接命名为“搜索本节”会制造错误的范围承诺。
- 选项：点击后自动搜索当前标题、扩展后端增加来源/Chunk 过滤，或只把完整标题路径交给现有检索输入。
- 决定：章节行显示“查资料”，可访问名称包含从根到当前节点的完整标题路径。点击只清除旧结果、预填路径、切换检索模式和聚焦输入框；用户编辑或确认后显式提交才产生请求。
- 理由：完整路径比单个子标题歧义更小，并且全部来自版本登记事实；复用现有检索状态不增加接口、过滤语义或模型费用，也不会把页面导航和网络副作用藏在同一次点击中。
- 边界：搜索范围仍是整个资料库，`topK=5` 和阈值 `0.0` 不变；不保证命中当前来源或目录所示 Chunk，不自动调用 Chat/Embedding，也不从模型文本生成动作。
- 验证：Vue 类型检查和 Vite 生产构建通过；浏览器合成响应确认点击后完整路径和输入焦点正确、搜索请求为 0，显式提交后才出现一次 GET，移动端无溢出且控制台无警告或错误。
- 回看条件：只有固定样本证明跨来源噪声稳定影响章节检索时，才设计结构化来源过滤，并同步调整接口文案与评估；不先假设过滤一定改善召回。

## ADR-073：资料目录使用主从工作区而不更换视觉语言

- 背景：用户认可现有工作台风格，但资料目录与详情纵向堆叠，详情中的章节、版本、重建和淘汰近似同权；目录数据态高度过大，中宽和移动端选择来源后详情出现过晚。
- 选项：整体更换配色和组件风格、继续使用纵向卡片流，或保留现有设计令牌并重组信息关系与密度。
- 决定：桌面端使用固定宽度资料列表加弹性详情的主从结构，详情内将章节树设为主栏，将版本历史和资料维护归入次栏；中小屏回退单列，窄屏选中来源后目录成为有限高度原生滚动区。目录、详情与维护区主要使用分隔线和留白，不新增嵌套卡片。
- 理由：问题来自任务关系和视觉权重，不是品牌风格。稳定主从关系让用户能同时定位来源和核对章节，维护操作保持可见但不抢占阅读主线；窄屏有限高度避免完整目录把已选择详情推到页面末端。
- 行为边界：不改变目录、详情、重建、淘汰和章节检索的 API 或事件契约，不新增抽屉、路由状态、动画、全局状态和视觉令牌。目录滚动使用浏览器原生行为。
- 验证：Vue 类型检查和生产构建通过；1440 px 显示章节主栏与维护次栏，1024/375 px 正确回退单列，三种宽度均无页面横向溢出，控制台无 warning/error。
- 回看条件：真实资料来源明显超过当前规模时，再评估目录搜索、虚拟列表或移动端独立详情路由；不因预期规模提前增加复杂导航。

## ADR-074：PDF 解析先建立同语料基线再调整算法

- 背景：`PdfInterviewDocumentTextExtractor` 使用 PDFBox 位置排序，现有测试只能证明文字存在，不能证明阅读顺序正确；直接引入列检测或另一运行时会失去可比较的改进依据。
- 决定：由测试侧确定性生成单栏、双栏和无文本层 PDF，以 `repository-deterministic-v1` 统一计算页数、关键短语命中、固定标记阅读顺序和失败类型，并把当前 `pdfbox-position-sort-v1` 报告固化为 golden baseline。
- 失败表达：基线允许并明确记录已知失败，而不是用宽松断言把它包装成通过。当前 3 个样本通过 2 个，关键短语命中率 100%，双栏阅读顺序失败；后续候选只有在同一语料、同一评估器下改善且不破坏单栏时才可替换线上路径。
- 理由：这种方式采纳 `pdf-inspector` 的可比较质量工程方法，但保持 Java/PDFBox 技术路线和最小改动；在真实脱敏样本不足时，不手写过度复杂的版面引擎。
- 边界：指标是固定字面断言，不声称实现 NID、TEDS 或 MHS；合成样本不代表真实简历总体质量。本轮不修改生产提取器、不增加 OCR、Rust/Python 运行时、表格 Markdown 或文件持久化。
- 回看条件：加入脱敏真实双栏、混合页、中文字体和表格样本后，再评估 PDFBox `TextPosition` 列检测、专用解析服务或逐页 OCR 路由。

## ADR-075：PDF 解析返回逐页质量证据并保守调整双栏

- 背景：原 `sortByPosition=true` 保住了字符但会按水平行交错双栏，且全文是否为空无法区分文本页、图片页和混合文档。用户需要的是可检查、可继续发展的解析能力，而不是针对一个 fixture 的特殊排序。
- 决定：继续使用 Java/PDFBox，一次加载后逐页收集文字坐标和实际绘制图像。文本先聚合基线并按大空隙拆段；只有左右各至少两行、垂直区间重叠、中间 gutter 足够且两侧平均正文宽度达到门槛时启用双栏，跨栏标题保留在前，栏间穿越内容和窄日期列回退单栏。
- 输出契约：兼容原 `content/format/pageCount`，新增文档类型、文本/图像页数、双栏调整页数、OCR 候选页、告警和逐页内容/版面摘要。整份无文字继续失败；混合 PDF 返回现有文字并显式提示指定图像页需要检查或补充。
- 理由：页面证据让前端、评估和后续 OCR 适配共享同一事实，不需要把另一运行时或外部服务塞进主路径；保守回退比误排单栏简历更容易由用户发现和修正。
- 安全与隐私：解析在本地请求内完成，不保存原文件或摘要，不写数据库、知识库、向量库和 localStorage；检测到 OCR 候选页不会自动调用第三方服务。
- 回看条件：先加入脱敏真实中文简历、日期侧标、表格和复杂侧栏基线；只有同评估器证明本地算法仍存在稳定缺口，才调整门槛或比较专用解析后端。OCR 接入必须另行明确供应商、隐私、成本、超时、失败和人工确认策略。

## ADR-076：复杂版面先扩展评估器，不为改生产代码而改算法

- 背景：`pdfbox-layout-aware-v2` 已修复清晰双栏并识别混合页，但此前只有四类合成样本；直接继续调门槛会围绕预期缺陷过拟合，也无法判断中文字体、日期侧标、技能表和复杂侧栏是否已经落在现有保守边界内。
- 决定：保持生产解析器不变，将确定性评估器升级为 `repository-deterministic-v2`。新增运行时嵌入黑体的脱敏中文单栏、右侧窄日期列、无边框技能键值表和宽侧栏简历；分别断言 Unicode 关键短语、逐行单栏回退或左栏后右栏顺序。测试机缺少指定字体时明确跳过整条基线，不把字体文件提交仓库。
- 结果：8 类样本 8/8 通过，文本关键短语 35/35，阅读顺序全部正确；日期列和技能表保持单栏，复杂侧栏识别为双栏。现有算法没有暴露稳定缺口，因此不修改生产代码、不新增配置或表格解析器。
- 理由：评估先行能把“继续增强”转换为证据驱动选择；没有失败样本时改算法只会增加回归风险。保留 `v1`、四类 `v2` 和八类 `v2` 报告可以区分解析器变化与语料扩展。
- 边界：合成样本不能证明所有真实中文字体、嵌套表格、浮动文本框或扫描件可用；OCR 检测仍只返回候选页，不触发外部服务。
- 回看条件：获得经授权脱敏的真实简历，且同一评估器稳定复现关键短语丢失、错误阅读顺序或页面分类错误后，再以最小测试驱动方式调整生产算法；否则保持当前保守实现。

## ADR-077：角色 Agent 先走简单基线，图工作流由真实状态需求触发

- 背景：项目希望扩展 Agent 技术栈，但当前主要需求是简历证据审计、岗位匹配和项目深挖；直接引入 LangGraph、多 Agent 或通用治理平台不能自动提高模型质量，还会增加调用、状态和部署成本。
- 决定：Java/Spring AI 继续作为主业务和 Agent 平台，首个角色只完成单次结构化审计与服务端证据验真。真实出现证据失败修正、条件分支、HITL 暂停或 checkpoint 恢复后，才引入图状态、条件边和节点级日志；其他角色随后作为专业节点或子图扩展，不自由对话。
- 技术边界：Java 负责权限、业务事实、最终写入和审计。优先比较与当前 Spring AI 兼容的 Java 图方案；Python LangGraph 先用于对照学习，只有图执行收益明显超过跨服务成本时才作为受控独立服务。
- 验收：图方案与简单基线使用同一批样本比较事实准确率、证据合法率、虚构率、修正/完成/恢复率、模型调用次数、token、费用和 P95 延迟；质量或恢复能力没有明确提升时回退简单工作流。
- 抽象条件：第一个角色局部实现治理，第二个角色出现相同模式后才提炼角色定义、请求观测、证据校验或工具策略，不提前建设通用 Agent Runtime、A2A、共享自由记忆或 AI Gateway。

## ADR-078：检索增强前先用分层困难指标定位失败

- 背景：旧固定集只有 6 题和 5 份明显区分的语料，6/6 首位命中不能回答相似来源竞争、跨章节覆盖、标题定位和无答案假阳性问题，也不足以决定混合检索或 rerank。
- 决定：固定集扩为 20 题和 8 份语料，题型覆盖精确术语、相似章节、标题路径、歧义、无答案和跨章节。检索仍使用 `topK=5`、阈值 `0.0` 观察完整排序，再按生产回答阈值 `0.60` 单独判断是否拒答。
- 指标口径：来源按不同逻辑来源去重；Hit@1 与 MRR 使用首个期望来源排名；Recall@5 计算每题期望来源覆盖比例；标题路径要求完整列表精确匹配；无答案拒答准确率只在 3 道无答案题上统计。
- 兼容边界：保留旧期望来源命中字段，但分母只包含 17 道可回答题。无答案题不伪造期望来源；回答评估返回空来源时视为符合拒答预期。
- 选择规则：真实基线若主要失败在首位排序再评估 rerank，来源召回不足再评估查询改写或混合检索，标题召回不足再评估父子索引或上下文化切片，拒答错误先调整语料与阈值。未形成失败分布前不引入新检索组件。
- 费用边界：确定性指标和 HTTP 契约可以零费用验证；导入三份新语料会产生 Embedding 调用，真实 20 题基线必须显式授权，未执行时不得生成结果文件或声称新指标成绩。
- 首轮结果：用户授权后执行真实 `text-embedding-v3` 基线，Hit@1 与 MRR 均为 `1.0000`，Mean Recall@5 为 `0.9706`，标题路径召回为 `0.9130`，拒答准确率为 `1.0000`。两条缺失证据都属于同一查询需要覆盖多个主题或章节，不属于首位排序错误，因此继续暂缓 rerank，先比较查询拆分或章节扩展。
- 阈值观察：3 道无答案题最高候选相似度为 `0.5700`，当前 `0.60` 全部拒答，但安全余量只有约 `0.03`。当前不调阈值，也不把 3 个样本外推为长期稳定；扩大语料后继续加入相近但无答案的问题。

## ADR-079：查询拆分先作为可回退的评估候选

- 背景：首轮困难基线的 Hit@1/MRR 已满分，但一个跨主题问题漏来源、一个歧义问题漏标题路径；直接改生产检索会在没有对照数据时增加 Embedding 次数，并可能把无答案候选推过 `0.60` 阈值。
- 选项：直接接入模型查询改写、引入 rerank/混合检索、扩展相邻章节，或先实现不依赖模型的确定性查询拆分对照。
- 决定：增加评估专用 `deterministic-clause-rrf-v1`。原问题始终保留；多句、逗号子句和带“分别/各自/两者”的协调结构最多产生 3 个额外查询。每路取 Top5，按 chunk 身份去重后使用 RRF 生成候选 Top5。
- 对照边界：baseline 与 candidate 复用同一次原查询；当前 20 题会拆分 13 题并增加 29 次查询。报告公开逐题查询计划、拆分题数和额外查询数，并继续比较 Hit@1、Recall@5、MRR、完整标题路径召回和拒答准确率。原评估、搜索、回答和面试接口语义不变。
- 接入门槛：真实 `text-embedding-v3` 对照必须显式授权。只有缺失证据被补回、Hit@1/MRR 不明显下降、3 道无答案拒答不退化，且额外调用成本可接受时，才设计生产接入；否则保留评估结论并转向章节扩展。

## ADR-080：首个角色使用单次结构化审计与 Java 证据裁决

- 背景：现有面试画像只要求模型列出简历证据，未逐条绑定事实和引文，也没有角色级请求日志。投递前路线要求先完成可讲清的简历证据审计，而不是直接引入图工作流或多个求职角色。
- 决定：首个角色固定为 `RESUME_EVIDENCE_AUDITOR`，使用 `resume-evidence-audit-v1` 单次 Spring AI Structured Output。模型输出事实、缺失、风险和建议；只有项目、技术、职责、时间、结果五类事实需要逐字引文，并由 Java 在返回前整体校验。
- 注入边界：强指令特征按整行从模型输入和证据范围隔离，响应只公开隔离数量。该方法能确定性阻断固定攻击样本，但不是通用 Prompt Injection 分类器；未命中特征的自然语言攻击仍需依赖系统 Prompt、结构化输出和后续真实评估。
- 失败语义：任一事实引文不在隔离后简历中时整次审计失败，不静默删除、不把它降级为风险，也不自动重试或启动修正循环。只有真实样本稳定出现可修复证据失败后，才评估有界修正和图节点。
- 隐私边界：请求日志独立保存 UUID、角色、Prompt/模型版本、token、耗时、状态和异常类型，不保存简历、完整 Prompt 或审计正文；日志失败只告警。迁移 `015` 未自动执行，避免在没有授权时写共享数据库。
- 质量边界：字面包含只能证明引文来自简历，不能证明事实陈述被引文完整支持。六类 Mock 固定样本只验证代码契约；真实事实准确率、证据合法率、缺失识别率和虚构率留给下一阶段固定模型评估。

## ADR-081：角色评估使用固定事实标签而不引入模型裁判

- 背景：简历证据审计已经能拒绝不在原文中的引文，但六类 Mock 测试只能证明代码路径，不能形成可重复的真实模型质量报告。直接使用 LLM-as-Judge 会增加费用、方差和新的 Prompt 版本，同时可能把简历正文交给第二个模型。
- 决定：建立版本化六类脱敏数据集，以“事实类型 + 逐字证据”作为预期事实标签，并为信息缺失与风险保存短关键词。模型结果经过现有 Java 验真后，再用确定性集合比较计算事实准确率、预期事实召回率、虚构率和信号召回率；不增加第二个模型裁判。
- 指标边界：事实准确率衡量已确认事实中匹配固定标签的比例，预期事实召回率单独衡量遗漏；证据合法率衡量模型候选事实中通过逐字校验的比例。结构化输出生成与完整审计成功分开计数，避免非法证据掩盖结构解析事实。
- 隐私与成本：HTTP 报告和可选结果文件只含样本 ID、计数、比率、版本、token、耗时和失败类型。没有可核对单价时费用字段保持为空并说明原因，不硬编码易失效价格；真实运行需要明确费用授权。
- 校准结果：`v1` 只标代表性事实并要求证据完整相等，真实运行把更多合法原文事实误记为虚构。`v2` 改为完整原子事实标签和同类型证据包含匹配；信息缺失与风险使用有限同义短词组。该调整来自固定输入和逐 case 计数，不查看或保存模型正文，也不按总分反向无限放宽标签。
- 真实基线：`v2` 六例审计/结构成功率和证据合法率均为 `1.00`，事实准确率 `1.00`、预期事实召回率 `0.80`、信息缺失识别率 `0.75`、虚构率 `0`、风险信号召回率 `1.00`，严格通过 `2/6`。当前不进入前端，先针对事实遗漏和技能使用场景漏报调整 Prompt，再用相同 `v2` 标签对照。
- 回看条件：固定标签不能覆盖语义等价表达或新简历形态时，先扩充人工标注样本；只有确定性标签无法评价的开放式建议质量成为核心需求时，才隔离比较人工评审或有限 LLM-as-Judge，并单独记录成本与方差。

## ADR-082：真实模型评估运行器默认拒绝隐式付费调用

- 背景：RAG 检索基线可能在导入或查询阶段调用 Embedding，简历证据审计固定评估会产生 6 次 Chat 调用。文档警告不能阻止复制命令或自动化在缺少费用授权时直接发起请求。
- 决定：两个 Python 运行器在解析参数后、任何 HTTP 请求和结果写入前检查专用授权参数。RAG 运行器使用 `--allow-embedding-calls`，简历审计运行器使用 `--allow-chat-calls`；缺少参数以退出码 2 拒绝执行。
- 理由：按调用类型命名比通用 `--force` 更清楚，也不会把一次授权持久化为配置或环境变量；每次运行都需要在命令中留下可见意图。
- 边界：不在后端接口增加全局费用开关，不改变正常产品 Chat/Embedding 能力，也不声称能够阻止所有直接 HTTP 调用。授权参数证明执行意图，不证明账号额度、模型可用性或费用上限。
- 回看条件：后续出现统一评估任务中心或模型预算治理时，再把调用预算、费用上限和审批记录收敛到服务端；当前不为两个脚本引入通用运行时。

## ADR-083：简历审计 Prompt 不以事实准确率换召回率

- 背景：`resume-evidence-audit-v1` 在 `dataset-v2` 上保持事实准确率 `1.00` 和虚构率 `0`，但事实召回率只有 `0.80`、信息缺失召回率只有 `0.75`。需要验证更明确的全量提取指令能否同时补齐两类缺口。
- 对照：冻结数据集、确定性匹配和 `qwen3.7-plus`，只将 Prompt 候选升级为 `resume-evidence-audit-v2`，要求逐句枚举、多类型拆分、技能逐项提取和技能场景缺失诊断。候选把事实与缺失召回均提高到 `1.00`，严格通过从 `2/6` 提高到 `4/6`。
- 决定：拒绝该候选并让生产继续使用 `resume-evidence-audit-v1`。原因是候选新增两条标签外事实，事实准确率降为 `0.9091`、虚构率升为 `0.0909`；证据逐字合法只证明引文来源，不能证明分类与事实陈述正确，不能用召回改善抵消该边界退化。
- 标签边界：不为了接受候选而继续放宽冻结的 `dataset-v2`。项目空泛和提示注入两例各出现一条标签外事实，但当前脱敏报告只有计数，不能把它们推断成数据集漏标或模型错误后再改标签。
- 回看条件：下一候选前先增加不含正文的事实类型级匹配/未匹配计数，缩小分类问题范围；只有新候选保持证据合法率 `1.00`、事实准确率 `1.00` 和虚构率 `0`，并改善事实或缺失召回时，才替换生产 Prompt。

## ADR-084：真实简历先扩事实语义边界，再接前端或图工作流

- 背景：固定六类短样本没有覆盖完整教育、任职主体、长技能区和多项目职责。一份用户授权的真实校招简历在 PDF 顺序修复后完成生产审计，27/27 引文合法，但至少出现 2 条事实类型错误和 1 条低价值缺失诊断。
- PDF 决定：保持 Java/PDFBox，在文本段最终排序时把纵坐标差不超过 `4pt` 的内容归入同一视觉行，并按横坐标排序。该规则修复不同字号导致的右侧日期先于左侧主体，不改变单栏/双栏判断；解析器升级为 `pdfbox-layout-aware-v3`，同评估器 8/8 不退化。
- Agent 结论：现有 `PROJECT`、`TECHNOLOGY`、`RESPONSIBILITY`、`TIME`、`RESULT` 五类不足以表达教育和任职主体，模型会为满足 Schema 把真实内容错误塞入 `PROJECT`。Java 字面校验无法发现这种语义分类错误，因此“全部证据合法”不是前端接入条件。
- 容量与质量：真实校招简历一次产生 27 条事实，已占 30 条上限的 90%，且仍漏掉个人技能事实和项目职责类型。不能只提高上限或再次要求全量拆分，否则会继续增加 token、延迟与错误分类；本次单调用已消耗 `7560` token、耗时约 `104.6s`。
- 后续顺序：先为教育和任职主体确定独立类型或明确排除规则，增加真实形态脱敏类型标签，并设计分节或优先级容量策略；这些基础语义稳定后再接 PDF 审计前端。只有真实出现可修复证据失败、人工暂停或恢复需求时，才进入图工作流。
- 隐私边界：真实原文和完整审计仅用于授权的一次性人工核对，永久报告只保存计数与结论；不得把真实 PDF 或个人信息转成仓库 fixture。

## ADR-085：教育与任职使用独立事实类型并先做固定分类回归

- 背景：真实校招简历暴露出现有五类事实不足，学校、专业、公司和职位会被模型归入 `PROJECT`；逐字证据校验只能证明来源合法，无法证明语义类型正确。
- 决定：在不改变生产 Prompt 版本和前端边界的前提下，新增 `EDUCATION` 与 `EMPLOYMENT` 两个事实类型。系统 Prompt 明确学校/专业/学历/教育主体归入教育，企业/职位/任职主体归入任职，日期（包括毕业年份）仍归入 `TIME`，禁止用项目类型承载两者。
- 验证边界：固定评估数据集升级为 `resume-evidence-audit-dataset-v4`，教育/任职样本仅保留用户简历中的最小分类字段，并保持报告不返回正文；真实模型基线必须在费用授权后重跑，当前不能把本地 Mock 通过写成真实分类质量证据。
- 后续：只有授权真实基线确认类型准确率、证据合法率和容量边界可接受，才继续扩展个人技能和项目职责标签；若分类错误仍集中出现，再设计分节/优先级容量策略，不直接提高事实上限。

## ADR-086：单行技能清单的场景缺失由 Java 窄规则兜底

- 背景：`dataset-v4` 真实基线中，`skill-stacking` 的五条技术事实和技能堆砌风险均命中，但模型没有在 `missingInformation` 指出缺少项目使用场景，使信息缺失识别率保持 `0.7500`。此前 Prompt v2 虽补齐该项，却使事实准确率从 `1.00` 降至 `0.9091`，不能再次用宽 Prompt 换召回。
- 决定：生产 Prompt 继续使用 `resume-evidence-audit-v1`。只有净化后的输入完整匹配一行 `技能`、`专业技能` 或 `技术栈` 清单，且模型缺失项没有包含场景或使用/实践证据时，Java 才补充固定缺失描述；模型已有同类描述时保持原结果。
- 理由：该条件与失败样本一一对应，结果确定、零额外模型调用，不影响事实类型、证据验真、风险和建议；相比多段简历语义匹配或新 Prompt，它的误判面和回归面更小。
- 边界：规则只证明“孤立技能清单没有提供使用上下文”，不判断候选人不会该技术，也不推断多段简历中技能与项目的关联。v4 历史指标不回写，真实指标只能在新的费用授权后重跑。
- 回看条件：若真实样本稳定暴露多段简历的技能场景缺失，应先增加脱敏类型标签和确定性失败样本，再决定分节审计或有界模型修正；不把当前正则扩成通用简历语义引擎。

## ADR-087：简历审计按证据质量门槛接入为可选内存态工作流

- 背景：真实简历已证明逐字证据合法不能自动保证事实类型正确，且 27 条结果接近 30 条上限。前端接入前需要同时解决项目/职责语义、容量诊断和可重复质量门槛，不能只以“接口调用成功”作为完成标准。
- Prompt 与容量：生产 Prompt 升级为 `resume-evidence-audit-v3`，明确项目名称、技术事实、个人职责和量化结果的边界；同一句允许拆分技术和职责。事实仍最多 30 条，超量优先保留各项目名称、职责和结果，再保留教育/任职、核心技术和时间，不直接扩大模型上下文与返回规模。
- 评估决定：`dataset-v6` 使用九类、64 条原子标签并返回七种类型指标与容量诊断。v5 第一轮新增的两条事实都能从固定输入直接证明，因此通过一次有限标签校准纳入 v6；该校准依据逐字输入与类型计数，不依据总分无限放宽标签。v6 事实准确率和证据合法率均为 `1.0000`、虚构率 `0`、职责召回率 `1.0000`，满足前端接入门槛。
- 前端决定：审计作为面试准备页可选步骤，不作为开始面试的硬门槛。结果只存在组件 composable 的页面内存，不写 localStorage、全局状态或业务表；失败保留直接开始路径，简历变更后旧结果只标记待更新。这样既提供可见价值，又不扩张简历数据生命周期。
- 表述边界：v6 总召回率为 `0.9219`，教育/任职样本从同一 Prompt 第一轮 `11/11` 波动到正式轮 `6/11`。页面和文档统一使用“已确认事实”，明确未出现不代表候选人不会，不宣传完整简历解析或稳定全量召回。
- 回看条件：只有扩大脱敏教育/任职与长简历样本后仍稳定出现同类遗漏，才比较分节抽取或有界修正；只有出现人工暂停、恢复或循环修正的真实需求，才引入图工作流。当前不增加第二次模型调用、PII 抽取、OCR、新中间件或通用 Agent Runtime。

## ADR-088：先扩样本并真实触顶，再决定分节抽取

- 背景：`dataset-v6` 只有一个教育/任职样本，同一 Prompt 两轮从 `11/11` 波动到 `6/11`；长简历样本最多 25 条事实，没有触达生产 30 条上限。单样本波动和未触顶数据不足以证明需要第二次抽取、修正循环或图工作流。
- 决定：`dataset-v7` 新增日期前置和多段教育/任职两种全合成版式，并把长简历样本扩为恰好 30 条互不重复原子事实。数据集共 11 类、90 条预期事实，生产 Prompt、30 条上限、接口、前端和数据生命周期保持不变。
- 容量口径：达到 30 条只表示模型候选数量触顶，不表示 30 条都正确或优先级执行正确。继续用类型级准确率/召回率和逐样本匹配判断教育、任职、项目、职责与结果是否按 Prompt 保留，不能只看总召回率。
- 费用与表述：离线 Mock 仅验证标签、聚合和触顶报告契约。v7 真实基线必须在新的 11 次 Chat 费用授权下执行；未运行前，v6 仍是最新真实质量证据，不声称召回改善或容量策略有效。
- 后续门槛：只有 v7 真实运行在多种教育/任职版式或 30 条样本上稳定复现同类遗漏，才比较分节抽取或最多一次有界修正；若准确率、证据合法率或虚构率退化，则优先收紧类型/容量指令，不以更多调用掩盖错误。

## ADR-089：v7 不进入分节抽取，先解决类型互斥

- 真实证据：`dataset-v7` 的 11 次 `qwen3.7-plus` Chat 全部完成审计和结构解析，90 条预期事实全部命中；教育 `16/16`、任职 `12/12` 与 30 条容量样本均无遗漏。该结果没有复现 v6 的教育/任职召回缺口，也没有证明容量优先级失败。
- 新缺口：多段教育/任职样本额外产生 2 条技术事实，项目职责样本额外产生 1 条职责事实，使事实准确率为 `0.9677`、虚构率为 `0.0323`。证据合法率 `1.0000` 只说明这些引文来自输入，不能证明跨类型重复正确。
- 决定：保持生产 `resume-evidence-audit-v3`、单次调用、30 条上限和前端边界不变，不进入分节抽取、有界修正或图工作流。先离线复核项目职责标签；随后只修改教育专业、学历和职位不得重复输出为技术事实的类型互斥指令，使用同一固定集做单变量候选对照。
- 标签边界：v7 报告不保存事实证据正文，不能仅凭总分把 3 条额外事实全部补入标签。项目职责样本存在可解释的动作短语，只记录为待复核；教育/任职样本没有独立技能段，额外技术事实按类型重复风险处理，不以召回满分抵消准确率退化。
- 运行边界：新的 Prompt 对照需要下一次明确 Chat 费用授权。共享数据库迁移 `015` 缺失导致本轮角色请求日志未落库，但不影响脱敏评估报告；迁移属于独立部署操作，不在本次模型授权内自动执行。

## ADR-090：拒绝查询拆分 RRF，采用有界相邻 Chunk 扩展

- 真实对照：固定 20 题在 `text-embedding-v3` 下执行 `deterministic-clause-rrf-v1`，13 题拆分、增加 29 次查询；Hit@1 从 `1.0000` 降为 `0.9412`，MRR 从 `1.0000` 降为 `0.9706`，Recall@5、标题路径召回和无答案拒答准确率均未改善。
- 决定：不把查询拆分或 RRF 接入生产，也不继续调权重。针对标题路径召回 `0.9130` 的局部缺口，在初始可靠向量命中后按 `source + document_version + chunk_order` 补充前后一段上下文。
- 边界：扩展器最多处理 3 个初始种子、最多返回 8 条资料；只允许同来源同版本，按来源/版本/顺序去重；初始无命中时不触发扩展。该逻辑只接入 RAG 回答，不改变裸检索、评估和面试链路的 `topK`/阈值语义。
- 证据边界：本轮确定性测试证明过滤、去重、上限和拒答保护；尚未证明固定题集指标提升，后续必须单独记录真实扩展前后来源覆盖和回答质量，不能把接线本身写成质量改善。

## ADR-091：PDF 知识资料先复用页面分析，再进入现有 Markdown/Chunk 链路

- 背景：项目已有面向简历的 PDFBox 版面分析，但知识库目前只有 Markdown，真实资料接入范围不足。直接新增另一套 PDF 解析器会造成阅读顺序和质量边界分叉。
- 决定：复用 `PdfDocumentAnalyzer` 的页面文本、双栏顺序、图片页和 OCR 候选判断；新增知识资料适配器，将有文本页面转换为带 `第 N 页` 标题的结构化内容，再复用现有版本登记、Chunk 切分和 Qdrant 写入。
- 数据边界：Qdrant 记录 `document_format=PDF` 和可识别 `page_number`；页面告警随导入响应返回。原始 PDF、完整解析正文不写入 MySQL 或 Qdrant，整份无文本 PDF 直接拒绝，混合 PDF 不索引空页面。
- 先进性判断：本轮价值不在“增加 PDF 后缀”，而在页面级来源追踪、版面质量告警和既有 RAG 生命周期复用。代码块/表格语义、跨页章节和 OCR 仍需独立样本验证，不声称已经完成通用文档理解。
- 后续门槛：先完成页面/章节结构化 Chunk 闭环，固定样本证明标题路径、页码引用和上下文扩展收益后，再决定是否引入文档结构图；未出现多文档多跳失败前不引入 Neo4j/GraphRAG。

## ADR-092：PDF 结构由版面证据确定性识别并显式进入 Chunk

- 背景：把每页包装为 `第 N 页` 虽可追溯，但会丢失真实章节、代码和表格边界，也无法让跨页正文继承上页主题。
- 决定：继续使用 Java/PDFBox，在通用页面分析中增加行坐标、字号、字重、等宽字体和视觉行分段证据；知识资料解析器过滤重复页眉页脚与独立页码，按字体层级和编号识别标题，按前缀、字体与多分段视觉行识别列表、代码和表格。标题栈跨页保留，无真实标题时才使用页码回退。
- 导入边界：文件提取器不持有或伪造业务来源，只输出结构块；控制器得到真实 `source` 后调用结构化导入或重建。Markdown 继续使用原标题解析器，不共享 PDF 启发式规则。
- 元数据：`page_number` 和 `block_type` 从 Section 贯穿 Chunk、Qdrant、检索响应、相邻上下文、回答 Prompt 与召回日志；旧向量缺少字段时兼容为无页码的正文块。
- 理由：该方案以低成本确定性证据提升可追溯性与检索解释力，不增加 OCR 服务、专用解析运行时或图数据库；固定样本和一次真实 Embedding 检索均可验证。
- 限制与回看：当前表格规则只覆盖单栏、连续多分段视觉行，双栏页不判表格以避免误报；复杂合并单元格、跨页表格和图片语义仍不支持。结构感知检索证明仅靠字段仍不足时，再评估章节聚合或轻量文档结构图。

## ADR-093：PDF 结构检索使用独立固定题和联合匹配指标

- 背景：生产检索已经返回标题路径、页码和内容块类型，但原 20 题只度量来源、排序、标题与拒答，无法发现“命中同一来源却返回错误页码或错误块类型”的退化。
- 决定：新增 3 道独立 `DOCUMENT_STRUCTURE` 题和一份两页合成 PDF。每个结构期望绑定来源、完整标题路径、页码与块类型；报告分别统计页码、块类型及四项联合召回。结构题不加入原回答评估，避免额外 Chat 调用。
- 边界：评估继续调用未经结构加权的原始向量检索，不改变生产排序，不把结构字段直接加权为得分。运行器沿用显式 Embedding 费用授权门禁，Mock 与解析测试只证明指标逻辑和语料结构。
- 回看条件：完成一次授权真实结构基线后，只有页码/块类型或联合召回出现稳定缺口，才单变量评估块类型权重或章节聚合；没有缺口时停止扩张，不进入文档结构图或 GraphRAG。

## ADR-094：按 Blog 风格同步 Lombok 与 OpenAPI，但保留 RAG 边界

- 背景：主项目广泛使用 Lombok 数据类、`@Slf4j` 和 Swagger 注释；RAG 当前虽已使用 MyBatis-Plus，但实体仍有大量手写访问器，Web 接口缺少统一可发现文档。
- 决定：持久化 Entity 采用 `@Data`、`@NoArgsConstructor`、`@AllArgsConstructor`；含日志类采用 `@Slf4j`；引入 Knife4j OpenAPI 3 并为 Controller、核心请求补充 `@Tag`、`@Operation`、`@Schema`。
- 注解版本：不同时保留 Swagger 2 的 `@Api/@ApiOperation/@ApiModel`。两套注解表达重复，当前 Spring Boot 3 + Springdoc 运行链路以 OpenAPI 3 的 `/v3/api-docs` 为准；Knife4j `/doc.html` 与是否使用 Swagger 2 注解无关。
- 保留边界：业务快照和只读响应继续使用 `record`；多实现继续由 `@Configuration + @Bean + @Profile` 装配；不引入 Blog 的全文请求/响应 AOP 日志，避免简历、回答、Prompt 和知识正文泄露；不为形式统一批量迁移 Mapper XML。
- 验收：编译通过，`/v3/api-docs` 契约测试通过；完整 storage 启动后的 `/doc.html` 浏览和生产依赖连通性仍需单独验证。

## ADR-095：结构检索基线无缺口，不增加结构加权

- 真实证据：在 9 份竞争语料下导入合成两页 PDF，执行 3 道独立结构题；6 个 PDF Chunk 成功写入并完成检索。来源命中率、Hit@1、Mean Recall@5、MRR、标题路径、页码、内容块类型和四字段联合结构召回均为 `1.0000`。
- 决定：保持当前未经结构加权的向量检索和现有生产排序，不增加块类型权重、章节聚合、轻量文档结构图或 GraphRAG。合成来源在基线完成后已从 MySQL/Qdrant 删除，结果保存在 `evaluation/results/2026-08-31-pdf-structure-retrieval-baseline.json`。
- 理由：固定样本没有证明标题、页码或块类型字段不足；新增排序逻辑会扩大复杂度和回归面，却没有当前质量收益证据。该结果只适用于合成结构题，不外推复杂表格、图片语义或 OCR。
- 回看条件：只有新增固定样本稳定出现同一结构字段漏召回，才重新设计单变量结构加权或章节聚合对照；未出现前不重复运行同一数据集寻找更高分。

## ADR-096：岗位匹配只消费已确认事实并独立记录元数据

- 背景：简历审计已经能够输出带逐字证据的确认事实，但用户还需要把这些事实与具体 JD 对照；直接把原始简历再次交给模型会扩大隐私范围，也会绕过审计的证据边界。
- 决定：新增 `JOB_MATCH_ADVISOR`，请求只接收目标岗位、岗位描述和确认事实。模型输出岗位原文引文、匹配状态和可选简历证据；Java 服务端逐字校验两类引文，`MISSING` 项禁止携带简历证据，不返回录用结论。
- 状态边界：`MATCHED` 表示直接支持，`PARTIAL` 表示部分支持，`NEEDS_VERIFICATION` 表示有相关证据但需要人工核对，`MISSING` 仅表示当前确认事实中没有支持证据，不表示候选人不会。
- 观测与数据：新增 `t_resume_job_match_request_log` 和迁移 `016_resume_job_match_request_log.sql`，只保存角色、Prompt/模型、token、耗时、状态和失败类型，不保存 JD、简历、证据或匹配正文。前端只在审计结果有效且 JD 未变更时展示结果，变更后标记待更新。
- 理由：该边界复用审计的证据验真和隐私原则，提供岗位匹配用户价值，同时避免建设通用招聘评分或跨会话候选人画像。

## ADR-097：岗位匹配先完成真实落库与单次模型验收

- 证据：在共享 MySQL 5.7.36 执行 `016_resume_job_match_request_log.sql` 后，`t_resume_job_match_request_log` 具备 12 个字段、请求 UUID 唯一键、状态/时间索引和创建时间索引，初始行数为 0。
- 真实结果：一次脱敏 `qwen3.7-plus` 调用返回 4 条要求，状态分布为 `MATCHED` 2、`PARTIAL` 1、`MISSING` 1；Java 服务端对岗位引文和非缺口简历证据逐字验真通过，`MISSING` 未携带简历证据。
- 决定：将岗位匹配视为已完成真实链路验证的可部署能力；不为同一 JD/事实样本重复付费调用，不因单次成功扩展招聘评分、跨岗位趋势或通用 Agent Runtime。
- 观测：日志查询只返回角色、Prompt、模型、token、耗时、状态和失败类型等元数据，未发现岗位描述、简历证据或匹配正文泄露。

## ADR-098：项目深挖采用确定性四维并隔离知识事实

- 背景：通用首轮出题依赖画像和 Chat，不能保证针对一个已确认项目稳定覆盖基础、取舍、故障和扩展，也无法阻止知识库资料被误解为候选人的项目经历。
- 决定：`project-deep-dive-v1` 只接受一条 `PROJECT` 类型的审计确认事实，由 Java 固定生成四类问题；每题保留同一条项目逐字证据和独立考察目标，不调用 Chat，不根据技术事实或知识正文补写项目内容。
- 知识边界：默认不检索。用户显式开启后，四类问题各自通过现有 `MarkdownSimilaritySearchService` 执行 `topK=3`、阈值 `0.60` 的只读检索，返回真实正文和来源用于答题参考；服务不写数据库、向量或简历事实。
- 理由：固定维度可用单元测试和接口契约直接验证，零 Chat 成本且不会引入模型方差；可选检索保留 RAG 的来源价值，同时把候选人事实与公共知识分开。
- 回看条件：下一步可以把四题作为显式项目深挖模式接入现有会话和证据化评分。只有固定题不能覆盖真实项目追问时，才基于失败样本评估有界 Chat 追问；此前不引入自由 Agent、图工作流或新持久化模型。

## ADR-099：项目深挖复用现有会话聚合并锁定四题上限

- 背景：项目深挖第一闭环已经能预览固定四题，但尚不能提交回答、获得证据化评分、生成报告或跨刷新恢复。另建会话表和评价器会复制已经验证的状态、乐观锁和证据验真逻辑。
- 决定：在 `t_interview_session` 增加 `session_mode`，取值为 `STANDARD` 或 `PROJECT_DEEP_DIVE`，历史行默认标准模式。深挖启动服务把确认项目事实构造为最小画像，将四题映射为现有 `InterviewQuestion`，并以 `maxQuestionCount=4` 进入同一个 `InterviewSessionService`。
- 追问边界：深挖回答仍由现有 `InterviewAnswerEvaluator` 评分，但题目数已等于上限，因此评价中的追问题目不会写入会话；第四题后按原逻辑确定性生成报告。知识来源继续绑定到当前题目并接受原来源一致性验真。
- 理由：显式模式足以让 API、持久化和前端区分训练类型，同时保留单行 JSON 聚合、乐观锁、复习任务和最近会话能力；不需要第二套表、Chat 出题、通用模式框架或 Agent Runtime。
- 部署边界：本 ADR 记录时迁移 `017_interview_session_mode.sql` 尚未执行；后续已在用户明确要求下于共享 MySQL 5.7.36 的独立库完成迁移和字段核验。只有真实失败样本证明固定四题不足时，才评估有界追问策略。

## ADR-100：验证服务于功能闭环，不作为开发主体

- 背景：项目已经具备多条 RAG、面试和 PDF 评估链路，若每轮继续扩大重复测试、审计和截图检查，容易挤占用户可调用功能的开发时间，也会把验证数量误当作产品进展。
- 决定：每轮自主开发必须先交付一个可调用功能、可运行链路或明确缺陷修复；测试、构建、浏览器检查和数据核验按改动风险选择最小必要范围，只覆盖当前闭环的关键边界、回归风险和部署事实。
- 边界：这不是取消测试。涉及持久化、迁移、并发、证据验真或用户流程时，仍保留能证明正确性的直接验证；但不为提高测试数量、重复同一结论或追求形式覆盖率而扩展本轮范围。
- 影响：开发记录必须把功能成果与验证证据分开陈述；没有功能进展的重复测试不能单独作为一轮开发收尾。

## ADR-101：以稳定 Spring AI 1.1.x 承载 RAG SSE，不提前引入图运行时

- 背景：项目已有同步 RAG 问答，用户需要更现代且可感知的交互体验，同时希望技术栈保持前沿；当前没有条件分支、checkpoint 或人工暂停等图工作流需求。
- 决定：Spring AI 升级到稳定 `1.1.8`，Spring AI Alibaba 升级到稳定 `1.1.2.3`，在现有 ChatClient、VectorStore 和结构化输出基础上新增 RAG SSE 流式入口。保留同步接口作为兼容路径。
- 实现边界：流式接口先完成检索和来源扩展，再转发 ChatClient `stream().content()` 的增量内容；最终事件统一返回可靠性和来源，日志只在结束或失败时记录一次。无可靠资料时不调用 Chat，直接返回拒答事件。
- 不采用：不因为版本更新或“前沿”标签加入 Spring AI Alibaba Graph、MCP、LangChain4j、Redis 或消息队列；只有真实出现分支、循环修正、HITL、checkpoint 或外部客户端复用需求时再评估。
- 验证边界：本轮只做 JDK 21 后端编译和前端类型/生产构建，未调用付费模型或外部向量服务；版本升级兼容性以当前源码编译通过为准，后续若使用新模块需单独验证。
- 兼容处理：Alibaba 新版本会自动发现多模态 Embedding 和 Video 配置；当前项目只使用文本 Embedding，因此在 `local`/`storage` profile 排除这两项自动配置，避免无 Key 启动失败且不改变现有模型能力。

## ADR-102：先用 Actuator + Spring AI Observation 建立单实例业务观测

- 背景：RAG、面试评分、复习助手和工具调用已有分散的请求日志与耗时字段，但缺少统一的运行状态和调用指标入口；当前项目仍是单体应用，没有跨服务 trace 或外部监控平台的部署前提。
- 决定：引入 Spring Boot Actuator，开放健康、信息和指标端点；复用 Spring AI 1.1.x 自带的 Chat/VectorStore Observation，以及 Spring Boot 的 HTTP/JVM 指标。指标统一使用 `application=java-interview-rag` 标签，方便本地与后续采集器区分。
- 隐私边界：关闭 Prompt、Chat 完成内容和 VectorStore 查询响应的日志观测；不开放环境、配置、Bean、线程转储等管理端点，不新建业务正文监控表。
- 不采用：暂不接入 Prometheus、OpenTelemetry Collector、Tempo、Jaeger 或云监控 exporter；没有跨服务部署和 trace 关联需求时，先保持零外部依赖的本地观测闭环。
- 回看条件：出现跨服务调用、需要按 requestId 串联检索/模型/工具节点，或需要长期告警与 P95 追踪时，再增加 Micrometer Tracing/OTel exporter，并同步定义高基数标签和脱敏策略。

## ADR-103：业务观测以低基数路由指标和只读概览交付

- 背景：Actuator 和 Spring AI Observation 能提供底层指标，但单看指标名称不方便定位当前项目的业务路由问题；直接把请求 ID、会话 ID 或正文放进标签又会造成高基数和隐私风险。
- 决定：用 Servlet Filter 统一处理 `/api` 请求，生成响应头 `X-Request-Id`，按 Spring MVC `BEST_MATCHING_PATTERN` 记录业务路由、结果类别和耗时；新增只读 `/api/observability/overview` 聚合当前进程的业务指标，并在 Vue 工作台提供手动刷新页面。
- 指标边界：请求标签只允许稳定路由模板和 `SUCCESS`/`CLIENT_ERROR`/`SERVER_ERROR`，不写入 URL 中的 UUID、问题、简历、回答、Prompt 或知识正文。SSE 请求在异步完成、超时或失败时结束计时。
- 理由：这是当前单体应用能够直接使用的故障定位闭环，能观察真实业务路由且无需数据库或外部监控基础设施；内存指标重启清零的限制对本地演示可接受。
- 不采用：不新增监控业务表，不建设自动轮询、告警中心、Prometheus/Grafana 或跨服务追踪；只有需要长期趋势、告警、跨服务定位时再引入持久化采集和 OTel exporter。

## ADR-104：角色对话先采用有界会话上下文与 SSE 阶段事件

- 背景：原正式面试回答是一次同步结构化评价，用户无法看到评价阶段，模型也只能看到当前题目和回答；直接引入 Graph 会同时带来状态图、checkpoint 和持久化复杂度，当前没有真实分支或人工暂停需求。
- 决定：在现有 `InterviewSessionService` 和 `InterviewAnswerEvaluator` 上增加上下文评价入口与 SSE 回合接口。上下文严格绑定当前会话，只保留最近 6 条回答的题目、最多 500 字摘要、评分和遗漏；原始简历、JD、跨会话内容和完整 Prompt 不进入上下文日志。
- 事件协议：阶段事件使用低基数类型 `ANSWER_SUBMITTED`、`EVALUATION_STARTED`、`EVALUATION_COMPLETED`、`FOLLOW_UP_GENERATED`、`SESSION_COMPLETED`，最终单独发送完整会话对象，避免前端解析未完成的结构化 JSON。
- 恢复边界：不增加消息表，`GET /events` 根据现有持久化回答重建时间线；这保证会话恢复可用，但历史事件的精确发生时间暂未持久化。
- 不采用：当前不引入 Graph Runtime、Spring AI Alibaba Graph、Redis、MQ、Temporal 或通用 Agent Memory。只有出现条件分支、修正循环、人工确认暂停或跨进程恢复需求时，才以同一事件协议评估 Graph checkpoint。

## ADR-105：解耦 storage profile 的 Chat 与 Embedding 凭据

- 背景：`storage` 原先让 OpenAI-compatible Chat 与 DashScope Embedding 共用 `JAVA_INTERVIEW_RAG_DASHSCOPE_API_KEY`。本轮真实演示中，临时为 Chat 切换独立兼容端点时会同时替换 Embedding 凭据，导致检索请求失败；两类服务本来就可以使用不同账号和端点。
- 决定：Chat 增加独立的 `JAVA_INTERVIEW_RAG_OPENAI_BASE_URL`、`JAVA_INTERVIEW_RAG_OPENAI_API_KEY` 和 `JAVA_INTERVIEW_RAG_OPENAI_CHAT_MODEL` 覆盖项；未提供时继续回退到原 DashScope Chat 配置，保持已有默认行为。DashScope Embedding 始终只读取 `JAVA_INTERVIEW_RAG_DASHSCOPE_API_KEY`。
- 影响：部署者可以单独为 Chat 配置兼容端点和密钥，不会改变已有 Qdrant 向量的 Embedding 模型或凭据；本轮未写入任何真实密钥。
- 验证边界：配置语义通过重新打包和 storage 启动确认；当前可用 Chat 账号/端点仍返回 HTTP `403`，因此没有把本轮结果写成新的真实回答质量基线。

## ADR-106：默认 Chat 模型切换为 qwen3.7-max-2026-06-08

- 背景：用户明确指定后续大模型调用使用 `qwen3.7-max-2026-06-08`；现有默认值仍为 `qwen3.7-plus`。
- 决定：将 `storage` profile 的默认 OpenAI-compatible Chat 模型切换为 `qwen3.7-max-2026-06-08`，Embedding 继续使用 `text-embedding-v3`，不重建现有向量。
- 覆盖规则：优先读取 `JAVA_INTERVIEW_RAG_OPENAI_CHAT_MODEL`，其次兼容旧变量 `JAVA_INTERVIEW_RAG_DASHSCOPE_CHAT_MODEL`，两者均未定义时使用新默认值。
- 真实验收：无 Chat 模型环境变量覆盖时启动临时 `storage` 实例，执行 1 次 HashMap RAG 问答；新默认模型返回 HTTP `200`、`grounded=true`，正确引用树化阈值 8 和最小容量 64。该结果只证明调用链可用，不替代固定评估集。
- 历史边界：既有 `qwen3.7-plus` 评估结果、日志样本和测试数据代表真实历史，不批量改写；后续若需要比较质量，应以新模型单独运行同一固定数据集并保存独立报告。
