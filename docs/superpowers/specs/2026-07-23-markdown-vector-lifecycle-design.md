# Markdown 向量替换与删除生命周期设计

## 目标

补齐阶段 2 中“同一逻辑来源的新版本替换旧向量”和“显式删除文档时同时清理向量与登记”的最小闭环。

本轮完成后：

- 同一来源首次导入继续写入当前版本的 chunk 向量。
- 同一来源导入新内容时，先写入新版本向量，再删除该来源下其他版本的向量。
- 历史上相同的“来源 + 版本”仍按重复导入处理，不重复调用 Embedding。
- 删除文档时，清理该来源的全部 Qdrant 向量和全部 MySQL 或内存版本登记。
- `local` profile 保持无外部向量依赖，但删除仍会清理进程内登记。

## 边界

本轮不增加手动重建、异步任务状态机、RAG 检索、前端资料管理页、collection 自动创建或新的 Maven 依赖。

版本表继续保存历史“来源 + 版本”登记，不增加“当前版本”字段。当前版本由 Qdrant 中该来源实际保留的唯一文档版本体现；如果以后需要版本审计、异步索引或批量恢复，再引入明确的文档状态模型。

逻辑来源按大小写敏感的精确字符串区分，并拒绝首尾空白。MySQL `source` 使用兼容当前 5.7.36 服务器和本地 8.0 的 `utf8mb4_bin`；删除 SQL 额外使用 `BINARY` 比较，避免关系登记与 Qdrant 元数据过滤产生不同的来源等价规则。

## 方案比较

### 方案一：先写新向量，再删除旧向量

导入器先登记新版本并完成解析、切分和向量写入，随后按来源和版本过滤删除旧向量。任一步骤失败时撤销本次新版本登记，稳定向量 ID 允许重试覆盖已写入的新点。

优点是新版本写入失败时旧资料仍然可用，且不需要新增表字段或事务协调器。缺点是 MySQL 与 Qdrant 仍不具备分布式事务，极端部分失败可能短暂同时保留两个版本，需通过同一导入重试收敛。

### 方案二：先删除旧向量，再写新向量

实现最直接，但新版本的 Embedding 或 Qdrant 写入失败会立即造成来源无可用向量，破坏现有可用性，因此不采用。

### 方案三：引入文档状态机

在 MySQL 中增加当前版本、`PENDING/SUCCESS/FAILED`、chunk 数量和错误信息，使用状态驱动写入、替换和恢复。这更适合异步任务与手动重建，但会同时扩大表结构、事务和恢复路径，超出本轮最小同步闭环，因此暂缓。

## 组件与契约

### `MarkdownChunkIndexer`

保留现有 `index(document, chunks)`，增加两个生命周期操作：

```java
void deleteOtherVersions(MarkdownDocument document);

void deleteBySource(String source);
```

接口提供默认空实现，使现有 lambda 形式的 `noOp()` 和 `local` profile 不连接 Qdrant。

`QdrantMarkdownChunkIndexer` 使用 Spring AI `FilterExpressionBuilder` 构造过滤条件：

- 替换：`source == document.source AND document_version != document.version`。
- 删除：`source == source`。

不自行拼接过滤表达式字符串，避免来源中的特殊字符改变过滤语义。

### `MarkdownImportRegistry`

保留单版本登记和失败撤销，增加：

```java
boolean unregisterBySource(String source);
```

内存实现删除相同来源的全部联合键；MySQL 实现执行按来源删除。返回值表示是否实际删除过登记，不把不存在视为异常。

### `MarkdownContentImporter`

新版本导入顺序固定为：

```text
登记新版本
→ 标题解析与切分
→ 写入新版本向量
→ 删除同来源其他版本向量
→ 返回成功
```

向量写入或旧版本清理抛出运行时异常时，撤销本次新版本登记并原样抛出；撤销异常继续作为 suppressed exception 保留。历史版本登记不删除，因此旧版本不会被重复向量化。

增加 `deleteBySource(source)`：先删除来源下全部向量，再删除来源下全部登记。Qdrant 删除失败时数据库登记保持不变，可以安全重试；若向量删除成功但数据库删除失败，再次调用删除仍是幂等操作。该顺序不能消除跨存储事务缺口，但不会把失败伪装为成功。

### HTTP 接口

在现有 `/api/knowledge/documents` 下增加：

```http
DELETE /api/knowledge/documents?source=java/basic.md
```

返回来源和是否删除过登记。使用查询参数承载逻辑来源，避免来源中的 `/` 与路径变量路由冲突。非法空白来源沿用现有 HTTP 400 中文错误响应。

## 失败语义

- 新版本向量写入失败：撤销新版本登记，保留旧版本向量，可原样重试。
- 旧版本向量清理失败：撤销新版本登记；可能已经写入的新版本使用稳定 ID，重试会覆盖并再次清理旧版本。
- 显式删除的 Qdrant 操作失败：不删除版本登记，调用方收到异常并可重试。
- 显式删除的 MySQL 操作失败：Qdrant 删除已完成但接口仍失败；再次删除会重复执行幂等向量清理并重试数据库删除。
- 删除不存在的来源：向量删除按幂等操作执行，登记删除返回 `false`。

## 验证策略

- 导入器测试覆盖新版本写入后调用旧版本清理，以及清理失败时撤销新登记并允许重试。
- 登记器测试覆盖内存和 MySQL 的按来源批量删除。
- 来源测试覆盖首尾空白拒绝、大小写变体独立登记和 MySQL 精确删除语句。
- Qdrant 索引器测试捕获结构化过滤表达式，验证替换条件和来源删除条件。
- Web 测试覆盖 DELETE 参数传递、响应形状和空白来源 400。
- 只执行直接相关的后端测试与 Maven 打包验证；本轮没有前端改动，不运行前端或浏览器测试。
- 在服务器 `storage` profile 下使用唯一来源真实验证两个版本替换和删除，随后确认 MySQL 与 Qdrant 均无残留测试数据。
