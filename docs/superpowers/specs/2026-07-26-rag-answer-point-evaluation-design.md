# RAG 回答要点对比设计

## 目标

在现有固定题集与 `RagAnswerService` 之上建立第一版批量回答评估：逐题生成真实 RAG 回答，比较期望来源和预期回答要点，并返回可审查的结构化报告。

## 方案选择

第一版使用“标准化字面包含”判断要点是否命中：回答与要点统一转为小写并移除空白、标点等非字母数字字符，再判断回答是否包含完整要点。报告固定返回匹配方法标识，避免把字面覆盖率误写成语义正确率。

未采用额外模型裁判。模型裁判会让每道题再增加一次调用费用，并引入不可重复的评分偏差；当前 6 道题的要点来自仓库内固定语料，先建立确定、可单测的基线更符合阶段 4 目标。

## 接口与数据流

- `POST /api/knowledge/evaluations/answers` 仅在 `storage` profile 暴露。
- 服务依次读取固定题集并调用现有 `RagAnswerService.answer(question)`。
- 每题返回回答、可靠依据标记、实际来源元数据、期望来源是否命中、命中与未命中要点及覆盖率。
- 汇总返回题目数、可靠回答数、来源命中数、要点总数、要点命中数和总体覆盖率。
- 复用回答服务意味着每题继续写入现有召回日志；任一模型调用失败时保持现有异常语义并终止本次批量请求。

## 边界

- 不修改现有回答 Prompt、检索参数、题集、数据库结构或前端。
- 不保存批量评估报告，不增加模型裁判、语义相似度或人工阈值。
- 字面匹配不能识别同义改写，结果只作为可重复基线，不能等同于语义正确率。
- 本轮不主动执行真实批量接口，避免未经确认产生 6 次 Chat 调用费用。

## 验证

- 服务测试覆盖大小写、空白和标点归一化、部分要点命中、来源命中与汇总指标。
- 控制器测试覆盖 `POST` 路由和结构化 JSON 字段。
- 执行回答评估、现有检索评估与回答服务的直接相关测试。
