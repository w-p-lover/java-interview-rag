# 技术方案

## 当前原则

- 采用单体 Spring Boot 应用逐步演进。
- 后端以 Java 17 为主，构建工具使用 Maven。
- 当前基线使用 Spring Boot 3.5.16，并通过 Maven Wrapper 3.9.14 固定构建工具版本。
- HTTP 层使用 Spring MVC，独立项目开发端口为 `18080`。
- 前端使用 Vue 3、Vite、TypeScript、Vue Router、Axios 和 Sass，位于仓库内独立的 `frontend/` 子目录。
- 大模型应用优先使用 Spring AI。
- 关系数据库使用 MySQL，连接池使用 Druid，数据访问使用 MyBatis-Plus；本地 Compose 固定 MySQL 8，当前共享服务器实际为 5.7.36，仓库 SQL 保持 5.7/8 兼容。文档来源、内容版本、召回日志和评估输入均已形成独立边界，向量生命周期与评估结果通过固定接口验证。
- 向量数据库使用 Qdrant；仓库 Compose 固定 `qdrant/qdrant:v1.10.1`，共享 storage 服务当前为 1.17.1，客户端兼容性告警仍单独记录。Embedding 使用 DashScope `text-embedding-v3`，`storage` profile 支持首次导入、重建和来源删除时的 chunk 批量向量写入。
- 检索采用双通道：Qdrant Dense 相似度检索与嵌入式 Lucene 9.12.1 BM25 稀疏检索并行维护；Hybrid-RRF v1 按 `source + documentVersion + chunkOrder` 去重后以 `1 / (60 + rank)` 融合。RAG storage 主链路默认使用 Hybrid，面试出题和历史 Dense 评估保持原 Dense 语义。
- 知识资料支持 Markdown 与文本型 PDF；PDF 复用版面感知的 PDFBox 页面分析，并根据字号、字重、字体、视觉行和页面位置识别章节、正文、列表、代码与表格块，扫描页只作为 OCR 候选告警，不在本阶段自动 OCR。

## 核心数据流

### 产品主线

```text
求职方向与目标岗位
→ 简历解析与候选人画像
→ 简历、岗位描述和面试资料检索
→ 模拟面试与动态追问
→ 结构化评分与薄弱项
→ 错题和复习计划
```

### 面试准备画像

用户侧面试能力不复用内部 `FixedRagEvaluationDataset`。`POST /api/interviews/preparations` 接收目标岗位、简历文本和可选岗位描述，在 `storage` profile 下复用现有 ChatClient，通过一次结构化输出生成候选人摘要、简历证据、岗位要求和面试关注领域。服务端保留请求中的目标岗位并记录 `interview-preparation-v1` Prompt 版本；输入资料只作为事实，不允许模型推断未提供的经历，也不在画像阶段生成题目和评分。

第一版不保存简历、岗位描述或画像，不调用 Qdrant，不建立确认状态机。响应是后续用户确认与生成面试题的草稿边界；题目生成必须在后续结合知识来源和考察目标单独实现。

`/interview` 使用独立的 `InterviewTextFileField` 与 `interviewDocumentText` 读取 `.pdf`、`.md`、`.markdown` 与 `.txt`，校验空正文和字符上限后填入现有字符串请求。Markdown/TXT 使用浏览器 `File.text()`；PDF 通过 `POST /api/interviews/documents/extract` 在后端由 PDFBox `3.0.5` 一次加载，逐页收集文本坐标和实际绘制图像，重建文本行，并只在中间 gutter、双侧连续正文宽度和垂直重叠都满足门槛时按左栏后右栏重排。响应除正文和页数外返回文档/页面类型、双栏调整页数、OCR 候选页、告警和逐页摘要。整份无文本继续返回 400；混合 PDF 保留已提取正文并要求用户检查指定图像页。服务不保存原文件、不写数据库、知识库、向量库或 localStorage，也不自动调用 OCR。简历与 JD 不经过知识库导入，不执行版本登记、切分或向量化，文本框继续作为可检查、可编辑的备用输入。DOCX 在具备可靠解析前不开放。

### 简历证据审计官

`POST /api/interviews/resume-audits` 复用同样的 `resumeText` 字符串输入，通过普通 Spring AI Structured Output 一次生成事实、信息缺失、风险判断和表达建议。`resume-evidence-audit-v4` 将事实类型固定为教育、任职、项目、技术、职责、时间和结果，并要求模型先按原文顺序逐段扫描，把学校/专业/学历、公司/职位、项目/职责/技术/结果分别作为原子事实；项目只承载项目或系统名称，技术只承载技术及明确使用事实，职责承载个人动作，结果承载可核验结果；同一句可以拆出技术和职责事实。每条确认事实必须携带模型从简历逐字复制的短证据，Java 服务端只接受隔离后原始简历中完整包含的引文。模型返回空结果或任一事实引文无效时整次审计失败，不把未验真的内容降级为事实。事实仍最多 30 条，超量时优先保留每个项目的名称、个人职责和量化结果，再保留教育/任职主体、核心技术和时间；未达到上限时不得提前停止，输出前必须按原文顺序做完整性自检。若隔离后的输入仅是一行 `技能`、`专业技能` 或 `技术栈` 清单，且模型没有指出技能使用场景缺失，Java 会确定性补充一条“缺少具体项目使用场景或实践证据”；该规则不处理多段简历中的技能与项目语义关联。

岗位匹配顾问 `POST /api/interviews/job-matches` 只接收目标岗位、岗位描述和已经通过审计的确认事实，不接收原始简历。`job-match-v1` 要求模型为每条重要岗位要求返回岗位原文引文、`MATCHED`/`PARTIAL`/`MISSING`/`NEEDS_VERIFICATION` 状态、可选的已确认简历引文和解释；Java 服务端逐字校验岗位引文属于 JD，非缺口项的简历引文必须完整等于某条已确认事实证据，缺口项禁止携带简历证据。该接口不输出录用判断，不把“没有已确认证据”解释为候选人不会，最多返回 30 条要求。每次通过输入校验的请求记录独立脱敏日志，包含角色、Prompt/模型版本、token、耗时、状态和失败类型；`GET /api/interviews/job-matches/requests` 不返回 JD、简历证据或匹配正文。部署前需执行 `016_resume_job_match_request_log.sql`。

服务在模型调用前按行隔离“忽略之前规则”、伪造 `resume_data` 边界等强提示注入特征，隔离行不进入模型输入，也不能成为事实证据；响应只增加隔离行数风险，不回显被隔离正文。该规则是保守的确定性防线，不能证明覆盖所有自然语言提示注入，也不能仅凭字面包含证明事实描述的语义准确性，后续固定评估必须继续度量事实准确率和虚构率。

每次通过输入校验的审计生成请求 UUID。`t_resume_evidence_audit_request_log` 只记录角色名、Prompt/模型版本、状态、token、耗时、异常类型和时间，不保存简历、完整 Prompt、事实、风险或建议正文；日志写入失败只告警，不改变审计结果。`GET /api/interviews/resume-audits/requests?limit=20` 返回最近 1 到 100 条脱敏元数据。部署前需执行 `015_resume_evidence_audit_request_log.sql`。

`POST /api/interviews/evaluations/resume-audits` 依次执行完整简历、缺少量化结果、时间冲突、技能堆砌、项目空泛、提示注入、教育/任职分类、项目职责边界和多段容量九类样本。`resume-evidence-audit-dataset-v6` 共包含 64 条预期原子事实；教育/任职样本只保留用户简历中与分类直接相关的学校、专业、公司、职位和日期字段，不保存联系方式、职责正文或完整简历，其他样本使用合成主体。全部原子事实保存类型与短证据，并为信息缺失和风险保存有限同义信号；同类型事实先精确匹配证据，再允许预期短证据与模型较长逐字证据互相包含。响应除整体指标外按七种事实类型返回准确率、召回率和未匹配计数，并返回 30 条上限、最大候选事实数与触顶样本数；逐样本指标同样不含正文。

评估使用确定性集合比较：事实准确率为“匹配预期标签的确认事实 / 全部确认事实”，预期事实召回率单独衡量遗漏；虚构率为未匹配预期标签的确认事实占比；证据合法率按模型候选事实统计 Java 字面校验通过比例；信息缺失和风险信号使用固定同义词组召回。结构解析成功与完整审计成功分开计算，避免把“结构已解析但证据校验失败”误记为解析失败。报告记录平均模型调用次数、token、平均耗时和 P95；未配置可核对的模型单价时 `estimatedCostCny` 保持 `null`，不伪造费用。该接口当前会产生九次 Chat 调用，Python 运行器必须显式提供 `--allow-chat-calls` 才会在网络请求前放行。

2026-08-26 在明确费用授权下执行两轮共 18 次 `qwen3.7-plus` Chat。`dataset-v5` 第一轮的两条“标签外事实”都能在固定输入中逐字证明，分别是项目空泛样本的职责和提示注入样本的项目名称，因此 v5 只作为评估标签校准证据；补齐标签后的 `dataset-v6` 是当前正式基线：9/9 审计与结构成功，事实准确率、证据合法率、信息缺失识别率和风险召回率均为 `1.0000`，虚构率 `0`，事实召回率 `0.9219`，严格通过 `8/9`，最大候选事实数 `25/30`。职责、项目、技术、时间和结果事实召回率均为 `1.0000`；教育/任职样本本轮只命中 `6/11`，而同一 Prompt 的 v5 第一轮为 `11/11`，说明单样本召回存在模型波动，不能把“已确认事实”表述为完整简历解析。

`/interview` 在简历材料后以内联面板接入该接口，结果只保存在 composable 的页面内存中，不写 localStorage、全局状态或业务表。检查是可选步骤：检查中暂时禁用简历修改和开始面试；检查失败会显示服务端错误但不阻止用户直接开始；简历修改后旧结果标记为待更新，仍保留供人工对照。前端只展示确认事实及逐字证据，并把待补信息、人工核对和修改建议分开，不把未出现的事实解释为候选人不会。

### 首轮面试题与知识来源

调用方确认画像后，通过 `POST /api/interviews/questions` 提交目标岗位、完整画像和 3 到 8 的题数。`InterviewQuestionGenerationService` 复用现有 ChatClient，以 `interview-question-v1` 一次生成指定数量的结构化题目；每题包含题目文本、考察目标、画像依据类型和独立知识检索查询。模型返回数量必须与请求一致，依据类型必须属于画像关注领域已经出现的 `TARGET_ROLE`、`RESUME`、`JOB_DESCRIPTION`，否则明确失败。

题目生成后，服务逐题复用 `MarkdownSimilaritySearchService`，固定使用 `topK=3`、相似度阈值 `0.60`。最终结果返回 `knowledgeGrounded` 和实际 `MarkdownSearchResult`；没有可靠命中时保留由画像支撑的题目，但返回空知识来源，不伪造引用。该接口不读取 `FixedRagEvaluationDataset`，不生成参考答案、评分或追问，也不保存画像和题目。

### 文本面试会话

`POST /api/interviews/sessions/start` 依次调用画像、首轮出题和会话创建服务，默认生成 5 道首轮题并允许整场最多 8 道；初始题数可配置为 3 到 8，整场上限可配置到 12。`POST /api/interviews/sessions` 继续支持保存调用方已经确认的画像和题目；`GET /api/interviews/sessions/{sessionId}` 恢复完整快照。

`POST /api/interviews/sessions/{sessionId}/answers` 必须同时提交当前题号、期望版本和回答。服务在模型调用前校验题号与版本，避免延迟重试被误当作下一题；更新 SQL 同时匹配会话 ID、旧版本和 `IN_PROGRESS` 状态，影响行数为 0 时返回冲突。会话固定按题号顺序推进，不支持跳题或修改历史回答。

`InterviewAnswerEvaluationService` 一次结构化模型调用返回技术、完整性、表达三项分数、优点、遗漏、改进建议、可选追问，以及回答原文和知识资料的候选引文。综合分由服务端确定性计算，知识可靠状态来自题目实际 chunk 而不是模型自报。服务端要求 1 到 3 条回答引文逐字属于当前回答；有可靠资料时要求至少一条知识引文，并将模型的 1-based 来源序号映射为完整来源元数据后校验引文属于对应 chunk；无可靠资料时拒绝任何知识引文。只有通过验真的证据才随评价 JSON 快照持久化，旧快照缺失证据字段时恢复为空列表。可选追问使用独立查询按 `topK=3`、阈值 `0.60` 绑定真实来源并追加到队列；完全重复或达到整场上限时不追加。模型要求追问但遗漏独立检索查询时，以追问题目本身作为查询，避免可选追问字段使已经有效的主评价整体失败。当前队列答完即完成会话，并从持久化逐题评价确定性生成平均分与汇总优缺点。

MySQL 表 `t_interview_session` 使用 `MEDIUMTEXT` 保存画像、动态题目、带评价回答和最终报告 JSON 快照，独立保存题数上限、当前题号、状态、乐观锁版本和时间。当前不保存原始完整简历和 JD，不实现用户归属、改答案或跳题。

`/interview` 的最近会话入口不新增全量查询接口。`useInterviewSession` 在 `localStorage` 中维护最多 8 个由当前浏览器创建或成功恢复的会话 UUID，并继续以 `GET /api/interviews/sessions/{sessionId}` 逐项读取服务端快照；创建、回答和恢复成功后把会话移到索引首位。404 表示服务端事实已不存在，会同时淘汰最近索引和匹配的当前会话 ID；连接失败、超时或 5xx 只显示部分读取失败，不删除 UUID。浏览器索引不保存岗位、简历、回答、评分、报告或知识正文。没有用户身份和数据归属前，不开放数据库全量会话列表，避免把其他会话暴露为公共历史记录。

### 错题沉淀与复习任务

`POST /api/interviews/sessions/{sessionId}/review-tasks` 只接受已完成会话。`InterviewReviewTaskService` 逐题读取已经保存的评价，跳过 `gaps` 为空的回答，其余每题生成一条 `PENDING` 任务；该过程不重新调用模型，不按任意分数阈值猜测错题。`GET` 同路径查询已经生成的任务，支持可选 `status`、`plannedDateFrom` 与 `plannedDateTo`，所有读取仍限制在路径中的单个会话。

MySQL 表 `t_interview_review_task` 以确定性 UUID 为主键，并以“会话 ID + 原题号”建立唯一键；重复生成通过 `INSERT ... ON DUPLICATE KEY` 保持幂等，部分写入失败后可以安全重试。任务保存题目、考察目标、遗漏项、改进建议及来源、文档版本、chunk 顺序、标题路径和相似度，不复制 chunk 正文。`PATCH /api/interviews/sessions/{sessionId}/review-tasks/{taskId}/complete` 使用会话与任务联合条件把状态单向更新为 `COMPLETED`，并通过 `COALESCE(completed_at, ...)` 保留首次完成时间；`PATCH .../{taskId}/schedule` 设置或清除可空 `planned_review_date`。`006`、`007` 与 `011` 均已在 MySQL 5.7.36 执行，真实验证覆盖生成幂等、跨重启查询、重复完成不覆盖时间及计划日期索引结构。当前不实现任务重开、提醒、跨会话查询或写入型 Agent 工具调用。

前端由 `useInterviewSession` 统一持有复习任务、查询条件、加载状态和独立错误状态。最后一题提交后若会话转为 `COMPLETED`，调用 `POST` 生成并展示任务；刷新恢复已完成会话时只调用 `GET`，避免页面恢复产生重复写请求。完成、筛选和计划日期更新均由组合式函数请求服务端；操作成功后按当前筛选重新读取列表，失败时保留原列表和原筛选。`InterviewReviewTaskPanel` 组合纯筛选与日期控件，只展示数据并发出 typed 事件，不展示 chunk 正文，也不自行发请求。

`GET /api/interviews/sessions/{sessionId}/review-tasks/history` 在单个会话边界内读取任务和已持久化 attempt，按题返回完整时间线、正式/首次/最近/最好分数和最近一次评价的遗漏，并汇总已练题数、总 attempt 数与最近分数高于正式回答的任务数。未作答任务保留原任务遗漏但不伪造复习分数。前端恢复任务和提交 attempt 后均重新读取该接口，以服务端事实更新概览和时间线，不在浏览器临时计算历史指标。

最小 Tool Calling 从只读、可验证的复习事实开始。`InterviewReviewTools` 使用 Spring AI `@Tool` 暴露 `list_review_tasks`，参数仍限定为单个 `sessionId`、可选状态和计划日期范围，内部复用 `InterviewReviewTaskService` 的会话边界、状态校验和日期范围校验；返回值只包含任务摘要、遗漏、改进建议和知识来源元数据，不包含候选人回答正文或 chunk 正文。`POST /api/interviews/review-assistant` 的顶层 `sessionId` 是本次请求的可信会话来源，助手服务把它写入模型不可见的 `InterviewAssistantRequestContext`；三个工具在访问业务服务前都要求模型参数与该作用域一致，缺少上下文或会话不匹配时记录失败并拒绝执行。`storage` profile 通过 `MethodToolCallbackProvider` 显式注册工具回调，避免只有工具类但没有 Spring AI 工具入口。

第三个工具 `get_review_progress` 直接复用 `InterviewReviewTaskService.findAttemptHistory(sessionId)`，不建立第二套进度算法。工具汇总任务总数、已练题数、总 attempt 数、提升题数和仍有遗漏的题数，并逐题映射正式/最近/最好分数、相对正式回答分差、最近未解决遗漏和最近练习时间。未练习任务保留空分数，不描述为退步；返回结构不包含正式回答、复习回答、attempt 对象或知识正文。

完成页在复盘成功后使用同一份 `InterviewReviewSessionHistory` 派生下一道练习题，不从模型自然语言中抽取任务标识。候选范围限定为当前筛选可见且仍有遗漏的任务，先选择未练习题，再按最近分数或正式回答分数升序、原题顺序稳定排序；入口只定位到已有再次作答文本框。attempt 提交后仍由现有会话 composable 重新读取持久化历史，用户显式点击“刷新本场复盘”后才再次调用模型，避免隐藏费用和第二套学习状态。

工具入口为每次具有有效会话 ID 的调用生成执行 UUID，并把工具名、会话 ID、成功/失败、成功结果数量、耗时、异常类型和创建时间写入 `t_interview_tool_execution_log`；不保存工具参数 JSON、返回正文或异常消息。日志写入异常只告警，不能覆盖原工具结果或业务异常。`GET /api/interviews/sessions/{sessionId}/tool-executions?limit=20` 只按路径中的单个会话查询最近 1 到 100 条记录。`012_interview_tool_execution_log.sql` 已在独立 MySQL 5.7.36 数据库执行。

写入工具 `schedule_review_task` 只允许为明确的 `sessionId + taskId` 设置明确的 `yyyy-MM-dd` 日期，内部复用 `InterviewReviewTaskService.schedule` 的会话存在性、任务归属和幂等覆盖语义；第一版不允许清空日期，也不暴露完成任务或提交回答。`POST /api/interviews/review-assistant` 使用独立系统提示并只绑定 `list_review_tasks`、`get_review_progress` 与 `schedule_review_task`；任务清单、进展复盘和改期分别路由到明确工具。改期请求还必须携带结构化 `scheduleConfirmation`，只读复盘无需确认。助手服务先校验确认会话与顶层 `sessionId` 一致，再将会话作用域和确认对象放入模型不可见的 `ToolContext`；工具调用前先校验当前会话，再精确比较确认与实际 `sessionId + taskId + plannedReviewDate`，缺失或任一参数不一致都拒绝写入并记录失败工具执行。确认只在单次请求内有效，不落库、不建立对话历史或通用审批状态。真实 `qwen3.7-plus` 验证中，查询与改期分别只执行一次对应工具，日期真实写入后清理合成数据；`get_review_progress` 也已使用一组脱敏持久化会话完成真实验证，模型正确区分已提升任务和未练习任务，请求与工具日志通过同一 `requestId` 关联，合成数据和日志随后精确清理。

复习助手请求级可观测性由 `t_interview_assistant_request_log` 记录，每次通过参数校验的助手请求生成 UUID 并通过 Spring AI `toolContext` 传给工具方法；工具日志的 `assistant_request_id` 可为空，以记录缺少助手上下文的失败调用。请求日志保存模型、状态、工具进入次数、累计 token、总耗时、最终响应是否存在、异常类型和创建时间；不保存用户消息、助手回答、工具参数、工具结果正文或异常消息。`GET /api/interviews/review-assistant/requests?limit=20` 返回最近 1 到 100 条请求日志。当前 Spring AI `1.1.8` 的 `OpenAiChatModel` 在工具调用后继续模型请求，并通过累计 usage 记录整次助手请求 token；provider/model 回合数没有公开业务接口，本项目不推算。`013_interview_assistant_request_observability.sql` 已在独立 MySQL 5.7.36 数据库执行。

模型重试复用 `OpenAiChatModel` 内部的 `RetryTemplate`，不在 `InterviewReviewAssistantService` 或 Controller 外层重放完整请求。项目当前将模型 HTTP 回合最多收敛为 2 次（首次加一次重试），固定退避 500ms；仅连接失败、连接/读取超时、HTTP 429 和 5xx 进入重试，其他 4xx、业务异常、空回答和工具异常直接失败。工具执行发生在模型 HTTP 响应之后，后续模型 HTTP 失败也只重试该 HTTP 回合，不重新进入已经完成的工具调用。

### 资料与 RAG 主线

```text
Markdown 文件或文本型 PDF 上传内容
→ Spring MVC 导入接口
→ 解析标题、页面与正文
→ 生成文档版本和 chunk
→ Embedding
→ 向量入库
→ 用户问题向量化
→ 相似度召回
→ 上下文拼接
→ 模型回答
→ 返回来源
→ 保存召回与评估结果
```

PDF 知识资料沿用现有版本登记和 Chunk 索引链路，但不再把整页正文交给 Markdown 标题解析器。PDFBox 行级证据先过滤重复页眉页脚和独立页码，再识别章节标题、正文、列表、等宽代码和多视觉分段表格；真实章节跨页继承，无可识别标题时才按页回退。结构化 Section 在真实逻辑来源确定后进入导入或重建，Chunk 与 Qdrant 保存 `page_number` 和 `block_type`，检索响应和回答上下文继续携带这些字段。原始 PDF 不写入数据库或向量库，混合/扫描页面会返回告警或拒绝空文档。

### 固定评估基线

阶段 4 以内置只读题集维护稳定的评估输入。20 道通用题包含唯一标识、问题、期望逻辑来源、完整标题路径和预期回答要点，通过 `GET /api/knowledge/evaluation-cases` 提供；独立的 3 道 PDF 结构题还包含期望页码与内容块类型，通过 `/api/knowledge/evaluation-cases/structure` 提供。题集查询本身不依赖 MySQL、Qdrant 或模型调用。`GET /api/knowledge/evaluations/retrieval` 固定以 `topK=5`、相似度阈值 `0.0` 计算来源排序、标题路径和拒答指标；`/structure` 在相同检索口径下增加页码、块类型及“来源 + 标题路径 + 页码 + 块类型”联合召回，不改变生产排序。`POST /api/knowledge/evaluations/answers` 仍只执行原 20 题，避免结构检索验证扩大 Chat 调用；匹配方法 `normalized-literal-containment-v1` 只衡量完整要点字面覆盖，不代表语义正确率。当前不保存评估历史。

### 资料库检索与问答入口

Vue `/answer` 通过 `answerKnowledgeQuestion` 调用现有 `POST /api/knowledge/answer`，不复制检索、可靠阈值或 Prompt 规则。`useKnowledgeAnswer` 只管理当前问题、提交中的问题、加载、错误和单次结果；新问题开始时清除旧结果，避免接口失败后仍把上一题答案显示为当前结果。浏览器入口将问题限制为 2000 字符，并为模型请求使用 60 秒超时，但服务端仍负责空问题等最终校验。

页面将 `grounded` 映射为“资料已支撑/资料不足”，回答正文按纯文本展示，不执行模型返回的 HTML。来源保持后端顺序，与回答中的 `[资料 N]` 编号一致；默认展示来源、标题路径和相似度，展开后显示文档版本、chunk 顺序与原始正文。第一版保持单次无状态问答，不在浏览器或数据库新增聊天历史；出现明确的连续追问需求和用户归属后，再设计会话持久化与上下文裁剪。

同一路由的“查资料”模式通过 `searchKnowledge` 复用现有 `GET /api/knowledge/search`，固定使用后端既有 `topK=5`、相似度阈值 `0.0` 语义，按服务端顺序展示相关 chunk，不调用 Chat 模型。`useKnowledgeSearch` 与问答状态隔离，新检索开始时清除旧结果，空结果和请求错误分别展示；浏览器不持久化检索词或结果正文，也不把相似度结果解释为可靠回答。章节树的“查资料”命令将根标题到当前标题按空格连接为确定性检索草稿，切换模式并聚焦输入框，不自动请求；现有接口仍在全资料库检索，不将该入口描述为当前来源或当前 Chunk 过滤。检索成功且存在命中时，结果面板可以把响应中的归一化 `query` 作为问答草稿交给父视图；父视图清除旧问答结果、预填问题并切换模式，但必须由用户编辑或确认后显式提交，不从来源正文或模型文本生成动作，也不自动产生 Chat 调用。

## 工程边界

- 文档元数据和向量记录必须可关联、可更新、可删除。
- 生成答案必须附带实际召回来源。
- 知识不足时明确兜底，不让模型伪造来源。
- 检索参数和 Prompt 变更应能够通过固定评估集比较效果。
- 新基础设施在需求出现后引入，不预先堆叠 Redis、MQ、Elasticsearch 或微服务。
- 默认 `local` profile 使用进程内登记器；`storage` profile 使用独立 MySQL 数据库 `java_interview_rag` 和 Qdrant collection `java-interview-rag-chunks`。
- `storage` profile 为每个 chunk 写入来源、文档版本、chunk/section 顺序、标题级别和标题路径；向量 ID 由“来源 + 文档版本 + chunk 顺序”稳定生成，重复重试不会生成另一批点。
- 同一文档的向量写入按原 chunk 顺序拆为每批最多 10 条，匹配当前 DashScope `text-embedding-v3` 服务端批量上限；某批失败时继续沿用现有登记撤销与稳定 ID 重试语义，不增加异步任务或额外状态。
- 导入先解析 Markdown/PDF、切片并构建无正文章节目录，再以“来源 + 版本”登记；重复版本在 Embedding 和 Qdrant 前短路，但仍承担本地解析成本。新版本写入 Qdrant 或 Lucene 失败时，Composite 会继续在两个索引中按精确 `source + documentVersion` 删除本次版本，再撤销 MySQL 登记并恢复上一当前版本；补偿失败作为 suppressed exception 保留，重传仍可依靠稳定 ID 收敛。新版本已完整写入但清理旧版本失败时不回滚新版本和登记，状态标记为 `FAILED`；调用方重传同一当前版本只幂等重试两个索引的旧版本清理，不重复 Embedding，成功后恢复 `READY`。跨 MySQL、Qdrant 与 Lucene 仍不具备分布式事务，进程重启会丢失内存状态，后续需要持久化状态或巡检入口。
- 同一来源的新版本先完成 Qdrant 与 Lucene 写入，再按 `source` 相等且 `document_version` 不等于新版本的条件删除旧索引；清理失败时保留新版本登记并标记 `FAILED`，同版本重传只重试旧版本清理，避免重复 Embedding 或误删已经完整写入的新版本。
- 版本表保留历史“来源 + 版本”登记，避免历史版本被重复向量化；显式 `DELETE /api/knowledge/documents?source=...` 先删除来源下全部向量，再删除全部历史登记，使删除后的任意历史版本可以重新导入。
- `GET /api/knowledge/documents` 只读返回每个逻辑来源当前登记的版本、内容字符数和登记时间。MySQL 以同一大小写敏感来源的最大登记 ID 作为当前版本；进程内登记器显式维护当前键，并在新版本写入失败撤销登记时恢复上一版本。接口不查询 Qdrant，不返回历史版本或 Markdown 正文。
- `GET /api/knowledge/documents/detail?source=...` 按大小写敏感来源返回当前版本、当前章节目录和按登记 ID 从新到旧排列的历史版本。章节目录由 `headingLevel`、`headingPath`、`sectionOrder` 和 `chunkOrder` 确定性构建，只保存标题、层级、首个直属 chunk 顺序、直属 chunk 数与子节点；标题前导正文不成为目录节点，空正文标题允许没有直属 chunk。详情只读取版本登记，不查询 Qdrant、不返回 Markdown 正文或索引健康状态。
- `t_knowledge_document_version.outline_json` 是可空 `MEDIUMTEXT`，通过 `014_knowledge_document_outline.sql` 增加。新导入原子保存目录快照；迁移前旧行保持 `null`，接口不伪造目录。历史版本详情仍只返回版本元数据，当前不提供历史章节预览。
- 手动 `POST /api/knowledge/documents/rebuild` 要求调用方重传来源和 UTF-8 Markdown 文件，只允许当前登记的精确“来源 + 版本”；历史登记不能直接重建，否则会删除当前版本向量却不改变目录当前版本。当前版本表不保存原始正文；向量重建成功后才更新同一登记的目录快照，向量失败时保留原目录，外部服务失败后可以用同一请求重试。
- Qdrant 重建非空文档时先用稳定 ID 写入或覆盖预期 chunk，再删除同来源其他版本，最后删除同来源同版本中 `chunk_order` 大于等于当前 chunk 数量的残留点；空文档直接清理该来源全部向量。
- 逻辑来源使用大小写敏感的精确字符串语义并拒绝首尾空白；MySQL `source` 列使用 5.7/8 均支持的 `utf8mb4_bin`，删除 SQL 使用 `BINARY` 比较，确保与 Java 字符串和 Qdrant 元数据过滤的来源边界一致。
- 私有连接信息通过 `.env` 或 `config/application-private.yml` 注入，环境变量统一使用 `JAVA_INTERVIEW_RAG_` 前缀。
- 服务器部署时只读导入 `D:/IdeaProjects/blog/blog-springboot/.env`，复用其中的 MySQL 主机、端口、账号、密码、Qdrant 地址和 DashScope Key；数据库名和 collection 名不复用主项目值，分别强制为 `java_interview_rag` 与 `java-interview-rag-chunks`。
- Qdrant 探测失败只告警不阻塞启动；MySQL 是 `storage` profile 的必要依赖。当前不自动创建 collection。
- `storage` profile 的 Chat 使用阿里百炼官方 OpenAI 兼容端点，并手动创建 `ChatModel`，默认模型为 `qwen3.8-max-0902`、温度为 `0.2`；原生 DashScope 客户端只承担 `text-embedding-v3`。全局禁用 OpenAI 自动配置，避免本地私有 profile 覆盖 YAML 排除列表后意外装配无关音频模型。回答服务固定使用 Hybrid 检索，Dense 可靠性仍按余弦阈值 `0.60` 判定，前 5 条资料以连续编号拼接上下文，并返回实际输入模型的来源列表。没有可靠来源时不调用模型，直接返回知识不足；模型空响应也返回同一兜底。Chat 模型切换不改变已有 Qdrant 向量。简历审计另设独立 `JAVA_INTERVIEW_RAG_RESUME_AUDIT_TIMEOUT`，默认 420 秒，以覆盖阿里云可能超过 200 秒且 Chat 最多两次尝试的窗口；超时取消有界任务、记录 `TIMEOUT` 并返回安全 `502`。
- RAG 召回日志存入独立 MySQL 表 `t_rag_retrieval_log`，记录问题、`topK`、阈值、Prompt 版本、状态、可靠依据标记、来源元数据 JSON、总耗时和失败类型；来源 JSON 只保留来源、版本、chunk 顺序、标题路径和相似度，不保存 chunk 正文或模型回答。日志存储故障只告警，不能影响已生成的回答；最近记录通过 `GET /api/knowledge/retrieval-logs` 查询。
- 通用固定评估题集为 20 条，覆盖精确术语、相似章节、标题路径、歧义问题、无答案和跨章节检索；独立 3 条 PDF 结构题覆盖代码、表格和跨页正文。回答评估使用 `POST` 且只执行通用 20 题，因为最多产生 20 次 Chat 调用并写入召回日志；结构题只用于 Embedding 检索，不增加额外模型裁判、语义评分或评估结果持久化。
- 面试准备画像与内部 RAG 评估集属于不同边界：固定评估集验证系统质量，画像只依据目标岗位、简历和可选 JD。画像输入限制为目标岗位 100 字符、简历 50000 字符、岗位描述 30000 字符，避免无边界模型上下文；模型输出为空或结构非法时明确失败，不返回伪造默认值。
- 首轮面试题只依据目标岗位和已确认画像，数量为 3 到 8 道；画像依据与知识依据分开表达。前者说明题目为何适合候选人，后者只保留相似度不低于 0.60 的实际知识库 chunk，空命中不伪造来源。
- 文本面试会话以 UUID 标识并保存单行 JSON 聚合；回答数量必须等于当前题号，回答序号必须连续，状态必须与动态题目队列是否答完一致。更新使用客户端题号、旧版本乐观锁和进行中状态三重校验，已完成、并发或延迟重复提交都不能覆盖已有回答。
- 复习任务只从完成会话的持久化逐题评价生成；是否生成由 `gaps` 是否为空确定，不追加模型判断。知识来源只保存可追溯元数据，任务创建用确定性 ID 和数据库唯一键保证重试幂等。
- 复习任务状态只允许 `PENDING -> COMPLETED`；完成接口使用会话 ID 与任务 ID 联合定位，并保留首次 `completedAt`，当前不支持重开。
- 计划复习日期使用 MySQL `DATE NULL`，设置 `null` 表示清除；状态和日期范围查询始终以会话 ID 为首个条件，不在缺少用户归属时开放全局待办。
- 复习历史只按当前会话聚合；每题最新遗漏直接来自最近一次持久化评价，不对自由文本遗漏做语义合并。没有用户身份和数据归属前不提供跨会话趋势。
- 固定面试回答评分基线内置 5 个脱敏样本，覆盖空回答拒绝、无关回答、部分回答、完整回答和无知识来源回答；`POST /api/interviews/evaluations/answers` 使用不生成追问的 `BASELINE` 模式执行。每次请求生成一个 UUID `baselineRunId`，五个稳定 `caseId` 共用该标识并随响应返回；成功结果额外返回回答证据和知识证据条数，不返回引文正文。分数区间只作为重复对比信号，不作为绝对正确性或录用判断。
- `ObservableInterviewAnswerEvaluator` 统一包裹正式、复习和基线评分，向 `t_interview_answer_evaluation_log` 写入评价模式、Prompt/rubric/model、四项分数、知识依据状态、耗时、状态和失败类型。基线模式同时保存 `baseline_run_id` 与 `baseline_case_id`，正式和复习模式保持为空；日志表不包含会话 ID、简历、题目、回答或知识正文，日志故障只告警，不改变评价返回或异常语义。
- `GET /api/interviews/evaluations/logs` 按评价模式读取最近 1 到 100 条日志，`BASELINE` 支持可选 `baselineRunId` 与 `baselineCaseId` 精确筛选，其他模式携带基线筛选时返回 400。响应保留 Prompt/rubric/model 版本汇总，并按“稳定样本 ID + Prompt/rubric/model”聚合跨运行结果；同一运行出现重复日志时只取按查询顺序最新一条参与样本统计，原始日志数量仍单独返回。总体方差只基于成功评价的总分，少于两次成功时为 `null`；迁移前无标识日志只计入 `unidentifiedBaselineCount`，不混入样本统计。查询不调用模型。`v3/v2` 已完成两轮真实评分，10 条日志按两个运行 ID 完整关联；评分日志仍不记录证据正文、证据条数或 token，证据条数只存在于当次批量响应。
- 前端 `/interview` 由 `InterviewView`、`useInterviewSession` 和面试组件组成，不引入 Pinia。组合式函数统一编排开始、恢复、提交与复习任务 API，并只在浏览器本地保存会话 UUID，不保存简历或回答全文；复习任务面板保持展示职责，不持有请求副作用。会话历史摘要使用独立纯展示组件，单题面板只接收服务端 summary 和 attempt 时间线。
- 前端 `/answer` 由目录、相似度检索和可靠问答三种独立模式组成。`useKnowledgeCatalog` 管理目录、当前选择、详情和淘汰请求；`KnowledgeCatalogPanel` 只展示当前来源列表并上报选择，`KnowledgeDocumentDetailPanel` 组合当前/历史版本、章节树和生命周期操作，`KnowledgeDocumentOutline` 展平服务端目录并通过类型化事件上报标题路径，`KnowledgeAnswerView` 负责与现有检索状态衔接。旧数据 `outline = null` 时提示重传当前原文件重建。人工淘汰复用现有 DELETE，成功后关闭详情并刷新目录，失败时保留详情供重试；目录和详情不触发 Chat、Embedding 或 Qdrant 查询，也不在浏览器持久化结果。
- 前端共享顶部只承载产品标识、资料库/面试训练导航、命令查找和服务状态；不展示开发阶段。资料库页面只保留实际可操作的导入链路和结果，项目能力边界、下一步计划等工程进度只写入文档。面试准备页通过岗位、简历的真实完成状态驱动准备度和按钮反馈；进行中页面由 `InterviewView` 提供单一工具边界，`InterviewQuestionPanel` 保持浅色主答题画布，`InterviewFeedbackPanel` 使用石墨侧栏和原生进度条表达服务端评分，组件契约与会话状态不因视觉调整改变。
