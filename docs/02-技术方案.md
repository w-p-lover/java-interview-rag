# 技术方案

## 当前原则

- 采用单体 Spring Boot 应用逐步演进。
- 后端以 Java 17 为主，构建工具使用 Maven。
- 当前基线使用 Spring Boot 3.5.16，并通过 Maven Wrapper 3.9.14 固定构建工具版本。
- HTTP 层使用 Spring MVC，独立项目开发端口为 `18080`。
- 前端使用 Vue 3、Vite、TypeScript、Vue Router、Axios 和 Sass，位于仓库内独立的 `frontend/` 子目录。
- 大模型应用优先使用 Spring AI。
- 关系数据库使用 MySQL，连接池使用 Druid，数据访问使用 MyBatis-Plus；本地 Compose 固定 MySQL 8，当前共享服务器实际为 5.7.36，仓库 SQL 保持 5.7/8 兼容。当前先保存文档来源与内容版本登记，后续再扩展向量状态、日志和评估数据。
- 向量数据库选择 Qdrant 1.10.1，Embedding 使用 DashScope `text-embedding-v3`；`storage` profile 已支持首次导入后的 chunk 批量向量写入。
- 第一版只支持 Markdown，避免文档解析范围膨胀。

## 核心数据流

### 产品主线

```text
求职方向与目标岗位
→ 简历解析与候选人画像
→ 简历、岗位描述和面试资料检索
→ 模拟面试与动态追问
→ 结构化评分与薄弱项
→ 错题和复习计划
```

### 面试准备画像

用户侧面试能力不复用内部 `FixedRagEvaluationDataset`。`POST /api/interviews/preparations` 接收目标岗位、简历文本和可选岗位描述，在 `storage` profile 下复用现有 ChatClient，通过一次结构化输出生成候选人摘要、简历证据、岗位要求和面试关注领域。服务端保留请求中的目标岗位并记录 `interview-preparation-v1` Prompt 版本；输入资料只作为事实，不允许模型推断未提供的经历，也不在画像阶段生成题目和评分。

第一版不保存简历、岗位描述或画像，不调用 Qdrant，不建立确认状态机。响应是后续用户确认与生成面试题的草稿边界；题目生成必须在后续结合知识来源和考察目标单独实现。

`/interview` 使用独立的 `InterviewTextFileField` 在浏览器本地读取 `.md`、`.markdown` 与 `.txt`，校验空正文和字符上限后填入现有字符串请求。简历与 JD 文件不经过知识库 multipart 导入，不执行版本登记、切分或向量化，也不把文件和正文写入 localStorage；文本框继续作为可检查、可编辑的备用输入。PDF/DOCX 在具备可靠解析前不开放。

### 首轮面试题与知识来源

调用方确认画像后，通过 `POST /api/interviews/questions` 提交目标岗位、完整画像和 3 到 8 的题数。`InterviewQuestionGenerationService` 复用现有 ChatClient，以 `interview-question-v1` 一次生成指定数量的结构化题目；每题包含题目文本、考察目标、画像依据类型和独立知识检索查询。模型返回数量必须与请求一致，依据类型必须属于画像关注领域已经出现的 `TARGET_ROLE`、`RESUME`、`JOB_DESCRIPTION`，否则明确失败。

题目生成后，服务逐题复用 `MarkdownSimilaritySearchService`，固定使用 `topK=3`、相似度阈值 `0.60`。最终结果返回 `knowledgeGrounded` 和实际 `MarkdownSearchResult`；没有可靠命中时保留由画像支撑的题目，但返回空知识来源，不伪造引用。该接口不读取 `FixedRagEvaluationDataset`，不生成参考答案、评分或追问，也不保存画像和题目。

### 文本面试会话

`POST /api/interviews/sessions/start` 依次调用画像、首轮出题和会话创建服务，默认生成 5 道首轮题并允许整场最多 8 道；初始题数可配置为 3 到 8，整场上限可配置到 12。`POST /api/interviews/sessions` 继续支持保存调用方已经确认的画像和题目；`GET /api/interviews/sessions/{sessionId}` 恢复完整快照。

`POST /api/interviews/sessions/{sessionId}/answers` 必须同时提交当前题号、期望版本和回答。服务在模型调用前校验题号与版本，避免延迟重试被误当作下一题；更新 SQL 同时匹配会话 ID、旧版本和 `IN_PROGRESS` 状态，影响行数为 0 时返回冲突。会话固定按题号顺序推进，不支持跳题或修改历史回答。

`InterviewAnswerEvaluationService` 一次结构化模型调用返回技术、完整性、表达三项分数、优点、遗漏、改进建议和可选追问。综合分由服务端确定性计算，知识可靠状态来自题目实际 chunk 而不是模型自报。可选追问使用独立查询按 `topK=3`、阈值 `0.60` 绑定真实来源并追加到队列；完全重复或达到整场上限时不追加。当前队列答完即完成会话，并从持久化逐题评价确定性生成平均分与汇总优缺点。

MySQL 表 `t_interview_session` 使用 `MEDIUMTEXT` 保存画像、动态题目、带评价回答和最终报告 JSON 快照，独立保存题数上限、当前题号、状态、乐观锁版本和时间。当前不保存原始完整简历和 JD，不实现用户归属、改答案或跳题。

### 资料与 RAG 主线

```text
Markdown 文件或上传内容
→ Spring MVC 导入接口
→ 解析标题与正文
→ 生成文档版本和 chunk
→ Embedding
→ 向量入库
→ 用户问题向量化
→ 相似度召回
→ 上下文拼接
→ 模型回答
→ 返回来源
→ 保存召回与评估结果
```

### 固定评估基线

阶段 4 以内置只读题集维护稳定的评估输入。每题包含唯一标识、问题、期望逻辑来源和预期回答要点；题集通过 `GET /api/knowledge/evaluation-cases` 提供，不依赖 MySQL、Qdrant 或模型调用。期望来源是评估时导入 Markdown 应使用的精确逻辑来源，不自动提供或导入测试资料，避免混入用户知识库。`GET /api/knowledge/evaluations/retrieval` 固定以 `topK=5`、相似度阈值 `0.0` 调用现有检索服务，比较实际来源和期望来源并计算命中率，不调用 Chat。`POST /api/knowledge/evaluations/answers` 复用现有回答服务，逐题返回回答、实际来源、来源命中、要点命中与总体覆盖率；匹配方法 `normalized-literal-containment-v1` 只衡量移除大小写、空白和标点差异后的完整要点字面覆盖，不代表语义正确率。当前不保存评估历史。

## 当前 Web 架构

```text
frontend/src/api/          HTTP 客户端、接口与类型
frontend/src/components/   导入面板、处理链和 chunk 账页
frontend/src/router/       页面路由
frontend/src/styles/       主题变量与全局样式
frontend/src/views/        求职面试工作台页面
```

前端通过 Vite 开发代理访问 `/api`，代理目标为 `http://127.0.0.1:18080`。目录组织参考只读项目 `shoka-blog` 的 API、路由、视图、组件和 Sass 分层，但不复制其博客功能、UI 框架、Pinia 或其他当前不需要的依赖。首页采用 Hallmark Workbench 信息结构与集中式 OKLCH 设计令牌，以柔和暖灰和克制珊瑚色表达求职训练产品；Markdown 导入与 chunk 检查只是资料准备阶段的基础能力，不代表产品最终定位。

## 工程边界

- 文档元数据和向量记录必须可关联、可更新、可删除。
- 生成答案必须附带实际召回来源。
- 知识不足时明确兜底，不让模型伪造来源。
- 检索参数和 Prompt 变更应能够通过固定评估集比较效果。
- 新基础设施在需求出现后引入，不预先堆叠 Redis、MQ、Elasticsearch 或微服务。
- 默认 `local` profile 使用进程内登记器；`storage` profile 使用独立 MySQL 数据库 `java_interview_rag` 和 Qdrant collection `java-interview-rag-chunks`。
- `storage` profile 为每个 chunk 写入来源、文档版本、chunk/section 顺序、标题级别和标题路径；向量 ID 由“来源 + 文档版本 + chunk 顺序”稳定生成，重复重试不会生成另一批点。
- 同一文档的向量写入按原 chunk 顺序拆为每批最多 10 条，匹配当前 DashScope `text-embedding-v3` 服务端批量上限；某批失败时继续沿用现有登记撤销与稳定 ID 重试语义，不增加异步任务或额外状态。
- 相同来源与版本在 MySQL 登记成功后才继续解析和写向量；Qdrant 写入失败时撤销该版本登记，使同一文档可以重试。跨 MySQL 与 Qdrant 不具备分布式事务，极端部分写入场景依靠稳定 ID 在重试时覆盖。
- 同一来源的新版本先完成向量写入，再按 `source` 相等且 `document_version` 不等于新版本的结构化过滤条件删除旧向量；清理失败时撤销新版本登记，使重试再次覆盖新点并收敛旧向量。
- 版本表保留历史“来源 + 版本”登记，避免历史版本被重复向量化；显式 `DELETE /api/knowledge/documents?source=...` 先删除来源下全部向量，再删除全部历史登记，使删除后的任意历史版本可以重新导入。
- 手动 `POST /api/knowledge/documents/rebuild` 要求调用方重传来源和 UTF-8 Markdown 文件，只允许 MySQL 或内存中已登记的精确“来源 + 版本”；当前版本表不保存原始正文，重建不创建、更新或删除登记，外部服务失败后可以用同一请求重试。
- Qdrant 重建非空文档时先用稳定 ID 写入或覆盖预期 chunk，再删除同来源其他版本，最后删除同来源同版本中 `chunk_order` 大于等于当前 chunk 数量的残留点；空文档直接清理该来源全部向量。
- 逻辑来源使用大小写敏感的精确字符串语义并拒绝首尾空白；MySQL `source` 列使用 5.7/8 均支持的 `utf8mb4_bin`，删除 SQL 使用 `BINARY` 比较，确保与 Java 字符串和 Qdrant 元数据过滤的来源边界一致。
- 私有连接信息通过 `.env` 或 `config/application-private.yml` 注入，环境变量统一使用 `JAVA_INTERVIEW_RAG_` 前缀。
- 服务器部署时只读导入 `D:/IdeaProjects/blog/blog-springboot/.env`，复用其中的 MySQL 主机、端口、账号、密码、Qdrant 地址和 DashScope Key；数据库名和 collection 名不复用主项目值，分别强制为 `java_interview_rag` 与 `java-interview-rag-chunks`。
- Qdrant 探测失败只告警不阻塞启动；MySQL 是 `storage` profile 的必要依赖。当前不自动创建 collection。
- `storage` profile 的 Chat 使用阿里百炼官方 OpenAI 兼容端点，并手动创建 `ChatModel`，默认模型为 `qwen3.7-plus`、温度为 `0.2`；原生 DashScope 客户端只承担 `text-embedding-v3`。全局禁用 OpenAI 自动配置，避免本地私有 profile 覆盖 YAML 排除列表后意外装配无关音频模型。回答服务固定检索前 5 条且相似度不低于 `0.60` 的 chunk，以连续资料编号拼接上下文，并返回实际输入模型的来源列表。没有可靠来源时不调用模型，直接返回知识不足；模型空响应也返回同一兜底。Chat 模型切换不改变已有 Qdrant 向量。
- RAG 召回日志存入独立 MySQL 表 `t_rag_retrieval_log`，记录问题、`topK`、阈值、Prompt 版本、状态、可靠依据标记、来源元数据 JSON、总耗时和失败类型；来源 JSON 只保留来源、版本、chunk 顺序、标题路径和相似度，不保存 chunk 正文或模型回答。日志存储故障只告警，不能影响已生成的回答；最近记录通过 `GET /api/knowledge/retrieval-logs` 查询。
- 固定评估题集当前为 6 条 Java/RAG 基线，覆盖 HashMap、线程池、`volatile`、GC Roots、MVCC 与 RAG 召回参数；已实现批量检索来源命中和批量回答要点字面覆盖对比。回答评估使用 `POST`，因为执行会产生 6 次 Chat 调用并写入召回日志；当前不增加额外模型裁判、语义评分或评估结果持久化。
- 面试准备画像与内部 RAG 评估集属于不同边界：固定评估集验证系统质量，画像只依据目标岗位、简历和可选 JD。画像输入限制为目标岗位 100 字符、简历 50000 字符、岗位描述 30000 字符，避免无边界模型上下文；模型输出为空或结构非法时明确失败，不返回伪造默认值。
- 首轮面试题只依据目标岗位和已确认画像，数量为 3 到 8 道；画像依据与知识依据分开表达。前者说明题目为何适合候选人，后者只保留相似度不低于 0.60 的实际知识库 chunk，空命中不伪造来源。
- 文本面试会话以 UUID 标识并保存单行 JSON 聚合；回答数量必须等于当前题号，回答序号必须连续，状态必须与动态题目队列是否答完一致。更新使用客户端题号、旧版本乐观锁和进行中状态三重校验，已完成、并发或延迟重复提交都不能覆盖已有回答。
- 前端 `/interview` 由 `InterviewView`、`useInterviewSession` 和四个面试组件组成，不引入 Pinia。组合式函数统一编排开始、恢复和提交 API，并只在浏览器本地保存会话 UUID，不保存简历或回答全文。
