# 面试准备与项目掌握要求

> 更新时间：2026-09-02。本文回答“项目掌握到什么程度可以投递和面试”，不重复开发路线或功能清单。

## 目标定位

不要求背下全部 Codex 生成的代码，但必须能独立解释：为什么这样设计、核心状态如何流转、模型和 Java 各自负责什么、失败时如何处理、评估结果能证明什么。

| 岗位方向 | 项目定位 |
| --- | --- |
| Java 后端 | 有 AI/RAG 差异化的重点项目之一 |
| Java AI 应用、RAG 后端 | 可以作为主讲项目，重点讲质量治理、证据边界和受控 Agent |
| Agent 应用工程 | 已完成简历证据审计和受控角色闭环，可主讲证据边界；图工作流仍需真实修正循环或 checkpoint 需求，不能声称多 Agent 平台经验 |
| 算法、模型训练、LLM Infra | 项目不匹配，不包装相关生产经验 |

## 一、达到什么程度可以开始投递

满足以下要求即可开始投递，不必等待所有后续技术完成：

- 能在 30 秒内讲清用户、主流程和三个工程亮点。
- 能不看文档画出 Vue、Spring Boot、Spring AI、MySQL、Qdrant、Lucene BM25 和 DashScope 的关系。
- 能完整讲清知识导入、RAG 回答、模拟面试、复习 Tool Calling 四条调用链中的至少三条。
- 能解释五个 RAG 指标及当前 8 份语料、18 个 chunk 的基线局限。
- 能说出至少五个真实失败场景及项目的处理方式。
- 能定位 Controller、核心 Service、持久化、模型调用、向量检索和直接测试。
- 能演示一条完整流程，并根据日志区分配置、数据库、Qdrant、模型和业务校验问题。
- 简历只写已实现并验证的能力，未完成内容明确标为 POC 或后续方向。

完成前六项即可开始投递；全部完成后，可以把项目作为 Java AI 应用/RAG 岗位的主讲项目。Graph、MCP、Memory 和多模型路由不是开始投递的前置条件。

## 二、必须掌握的核心内容

| 主题 | 必须能解释 | 合格标准 |
| --- | --- | --- |
| 定位与架构 | 为什么不是模型 API Demo；Java、模型、MySQL、Qdrant 的责任；为什么保持单体 Java 主线 | 三分钟从用户入口讲到模型和数据层，并说明每层边界 |
| 知识与向量生命周期 | 标题/chunk 元数据；重复导入短路；新版本、重建、删除；MySQL 与 Qdrant 最终一致性 | 画出四条状态变化，指出最容易产生脏数据的位置和恢复方式 |
| RAG 与可信回答 | Embedding、TopK、阈值；查资料与问资料库的区别；拒答、来源引用和服务端核对 | 未命中时先区分“语料没有”与“事实存在但没召回”，再选择补语料、改查询、切分或排序 |
| 评估体系 | Hit@1、Recall@5、MRR、标题路径召回、拒答准确率；检索/回答/评分评估分离 | 能解释指标上升的副作用，以及当前接近满分为何不能代表任意知识库 |
| 模拟面试 | 简历/JD 画像如何影响出题；知识库如何提供评分依据；追问、报告和复习如何衔接 | 从提交回答讲到评分、验真、持久化、报告和复习，并指出三个模型错误 |
| 证据化评分 | 模型提出候选引文、Java 逐字验真；正式/复习/基线的模式和关联标识 | 能说明验真能防什么、不能防什么，以及为什么评分仍可能波动 |
| Tool Calling | 普通 Chat 与工具调用区别；白名单、会话作用域、参数校验和结构化人工确认 | 能设计一个越权或重复写入攻击，并指出在哪一层被阻止 |
| 安全与隐私 | Prompt Injection、Excessive Agency、敏感日志、模型重试和写工具幂等 | 能解释“模型建议执行”和“服务端授权执行”的区别 |
| 缓存 | 为什么当前没有提前引入 Redis；Embedding、解析、检索和回答缓存的收益与风险；知识更新后的失效方式 | 能设计包含模型、Prompt、Chunk、索引和知识空间版本的缓存键，并说明为什么最终回答不能只按问题文本缓存 |
| 长对话 | 单轮无状态知识问答与有界面试上下文的区别；指代问题改写、Token Budget、历史摘要和事实记忆 | 能区分“检索问题缺少上下文”“模型上下文超限”“召回正确但生成错误”，不把三者都描述成检索失败 |
| 文件切分 | 当前标题 Section、段落优先、800 字符和超长段落硬切逻辑；标题路径、页码、块类型与相邻 Chunk 扩展 | 能解释字符切分的代码/表格/长段落风险，并设计一组同时衡量召回、噪声、Chunk 数和成本的消融实验 |
| 多格式解析 | Markdown、知识 PDF、面试 PDF、TXT 的不同生命周期；双栏恢复、重复页眉页脚、标题/列表/代码/表格识别及 OCR 边界 | 能画出知识文件与简历文件两条解析链，说明为什么简历/JD 不进入知识库，以及当前复杂 PDF、DOCX 和扫描件边界 |

### 工程化 RAG 专项追问

必须能够基于当前实现回答以下问题，不把后续方案表述为已经完成：

1. 为什么当前没有使用 Redis？哪些对象适合缓存，为什么优先考虑 Query Embedding 和解析结果，而不是直接缓存最终回答？
2. 文档导入、重建或删除后，检索缓存如何失效？模型、Prompt、Chunk 策略和权限发生变化时，缓存键还需要包含什么？
3. 知识问答为什么不会随着页面历史无限增大？用户追问“它为什么这样做”时，为什么仍可能检索失败？
4. 面试上下文为什么只取最近 6 条、每条最多 500 字？字符上限与 Token Budget 有什么区别，旧信息被裁剪后如何处理？
5. 当前 800 字符切分如何处理标题、段落和超长段落？如果代码块或表格超过 800 字符，会产生什么风险？
6. 为什么先做切分消融和困难样本，而不是直接引入语义切分、父子索引或 rerank？
7. Markdown 知识资料、PDF 知识资料、PDF 简历、Markdown/TXT 简历分别在哪里解析，最终数据是否进入 MySQL、Qdrant、Lucene 或只进入本场模型上下文？
8. PDF 的双栏、跨页章节、重复页眉页脚、代码和表格怎样识别？复杂双栏表格、图片语义和扫描页当前为什么不能宣称已支持？
9. 多份不同来源文件进入同一知识库后，怎样避免跨文件污染？未来知识空间、来源过滤和权限应该放在哪一层？

当前合格回答应明确：缓存尚未实现；知识问答是单轮无状态；面试上下文是有界摘要；Markdown 使用标题和段落优先的固定字符切分；知识 PDF 与简历 PDF 复用底层版面分析但采用不同上层生命周期。对应后续进入条件见 [后续开发路线](09-后续开发路线.md#5-工程化-rag-专项补齐)。

## 三、新 Agent 完成后追加掌握

| 技术 | 需要达到的程度 |
| --- | --- |
| 简历证据审计 | 解释事实、证据、缺失、风险和建议为何分离；会计算事实准确率、证据合法率和虚构率；能演示简历内提示注入不会改变规则 |
| 图工作流 | 说明普通链何时足够、何时需要状态图；画出节点、条件边、有界循环、HITL 和 checkpoint；解释恢复时如何避免重复调用和写入 |
| OpenTelemetry | 解释 span 边界、trace 传播、敏感正文、高基数标签和采样；能定位一次请求在哪个环节失败 |
| MCP | 解释 Resources、Prompts、Tools、Client/Server 和 Transport；说明 MCP 是 Agent 到工具，A2A 是独立 Agent 到 Agent |

图工作流、OpenTelemetry 或 MCP 只有真实代码、运行结果和消费者时才能写“实现并验证”；隔离实验必须写“POC”。

## 四、只需了解适用场景的方向

| 方向 | 投递前至少需要知道 |
| --- | --- |
| 查询拆分与 RRF | 多查询补召回、RRF 融合排序，以及为什么必须与原查询做同口径对照 |
| Hybrid Search | dense 和 sparse 的互补关系、RRF 按排名融合、分数尺度隔离，以及当前真实基线只证明标题路径局部收益 |
| rerank | 主要优化排序，会增加模型、延迟和费用，不能解决语料缺失 |
| Agent Memory | 不等于聊天记录；需要身份、来源、冲突、过期和删除规则 |
| GraphRAG | 面向实体关系和多跳问题，不是向量检索的默认升级 |
| A2A | 面向独立 Agent 系统互操作，不等于进程内子 Agent 或工具调用 |
| Temporal | 面向长任务和持久化执行，不是所有图工作流的必需组件 |
| 多模型路由 | 必须用固定任务比较质量、费用和延迟，不能按模型品牌硬编码 |
| Ragas/Langfuse/Phoenix | 分别偏离线评估或调用链观察，不应为了技术数量全部接入 |

这些方向能解释概念和进入条件即可；没有代码和结果时，不写进简历成果。

## 五、推荐口述结构

### 30 秒版本

```text
这是一个基于 Java、Spring Boot、Spring AI、MySQL 和 Qdrant 的 Java 面试训练系统。
它覆盖知识版本和向量生命周期、RAG 问答、固定评估、简历个性化面试、证据化评分、
复习任务和受控 Tool Calling。模型负责生成和评价，Java 负责状态、幂等、证据验真、
工具授权和数据边界，所以重点不是接模型 API，而是可信 RAG 和 Agent 工程治理。
```

### 3 分钟版本

1. 用户问题：资料查询、个性化面试和复习缺少可信闭环。
2. 系统架构：Vue、Spring Boot、Spring AI、DashScope、MySQL、Qdrant。
3. RAG：版本导入、切分、向量生命周期、阈值拒答和来源引用。
4. 面试：画像、出题、评分、追问、报告和复习 attempt。
5. 治理：固定评估、Java 证据验真、工具白名单、人工确认和无正文日志。
6. 结果与边界：给出真实指标，同时说明语料规模和未实现方向。

### 10 分钟深挖版本

只选两个问题讲深：

- MySQL 登记与 Qdrant 向量的失败恢复和最终一致性。
- RAG 评估如何发现跨主题漏召回，以及查询拆分为什么不直接进入生产。
- 评分引文如何经过 Java 验真，为什么仍不能证明评分长期稳定。
- Tool Calling 如何处理会话越权、人工确认、重试和重复写入。
- 简历证据审计如何处理事实、证据、提示注入和图工作流恢复。

## 六、Codex 开发下的学习方法

每完成一个闭环，不逐行背代码，但必须完成：

1. 自己找到入口 Controller、核心 Service、数据对象、持久化实现和直接测试。
2. 手动画一次调用链或状态图，不直接复制生成的架构图。
3. 不看文档回答“业务问题、方案、取舍、失败、指标、回退”六个问题。
4. 手动运行一次正常演示和一次失败演示，观察日志和返回状态。
5. 先独立口述 Codex 生成的追问题，再让 Codex 指出事实错误和遗漏。
6. 把无法回答的问题列为学习任务，不通过增加技术栈掩盖知识缺口。

投递前建议约 60% 时间用于系统学习和口述训练，25% 用于核对实现与测试，15% 用于演示、文档和简历调整。代码量不是主要瓶颈，能否解释设计和失败边界才是。

## 七、面试就绪自测

- [ ] 30 秒和 3 分钟版本能自然讲完，不堆技术名词。
- [ ] 能画完整架构和三条核心调用链。
- [ ] 能解释五个 RAG 指标及当前基线边界。
- [ ] 能区分语料缺失、召回失败、生成错误和评分波动。
- [ ] 能解释 MySQL/Qdrant 最终一致性及一个失败恢复过程。
- [ ] 能解释 Tool Calling 的会话隔离、人工确认、重试和日志脱敏。
- [ ] 能说明当前无缓存的原因，并设计具备知识版本和权限边界的缓存失效方案。
- [ ] 能区分单轮 RAG、上下文问题改写、Token 超限和真正的召回失败。
- [ ] 能口述 Markdown/PDF 的解析与切分链，并说明复杂表格、图片、扫描件和 DOCX 的当前边界。
- [ ] 能在两分钟内定位一个 Controller、Service、Mapper/Store 和测试。
- [ ] 能说出三个未采用的前沿技术及不采用理由。
- [ ] 能演示正常流程，并处理一个外部服务不可用场景。
- [ ] 简历中的每一句项目成果都有代码、测试、运行结果或文档证据。

完成前八项即可投递；全部完成后可作为 Java AI 应用/RAG 岗位主讲项目。发现薄弱点时优先补理解、演示和证据，不自动扩展新方向。
