# 需求边界

## 当前必须实现

- Java 17 与 Spring Boot 3 的最小可运行骨架。
- Markdown 文档导入、元数据和版本识别。
- 按标题、段落和最大长度进行文本切分。
- Embedding 与向量新增、更新、删除和重建。
- RAG 问答、来源引用和无可靠来源兜底。
- 提供可直接使用的资料库问答页面，显示回答是否由可靠资料支撑，并允许逐条核对来源、标题路径、相似度、版本、chunk 顺序和原文。
- 提供资料来源详情和生命周期操作：查看当前版本与历史登记，新版本成功后自动淘汰旧向量；整来源人工淘汰必须确认并保持先删向量、后删登记。
- 召回日志、相似度、耗时和 Prompt 版本记录。
- 固定 RAG 评估问题集及批量评估结果。
- 根据目标岗位、简历和可选岗位描述生成可确认的面试准备画像，并基于画像生成 3 到 8 道带考察目标、依据类型和真实知识来源状态的首轮面试题；用户侧面试能力与内部固定 RAG 评估集隔离。
- 保存确认画像、动态题目队列、逐题回答与评价，支持恢复文本面试会话、按顺序安全提交回答、在最多 12 道的边界内动态追问，并在题目队列完成后生成汇总报告。
- 正式面试和复习作答的结构化评价必须携带可核验证据：回答证据逐字来自当前回答，知识证据只能引用当前题目已经检索到的可靠资料；服务端验真后随评价快照持久化并展示。
- 提供可直接操作的文本面试页面，支持配置题数、查看即时反馈和最终报告，并从浏览器保存的会话 ID 恢复进度。
- 在 `/interview` 提供当前浏览器最近 8 场面试入口；浏览器只保存会话 UUID，岗位、状态、进度和更新时间均通过单会话接口恢复，404 会话自动淘汰，临时网络错误保留入口。
- 将资料库与面试输入明确拆分：资料库只接收需要长期检索和向量化的学习/项目技术资料；简历与可选 JD 从模拟面试入口独立上传、自动提取正文并生成画像，默认不进入知识库。文本粘贴只作为文件解析失败或特殊输入的备用方式。
- 面试文件支持带文本层且不超过 10 MiB 的 PDF、Markdown 和 TXT；PDF 经后端临时解析并按位置排序，Markdown/TXT 在浏览器本地读取；扫描件不执行伪 OCR，DOCX 暂不开放。
- 对已完成面试按逐题评价确定性生成待复习任务；每道存在遗漏的题目保存原题、考察目标、遗漏项、改进建议和知识来源元数据，重复生成保持幂等，不再次调用模型。
- 待复习任务可以单向推进为已完成并记录首次完成时间；重复完成不覆盖原时间。
- 复习任务可以独立多次作答并保留评价版本、分差和单会话历史；正式面试答案和报告保持不可变。
- 复习任务支持可选计划日期，并在当前会话内按状态和计划日期范围查询；第一版不创建提醒或定时任务。

## 后续阶段实现

- 混合检索、必要的 rerank 和查询改写。
- 固定面试回答评估样本、评价耗时/状态日志和必要的服务端评分边界。
- 数据归属明确后的跨会话复习汇总与趋势。
- 分段结构化简历证据与可配置岗位 rubric；保持现有 `resumeText` / `jobDescription` 输入契约，等真实样本证明收益后再实现。
- Tool Calling 和执行记录。
- 真实需求出现后的 MCP 接入。
- 在普通向量 RAG 的多跳关系问题经过固定评估集证明后，再评估 GraphRAG；候选关系包括“候选人—项目—技能—岗位要求—面试题—回答—薄弱项—知识资料—复习任务”。
- 资料原文持久化、历史版本在线预览、软删除保留期和版本回滚；当前只有版本元数据，不能把 Qdrant 反向拼接冒充原始文件。

## 当前明确不实现

- 纯 Python 主后端。
- 模型训练、微调和 LLM Infra。
- Dify、Coze、n8n 替代核心功能。
- 多 Agent 平台和通用 Agent Runtime。
- 语音、视频、防作弊、组织管理和多租户招聘平台。
- 白板、实时代码编辑器和大型后台管理系统。
- 没有当前需求支撑的微服务及中间件堆叠。
- 没有多跳召回收益数据时，不提前引入 GraphRAG、Neo4j 或独立知识图谱基础设施。
- 没有用户身份和数据归属前，不提供后端全量面试会话列表或跨浏览器历史查询。

## 输入与存储边界

| 输入 | 业务入口 | 主要用途 | 默认持久化与向量化 |
| --- | --- | --- | --- |
| Java 面试资料、项目技术说明、学习文档 | 资料库 | RAG 回答、出题和评分依据 | 是 |
| 候选人简历 | 模拟面试 | 候选人画像、个性化出题 | 否 |
| 岗位描述 JD | 模拟面试 | 岗位要求提取、题目侧重 | 否 |

简历和 JD 可以复用通用文件读取能力，但不能复用资料库的版本登记与向量生命周期。未来如确有“把简历作为长期求职档案保存”的需求，应建立独立的求职档案模型和用户确认机制，不能默认把个人资料写入公共知识库。

## 变更规则

用户最新明确需求可以调整本文件。自动开发可以细化实现顺序，但不得自行改变长期定位或把“后续阶段”整体提前到当前阶段。
