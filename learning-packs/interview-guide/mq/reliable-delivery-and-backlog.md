# 消息队列可靠投递、幂等、顺序与积压治理

## 学习目标

学完后应能沿“业务事务 -> Producer -> Broker -> Consumer -> 业务副作用”逐段分析消息在哪丢、在哪重复、顺序在哪被破坏。面试回答不能停在 `ACK`、重试和死信队列名词，还要给出幂等键、状态转换、积压恢复速度和当前项目为什么尚未引入 MQ。

## 一、消息可靠性必须分段证明

业务写库成功不等于消息已发送，Producer 收到确认也不等于消费者业务已完成。可靠链路至少包含：

1. 本地业务状态如何与待发送事件保持一致。
2. Producer 发送失败或超时后怎样安全重试。
3. Broker 怎样持久化、复制和确认消息。
4. Consumer 什么时候 ACK，处理失败怎样重投。
5. 重复消费怎样避免重复扣款、发券或写状态。

只说“使用可靠 MQ”无法覆盖第一段和最后一段。数据库事务与 Broker 不是同一个原子事务时，常见做法是在本地事务写业务数据和 Outbox 事件，再由独立发布器投递；投递成功后标记事件，扫描器负责恢复遗漏。

## 二、投递语义与 exactly-once 边界

At-most-once 通常先确认或不重试，性能较高但允许丢失。At-least-once 在确认不确定时重投，因此更可靠但可能重复，也是最常见的工程基础。所谓 exactly-once 往往只在某个产品和处理边界内成立，例如 Kafka 事务能约束 Kafka 内的读写，却不能自动让外部 MySQL、HTTP 支付接口也恰好执行一次。

端到端可靠性通常是“至少一次投递 + 幂等消费”。消费者使用稳定事件 ID 或业务键，在同一数据库事务中记录消费结果并执行状态变更；唯一键、条件更新或状态机让重复消息得到相同结果。先记去重再执行业务可能在业务失败时误认为完成，先执行业务再记去重又可能留下重复窗口，必须设计同一事务或可补偿协议。

## 三、ACK、重试和死信

消费者应在业务事务成功后 ACK。若自动 ACK 发生在业务完成前，进程崩溃会丢消息；若业务成功后 ACK 丢失，Broker 会重投，所以消费端仍需幂等。

重试必须区分瞬时错误和永久错误。网络超时可有限次数指数退避；参数非法、权限拒绝或数据约束错误通常不应无限重试。达到上限后进入死信队列或失败表，保留事件 ID、错误类型、尝试次数和下一次人工/自动处置入口。死信不是“消息已经解决”，而是把未知循环转换成可观测终态。

## 四、顺序性要先定义范围

全局顺序通常意味着单分区、单队列或单消费者，吞吐和可用性代价很高。多数业务只需要同一订单、账户或聚合根内有序，可用业务 Key 路由到同一分区，再在消费者端按版本或序号拒绝倒序事件。

即使 Broker 保证分区顺序，重试、并行线程和下游异步调用也可能让业务完成顺序改变。解决方案不是笼统地“开启顺序消息”，而是限制同 Key 并行度、保存期望版本、对缺口等待或重放，并为长期缺失设置失败终态。

## 五、积压要用吞吐量计算

假设积压 `B` 条，新流入速率为 `P` 条/秒，当前消费能力为 `C` 条/秒。只有 `C > P` 才能消化积压，理论清空时间约为 `B / (C - P)`；还要考虑失败重试和下游容量。简单增加消费者只有在分区数、数据库连接、外部接口限额和幂等能力允许时才有效。

应急步骤通常是先止血：识别慢点、暂停非核心生产、隔离毒消息、保护数据库；再扩展分区或消费者并估算恢复时间。恢复后要补充 Lag、生产/消费速率、失败率、重试次数、处理耗时和最老消息年龄告警。

## 六、选型不是背产品特点

Kafka 偏向高吞吐日志与事件流，RabbitMQ 擅长灵活路由和任务分发，RocketMQ 提供电商常见的事务、延迟和过滤能力。选择时应从吞吐、延迟、保留时间、顺序范围、事务边界、消费模型、运维经验和生态约束出发。

没有跨进程 Worker、持久积压或服务解耦需求时，进程内有界线程池加数据库任务表可能更简单。为了简历关键词提前引入 Broker，会增加部署、监控、重复消费和数据一致性成本，却未必解决真实问题。

## 七、本项目的任务协议映射

本项目当前没有 Kafka、RabbitMQ 或 RocketMQ。资料导入和题库生成使用有界进程内执行器控制并发，数据库保存 `QUEUED/PROCESSING/SUCCEEDED/FAILED/CANCELLED` 状态。题库任务用 `requestId` 唯一键处理重复提交，用活动任务唯一键限制同资料版本的并发生成。

Worker 领取任务后写入新的 `attemptId`，心跳和所有进度/终态更新都必须匹配当前 attempt。失联扫描只允许有限恢复，旧 Worker 即使恢复，也会因 attempt 不匹配被拒绝。这对应消息系统里的幂等提交、消费租约、有限重试和 fencing，但它不是持久 Broker：排队工作仍在单进程内，资料正文也没有持久化为可跨进程重放的消息。

当出现多个独立 Worker、需要应用重启后保留 Pending、需要独立扩缩消费能力，或生产与消费生命周期必须解耦时，才有理由引入 Redis Stream 或 MQ。迁移时仍应保留数据库业务状态、requestId、attempt fencing 和幂等写，不能把正确性全部交给 Broker。

## 八、面试回答模板

1. 明确业务事件、允许丢失/重复的边界和吞吐、延迟、保留时间。
2. 沿业务事务、Producer、Broker、Consumer、外部副作用逐段分析失败。
3. 说明确认时点、重试上限、幂等键和状态机条件。
4. 定义顺序范围，不默认要求全局有序。
5. 用生产速率、消费速率和积压量估算扩容与恢复时间。
6. 给出监控、死信处理、回放和回滚方式，再做产品选型。

## 九、练习题

### 主问题 1

订单落库后要发布“订单已创建”事件，怎样避免数据库成功但消息丢失，又怎样处理发送超时导致的重复消息？

回答检查点：本地事务 Outbox、发布扫描、Broker Confirm、稳定事件 ID、消费幂等、终态和补偿。

追问：为什么“Producer 收到 ACK”仍不能证明下游业务已经完成？

### 主问题 2

某 Topic 积压 100 万条，新消息每秒 2000 条，当前每秒只能消费 2500 条。如何估算恢复时间并制定不压垮数据库的扩容方案？

回答检查点：净消费速率、理论清空时间、分区并行度、下游容量、失败重试、限流和 Lag 指标。

追问：消费者数量超过分区数后为什么通常不会继续线性提速？

### 主问题 3

本项目题库生成已经有数据库任务状态、requestId、attemptId、心跳和失联恢复。什么时候仍值得引入 MQ，迁移后哪些机制不能删除？

回答检查点：跨进程消费、持久 Pending、独立扩缩容、进程内队列边界、幂等、业务状态、fencing、有限重试。

追问：Broker 已经保证至少一次投递，为什么还必须保留业务唯一键？

## 十、掌握标准

- 能逐段证明消息可靠性，不把 Broker 持久化等同端到端成功。
- 能解释 exactly-once 的产品边界和外部副作用限制。
- 能设计稳定事件 ID、幂等消费和有限重试终态。
- 能定义分区有序并处理业务完成乱序。
- 能根据净消费速率估算积压恢复时间。
- 能说明当前项目未使用 MQ 的合理性和未来引入条件。
