# 分布式一致性、幂等、租约与故障恢复

## 学习目标

学完后应能在网络分区、超时和重试存在时说明系统如何避免重复副作用、旧 Worker 覆盖新结果，以及数据库与多个索引无法原子提交时怎样暴露和修复不一致。重点不是背 CAP、2PC、TCC 名词，而是把约束、状态流、失败窗口和恢复入口讲完整。

## 一、CAP 讨论从网络分区开始

CAP 不是“一个系统平时只能选两个字母”。当通信正常时，一致性与可用性可以同时很好；真正的取舍发生在网络分区期间：无法确认另一侧状态时，是拒绝部分请求以保持单一一致结果，还是继续接受请求并允许分区间暂时不一致。

CP 或 AP 也不是整个系统唯一标签。注册中心、余额扣减、商品详情缓存可以选择不同边界。回答时应说明操作类型、冲突代价、允许陈旧时间、恢复合并方式和用户看到的行为。

BASE 描述基本可用、软状态和最终一致性，但“最终”必须有收敛机制和时间目标。没有重试上限、补偿任务、对账和告警的异步双写，只是希望它最终一致。

## 二、超时制造未知结果

调用超时只表示调用方没有及时收到结果，不代表服务端没有执行。盲目重试可能重复创建订单、扣款或生成题目。因此每个可重试写请求需要稳定幂等键，并在权威存储中保存该键对应的输入契约和结果。

相同幂等键、相同输入应返回同一结果；相同键却对应不同输入必须拒绝。数据库唯一键处理并发首写，业务状态机或条件更新保证结果只能沿合法方向变化。仅在网关做短期 Redis 去重不足以覆盖缓存丢失、过期和数据库已提交但响应丢失。

## 三、锁、乐观锁和 fencing 分工

悲观锁在持有期间阻止其他事务修改同一资源，适合短事务内的强互斥；乐观锁用版本条件检测“读后被别人改过”，冲突时由调用方刷新或重试；唯一约束保护不可重复的业务事实。这三者作用不同。

分布式租约还多一个旧持有者问题：Worker A 的租约过期后 Worker B 接管，A 可能从长暂停中恢复并继续写。仅让 B 获得新锁不能撤销 A 已经持有的进程状态。fencing token 为每次接管分配递增序号，资源端只接受不小于已见序号的写入，从而拒绝迟到旧 Worker。

若使用随机 `attemptId` 而不是数值 token，也可以在数据库条件写中要求 attempt 必须等于任务当前 attempt。它不能跨越所有外部系统，但能保护这个数据库事实源不被旧 Worker 覆盖。

## 四、分布式事务方案按业务语义选择

2PC 通过准备和提交协调多个参与者，能提供较强原子语义，但有同步阻塞、协调者和资源占用问题。TCC 把业务拆成 Try/Confirm/Cancel，需要处理幂等、空回滚和悬挂，适合能明确预留资源的核心业务。Saga 把长流程拆成局部事务和补偿动作，吞吐与可用性较好，但补偿不一定能恢复物理世界的所有副作用。

数据库加消息的常见最终一致性方案是 Outbox：同一事务写业务数据和事件，再异步发布；消费者幂等处理。选择方案时应看一致性强度、事务时长、参与者是否可改造、补偿可行性、吞吐和故障人工成本，而不是默认引入 Seata 或全局事务。

## 五、心跳、租约与故障检测

心跳超时是故障怀疑，不是故障证明。阈值过短会因 GC、网络抖动和慢调用误判，过长又会拖慢恢复时间。租约协议要定义心跳周期、失联阈值、最大恢复次数、接管后的 attempt、旧 Worker 拒写条件和恢复耗尽终态。

恢复目标可用 RTO 和 RPO 表达：RTO 是恢复服务所需时间，RPO 是最多允许丢失或回退多少数据。任务系统还要区分“任务状态已恢复”和“外部副作用是否已发生”，后者通常需要幂等、对账或补偿。

## 六、多存储写入的现实边界

本项目导入一份资料时要登记 MySQL 正文/版本，并写 Qdrant Dense 和 Lucene Sparse。三者没有共同事务，因此不能靠 `@Transactional` 一次回滚。当前实现以 MySQL 保存预期版本和 Chunk 数，以索引状态记录 `INDEXING/READY/FAILED`，失败时做删除补偿；一致性巡检分别比较当前版本数量、元数据版本、旧版本残留和期望 Chunk 数，人工确认后可从持久化快照重建。

这个协议把跨存储“原子提交”降为可检测、可恢复的状态机，但索引构建期间仍可能暴露部分结果，旧 Worker 的迟到索引写也还没有 generation 级隔离。阶段 9.2 计划采用临时 generation 完整构建后再提升当前版本，解决发布可见性和旧 attempt 隔离，而不是假装现有补偿等同强原子性。

## 七、本项目的幂等与恢复案例

正式面试创建使用稳定 `requestId` 和数据库唯一键。两个并发请求都尝试插入时，胜出者创建会话，失败者按 requestId 读取同一结果；同一个键用于不同输入则由服务契约拒绝。

题库生成任务同时使用 requestId 唯一键和“source + documentVersion”活动任务唯一键。Worker 开始时获得 attemptId，心跳、逐题保存、完成和失败都要求匹配当前 attempt。失联扫描最多恢复有限次数，恢复耗尽进入明确失败终态。它体现了幂等、防并发活动任务、租约检测、fencing 和有界恢复的组合。

这些机制没有让系统变成自由分布式任务平台：执行器仍在单进程内，资料任务正文不持久化，Qdrant/Lucene 发布尚未 generation 隔离。面试中应同时说出已有保障和未覆盖边界。

## 八、面试回答模板

1. 先澄清 QPS、SLA、一致性级别、故障域和允许的数据损失。
2. 画出权威事实源、派生存储、请求状态和外部副作用。
3. 对超时和重试定义幂等键、输入契约、唯一约束和结果恢复。
4. 对 Worker 接管定义心跳、租约、attempt/fencing 和旧 Worker 拒写。
5. 对跨资源写入选择强事务、Outbox、TCC、Saga 或可检测补偿。
6. 给出 RTO/RPO、告警、对账、人工终态和演练方法。

## 九、练习题

### 主问题 1

客户端创建面试时超时并重试，怎样保证不会创建两个会话，同时又能恢复第一次已经成功但响应丢失的结果？

回答检查点：客户端稳定 requestId、输入契约、数据库唯一键、并发插入、冲突后读取、状态机与返回同一结果。

追问：仅在 Redis 中 `SETNX` 一个 30 秒去重 Key，为什么不能作为最终正确性边界？

### 主问题 2

题库 Worker A 心跳过期后由 Worker B 接管，但 A 随后恢复。如何阻止 A 的迟到结果覆盖 B，为什么只有分布式锁还不够？

回答检查点：故障误判、租约过期、新 attempt、所有条件写校验 attempt、fencing、唯一键、外部副作用边界。

追问：心跳阈值设置过短和过长分别有什么代价？

### 主问题 3

一份知识资料需要同时写 MySQL、Qdrant 和 Lucene，三者不能参加同一事务。如何让用户只看到完整版本，并能从部分失败中恢复？

回答检查点：权威快照、临时 generation、状态机、完整计数、原子提升、旧版本保留、巡检、补偿和重建。

追问：为什么“捕获异常后依次删除”仍不能等价于跨存储原子事务？

## 十、掌握标准

- 能正确解释网络分区时的 CAP 取舍，不把系统粗暴贴成 CP/AP。
- 能区分超时、失败和未知结果，并设计持久幂等协议。
- 能说明悲观锁、乐观锁、唯一键、租约与 fencing 的职责。
- 能按业务语义比较 2PC、TCC、Saga 和 Outbox。
- 能为心跳恢复定义阈值、最大次数、RTO/RPO 和终态。
- 能用本项目解释 MySQL、Qdrant、Lucene 的可检测恢复与尚未完成的原子发布边界。
