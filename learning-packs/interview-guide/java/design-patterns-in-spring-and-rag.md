# 设计模式在 Spring 与 RAG 工程中的应用

## 一、模式是问题语言，不是类名清单

设计模式描述在特定约束下反复出现的协作方式。判断是否值得使用，应看它是否隔离变化、减少条件分支、保护不变量或改善测试；为展示模式增加一层只有单个实现的接口，通常只是复杂度。

## 二、策略、模板方法与工厂

策略模式把可替换算法放在统一契约后，例如 Dense、Sparse、Hybrid 检索或不同 Store。选择应由明确配置或业务上下文完成，不能把 `if/else` 只是搬到工厂里。

模板方法固定骨架、开放少量步骤，适合流程稳定且子类变化受控；组合函数通常比深继承更灵活。工厂封装创建决策，Spring 容器本身承担大量对象创建和依赖组装，但业务工厂仍应表达领域选择而不是隐藏任意 Service Locator。

## 三、装饰器、适配器与代理

装饰器在相同接口外叠加观测、缓存或校验，多个装饰器顺序会改变行为。适配器把外部 API 转成内部契约，隔离 SDK 模型；代理控制调用入口，可实现事务、权限和远程调用。三者结构相似，意图不同：增强职责、转换接口、控制访问。

## 四、观察者、状态与责任链

事件观察者降低发布者与多个副作用的耦合，但异步事件会引入顺序、重复和最终一致性。状态模式把合法转换集中管理，适合任务生命周期；若只用枚举加条件更新也足够清晰，不必强建状态类层次。责任链适合验证和处理步骤可组合，但要明确短路、顺序和错误聚合。

## 五、本项目代码映射

Store 接口及内存/MySQL 实现体现策略与适配边界；Spring `@Configuration` 按 Profile 创建具体实现。`ObservableInterviewAnswerEvaluator` 包装核心 evaluator，增加日志和指标而不复制评分逻辑，是装饰器。题库与资料任务的枚举状态、版本条件更新体现状态机约束。RAG 回答按检索、上下文、生成、证据验证组成显式流水线，比建立通用责任链框架更直接。

本地选择强调够用：只有真实替换点才保留接口，流程只有一个实现时使用普通方法；没有为模式命名而重构现有代码。

## 六、练习题

### 主问题 1｜原理与实现

如何区分装饰器、适配器和代理，并各举一个 Java/Spring 场景？

参考回答：装饰器保持接口并叠加职责，如 evaluator 外包观测；适配器把外部 SDK 响应转换成内部模型；代理控制访问入口，如 Spring AOP 事务代理。要说明对象关系和意图，不能仅凭“包了一层”判断。

回答检查点：相同接口增强、接口转换、访问控制、组合顺序和真实场景。

追问：观测装饰器放在重试外和重试内记录的指标有什么差异？

追问参考：外层记录一次业务请求总耗时和最终结果，内层会记录每次尝试；两者可同时存在但指标命名必须区分。

### 主问题 2｜并发与边界

任务状态机只用枚举和数据库条件 UPDATE 是否足够，什么时候才需要状态模式类层次？

参考回答：状态少、转换固定且数据库是权威源时，枚举、集中校验和条件更新更简单可靠。若不同状态拥有大量独立行为、转换扩展频繁且可在单进程内封装，状态对象可能减少分支。无论形式如何，数据库条件和并发版本仍负责跨实例原子性。

回答检查点：复杂度阈值、集中不变量、数据库原子转换、类爆炸和演进成本。

追问：把每个状态做成 Bean 能否自动解决并发转换？

追问参考：不能；它只组织代码，跨请求竞争仍需锁、版本或条件更新。

### 主问题 3｜结论与推理表达

为什么本项目对 Store 使用接口，而没有把所有 Service 都抽象成接口？

参考回答：Store 存在 local 内存和 storage MySQL 两个真实替换实现，也便于隔离持久化测试；许多 Service 只有一个业务实现，额外接口不减少变化成本。抽象应围绕稳定契约和真实替换点，不应按层机械生成。

回答检查点：真实变化轴、测试边界、Profile 替换、单实现成本和避免过度设计。

追问：接口只有一个实现就一定应该删除吗？

追问参考：不一定；若它隔离外部系统、形成领域端口或测试边界仍有价值，但需给出具体作用。
