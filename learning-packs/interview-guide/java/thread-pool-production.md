# ThreadPoolExecutor 从任务接收到生产治理

## 学习目标

学完后应能完成四件事：准确描述 `execute` 的决策顺序；根据任务和下游容量解释线程数、队列和拒绝策略；说明取消、超时、关闭与进程重启的边界；用本项目资料索引和检索线程池讲清一次真实工程取舍。

面试回答不要从参数名开始背诵。先说明业务任务与容量约束，再讲执行机制、失败边界、观测指标和恢复方式。

## 一、任务提交时到底发生了什么

`ThreadPoolExecutor.execute(command)` 的主决策顺序是：

1. 当前工作线程少于 `corePoolSize` 时，尝试创建核心工作线程直接接收任务。
2. 核心线程已满且线程池仍在运行时，尝试把任务放入工作队列。
3. 入队后必须再次检查运行状态。线程池可能在检查与入队之间开始关闭，此时要尝试移除任务并执行拒绝策略；如果池内没有工作线程，还要补建一个空任务 Worker，确保队列有人消费。
4. 队列无法接收任务时，才尝试创建不超过 `maximumPoolSize` 的非核心线程。
5. 非核心线程也无法创建时，执行 `RejectedExecutionHandler`。

因此，“任务一来就扩到 maximumPoolSize”是错误说法。使用有界队列时，最大线程数通常要等队列已满后才参与决策；使用 `SynchronousQueue` 时没有队列容量，每次提交都需要直接交接给 Worker，扩容行为会明显不同。

## 二、参数不是独立旋钮

### corePoolSize 与 maximumPoolSize

CPU 密集任务首先受核心数限制，线程过多只会增加上下文切换。I/O 密集任务可以适当增加并发，但最终上限仍要服从数据库连接池、HTTP 下游并发、模型限流和内存预算。公式只能提供初值，压测和生产指标才决定最终配置。

固定线程池把核心数和最大数设为相同值，容量更容易解释；代价是高峰时不能临时扩容。弹性线程池允许扩到最大线程数，但必须同时说明空闲回收、队列类型和下游保护，否则“弹性”可能只是把压力转移给数据库或模型服务。

### workQueue

无界队列会让 `maximumPoolSize` 很难生效，并把过载表现推迟为长等待或内存压力。有界队列把最大积压显式化，能较早拒绝并形成背压，但队列大小必须结合可接受等待时间估算。

可用近似关系理解容量：如果稳定吞吐为每秒 `R` 个任务，可接受排队时间为 `T` 秒，队列初值可以从 `R * T` 推导，再结合单任务内存、突发流量和下游限额压测调整。队列容量不是越大越安全。

### keepAliveTime 与核心线程超时

它主要控制超过核心数的空闲线程何时回收。若显式允许核心线程超时，核心线程也会退出，适合长时间低流量且允许冷启动的任务；延迟敏感链路通常不应只为减少几个线程而承担重新建线程的抖动。

### ThreadFactory

线程名是最低成本的可观测性。名称应能区分业务用途，例如 `dense-retrieval-`、`knowledge-task-`，这样线程转储、超时日志和监控才能快速定位到具体执行器。还应明确未捕获异常处理和是否使用守护线程，不能依赖默认名称排查生产问题。

## 三、拒绝策略就是过载协议

- `AbortPolicy`：立即抛出异常，适合调用方能够返回 429/503、重试或记录失败的接口。
- `CallerRunsPolicy`：由提交线程执行，通过拖慢生产者形成背压；若提交线程是 Web 请求线程，要评估延迟放大和请求线程耗尽。
- `DiscardPolicy`：静默丢弃，只有业务明确允许丢失且另有计数时才可用。
- `DiscardOldestPolicy`：丢弃队列最老任务后重试。它会破坏先到先服务和任务时效语义，不适合必须完成或需要幂等顺序的任务。

不能只说用了哪一种策略，还要说明拒绝后业务状态如何落地。对持久化异步任务，线程池拒绝只是执行层信号；任务表应进入明确失败状态并释放活动键，调用方才能安全重试。对只读在线查询，可以把拒绝映射为“当前繁忙”，不应伪装成空结果。

## 四、取消、超时和关闭的真实边界

`Future.cancel(true)` 只是发送中断信号。任务是否停止取决于执行代码是否响应中断，外部 HTTP、数据库或模型 SDK 也可能继续运行。业务不能把“发出了 cancel”直接等价为“副作用已经撤销”。

取消仍在队列中的任务时，除了改变领域状态，还要让工作对象离开执行队列；否则一个已取消任务仍可能占用有限队列槽位。可以保存对应 `FutureTask`，取消后调用执行器的 `remove`。运行中的任务若存在外部副作用，保守做法通常是拒绝强制取消，等待其得到明确终态。

超时至少包含两个层次：

- 等待方超时：调用方不再等待，但 Worker 可能仍在运行。
- 业务截止时间：领域状态只允许一个完成者写终态，超时与正常完成竞争时需要完成门闩或数据库条件更新。

`shutdown()` 停止接收新任务并等待已提交任务完成；`shutdownNow()` 尝试中断运行任务并返回未开始任务，同样不保证副作用回滚。进程级重启更不会由线程池自动恢复任务。需要恢复时，必须把任务状态、输入或可重建引用持久化，并使用 attempt fencing 防止旧 Worker 迟到覆盖新尝试。

## 五、动态调参要回答顺序和证据

动态修改核心线程数和最大线程数时要满足 `corePoolSize <= maximumPoolSize`，缩小最大值前应先处理核心值和正在运行的任务。普通阻塞队列的容量通常不是一个可靠的运行时可变参数；为了“在线调队列”替换内部队列，风险往往大于收益。

调整前至少观察：活动线程数、当前排队数、队列容量、完成数、拒绝数、超时数、任务耗时分位数、下游错误率和下游连接池等待。只看到队列长就加线程，可能让数据库、向量库或模型服务更快过载。

一次可靠的调参说明应包含：当前瓶颈证据、目标指标、单次改动、回滚阈值和改动后观察窗口。没有这些信息，“支持动态配置”只是把错误配置变得更快。

## 六、本项目代码追踪

### 资料索引任务

入口是 `KnowledgeDocumentTaskExecutorConfiguration`：核心线程和最大线程都为 2，队列容量为 8，线程名前缀为 `knowledge-task-`。这是固定、小容量的有界执行器，目标是限制 Embedding、Qdrant 和 Lucene 写入并发，而不是追求无限吞吐。

`KnowledgeDocumentTaskService` 在提交前创建持久化任务；执行器拒绝时写入 `TASK_REJECTED`，不会留下看似仍在排队的任务。排队任务取消时同时更新领域状态、取消 `FutureTask`、从线程池队列移除工作并取消超时句柄。超时与正常完成通过一次性 completion guard 竞争，避免双写终态；`attemptId` 又阻止错误尝试更新当前状态。

这里仍有明确边界：资料正文没有持久化，且旧 Worker 对 Dense/Sparse 的业务副作用尚未被 generation fencing 隔离，所以应用重启选择安全失败，而不是自动补投。后续索引临时构建与原子发布要解决的是副作用隔离，不是简单再加一个重试。

### Dense/Sparse 检索

`KnowledgeRetrievalConfiguration` 为 Dense 使用 4 个固定线程和 16 个队列槽，为 Sparse 使用 2 个固定线程和 8 个槽。两条检索链路的成本和外部依赖不同，所以分池隔离，避免一条链路拥塞拖死另一条。

`KnowledgeRetrievalDeadline` 把任务包装为 `FutureTask`，等待超时时取消并尝试从队列移除；队列拒绝和等待超时分别映射为“不可用”和“超时”，并记录 submitted、active、queued、completed、timedOut、rejected。因为检索是只读操作，迟到完成不会修改业务数据，这使取消边界比索引任务简单。

### 题库生成

`QuestionBankConfiguration` 将生成编排池设为 2 线程、8 槽队列，同时把真正调用模型的执行器限制为单线程。前者允许任务状态和恢复流程并行，后者控制付费模型并发。任务心跳和失联扫描使用独立调度器，说明“执行业务任务”和“维护租约”不能互相阻塞。

## 七、面试回答模板

可以按下面顺序组织两分钟回答：

1. **场景**：任务是什么，CPU/I/O 特征、下游容量和是否允许丢失。
2. **机制**：核心线程、入队、最大线程、拒绝的真实顺序。
3. **选择**：为什么固定或弹性，为什么有界队列，拒绝后如何反馈。
4. **边界**：取消和超时只是信号，哪些副作用不能自动回滚，重启如何处理。
5. **观测**：活动线程、排队、拒绝、超时、耗时分位和下游等待。
6. **案例**：用资料索引的 `2/2/8`、排队取消、超时门闩和 attempt fencing 说明取舍。

一个合格回答不要求给出“万能线程数”，而是展示如何由业务约束得到参数、如何在过载时保持状态真实、如何通过指标验证调整。

## 八、练习题

### 主问题 1

`ThreadPoolExecutor` 收到任务后，为什么不是直接创建到 `maximumPoolSize`？请说明任务入队后的二次检查。

回答检查点：核心线程优先、运行状态、队列 `offer`、入队后二次检查、零 Worker 补建、队列满后才尝试非核心线程、最终拒绝。

追问：把队列改成无界队列后，最大线程数、延迟和内存风险会怎样变化？

### 主问题 2

一个资料索引任务仍在队列中，用户点击取消。只把数据库状态改成 `CANCELLED` 有什么问题？

回答检查点：队列槽仍被占用、Worker 仍可能领取、需要关联工作对象、取消并 `remove`、领取竞态要靠状态条件更新、运行中任务不能假设副作用可回滚。

追问：如果取消与 Worker 领取同时发生，哪个状态条件保证只有一方成功？

### 主问题 3

线上看到队列持续增长，你会不会直接增加线程数？请给出诊断和回滚步骤。

回答检查点：先看任务耗时与下游连接池/限流，区分 CPU、I/O 和外部瓶颈；观察 active、queued、rejected、timedOut、P95/P99；单变量调整；定义拒绝率、延迟和下游错误率回滚阈值。

追问：为什么 `CallerRunsPolicy` 既可能形成背压，也可能耗尽 Web 请求线程？

## 九、掌握标准

- 能不看资料画出 `execute` 的五步决策图。
- 能解释本项目为什么把资料任务设为 `2/2/8`，以及它保护了哪些下游。
- 能区分排队取消、运行中中断、等待超时、业务终态和进程重启恢复。
- 能从运行观测页选择至少五个线程池或下游指标，并说明各自对应的故障假设。
