# Redis 缓存一致性、故障保护与分布式锁

## 学习目标

学完后应能从数据流而不是组件名解释缓存：谁是事实源、读写顺序是什么、允许多长时间不一致、缓存故障时怎样回源、热点失效时怎样保护数据库。还要能说明 Redis 锁的租约风险，以及为什么涉及外部副作用时仅有“互斥”还不够，通常还需要幂等和 fencing token。

## 一、先定义缓存契约

缓存不是第二个事实源。设计前先回答四个问题：

1. 数据库、远程服务或计算结果中，哪个是权威事实源。
2. 缓存对象能容忍多长时间陈旧，是否允许短暂读旧。
3. 未命中和 Redis 不可用时，业务能否回源，回源容量是多少。
4. 哪些结果可以缓存，哪些失败、空结果或权限相关结果不能共享。

常见 Cache Aside 读路径是“先查缓存，未命中再读事实源，最后回填”；写路径通常先提交数据库，再删除缓存。选择删除而不是直接更新，是为了避免应用需要在两个存储中维护完全相同的更新逻辑，但它只提供最终一致性，不能消除所有并发窗口。

## 二、缓存与数据库一致性

### 为什么通常先写库再删缓存

若先删缓存再写数据库，并发读可能在数据库提交前读到旧值并把旧值重新写回缓存，造成较长时间脏数据。先写数据库再删缓存把主要风险缩小到“数据库已成功、缓存删除失败”这个窗口，可通过有限重试、消息或 Binlog CDC 补偿。

延迟双删试图在第一次删除后等待可能存在的旧读回填，再删除一次，但延迟很难覆盖所有执行时间，服务重启也可能丢失第二次删除。它可以是降低概率的手段，不是严格一致性证明。严格边界应落到版本号、变更事件、数据库事务内 Outbox 或读取时的版本校验。

### 一致性策略怎么选

- 允许分钟级陈旧：TTL 加写后删除通常足够，重点是监控删除失败和回源压力。
- 允许秒级陈旧但更新频繁：写后删除配合重试或 CDC，让失败失效动作可恢复。
- 余额、库存等关键写入：数据库条件更新或唯一约束承担正确性，缓存只加速读取。
- 必须读己之写：写请求可短时间绕过缓存、携带版本，或读取主库，不能只靠缩短 TTL。

## 三、穿透、击穿与雪崩不是同一个问题

缓存穿透是请求对象本来就不存在，缓存和数据库都无法命中。可以在输入层拒绝非法键、缓存短 TTL 空值，或在数据集合相对稳定时使用布隆过滤器。布隆过滤器有误判且删除困难，不能把“可能存在”当成真实存在。

缓存击穿是单个热点键失效，大量并发同时回源。常见办法是 single-flight/互斥重建、逻辑过期配合后台刷新，或对极热点使用主动续期。互斥等待必须有超时，持锁者失败后要允许恢复，不能让保护机制自己变成阻塞点。

缓存雪崩是大量键在相近时间失效或 Redis 整体不可用。随机化 TTL 只能分散集中到期，解决不了节点故障；还需要限流、舱壁、降级、预热、多级缓存和明确的数据库回源上限。

## 四、Redis 故障时不能无限回源

“Redis 挂了就查数据库”只在数据库有足够余量时成立。若正常流量主要由缓存吸收，全部回源可能直接压垮事实源，形成级联故障。应提前定义：

- 回源并发和 QPS 上限，而不是让所有请求穿透。
- 可接受时返回旧缓存、默认值或明确的服务降级。
- 对不同业务区分 fail-open 与 fail-closed，例如公开知识查询可旁路，权限判断不能用不可信旧值。
- 使用命中、未命中、旁路、回源耗时、热点键、连接错误和数据库负载判断是否恢复。

Redis 主从、Sentinel 或 Cluster 提升的是服务可用性和容量，不会自动解决应用级脏数据、热点击穿或错误缓存。切换期间仍可能有复制延迟、连接重建和短暂不可用，应用必须有超时和降级边界。

## 五、分布式锁、租约与 fencing

基础 Redis 锁需要原子 `SET key owner NX PX ttl`，释放时用 Lua 比较 owner 后删除，避免误删他人的锁。续期可以降低长任务超过 TTL 的概率，但进程停顿、网络分区和主从切换仍可能让两个客户端先后认为自己持锁。

因此锁只能控制“谁被允许开始”，不能保证旧持有者恢复后不会迟到写入。对数据库或外部系统的关键副作用，应发放单调递增 fencing token，并让资源端拒绝比已见 token 更小的写入。若资源端无法校验 token，至少要使用业务唯一键、状态条件更新和幂等结果表限制重复副作用。

## 六、本项目的真实缓存案例

`RedisRagAnswerCache` 只缓存已经通过知识证据校验的完整回答，并设置 TTL。`RagAnswerService` 的缓存键包含 Prompt 版本、上下文预算、索引版本、全部当前知识资料版本、问题和有界历史；资料或 Prompt 变化后自然生成新键，不需要遍历删除旧回答。

读取 Redis 异常时返回未命中并继续检索和生成，写缓存失败也不覆盖已经生成的可靠回答，所以 Redis 不是问答单点。系统记录 `HIT/MISS/BYPASS`，可以区分正常未命中与缓存故障旁路。这个策略适合“缓存是优化、知识库与模型链路是主流程”的读场景。

边界也必须讲清：当前实现没有 single-flight，同一个冷门问题在高并发首次访问时仍可能重复调用模型；Redis 整体失败后全部回源还要受回答线程池和并发许可限制。缓存键按全知识目录版本失效，正确但粒度较粗，任一资料更新都会让所有回答形成新键。

## 七、面试回答模板

1. 先给出事实源、QPS、热点分布、SLA 和可接受陈旧时间。
2. 画出命中、未命中、写库、失效和失败补偿的数据流。
3. 分别处理穿透、单热点击穿、批量雪崩和 Redis 整体不可用。
4. 给出回源限流、舱壁、降级与恢复指标，不能只说“主从高可用”。
5. 涉及锁时说明 owner、TTL、续期、迟到持有者和资源端 fencing。
6. 最后说明一致性与延迟、成本、复杂度之间的取舍。

## 八、练习题

### 主问题 1

设计一个读多写少的知识回答缓存。如何让资料或 Prompt 更新后不再命中旧回答，同时避免每次更新都扫描删除大量 Key？

回答检查点：事实源、版本化缓存键、TTL、只缓存可靠结果、写入失败旁路、粗粒度失效代价。

追问：若只有一份低频资料更新，为什么全目录版本键可能造成额外模型调用？

### 主问题 2

Redis 整体不可用和单个热点 Key 失效分别会造成什么风险？你会如何限制回源并证明系统正在恢复？

回答检查点：击穿与雪崩差异、single-flight、限流/舱壁、降级、数据库容量、HIT/MISS/BYPASS 和长尾耗时。

追问：直接返回旧缓存适合哪些业务，不适合哪些业务？

### 主问题 3

一个任务使用 Redis 锁并开启看门狗续期，为什么仍可能出现旧 Worker 的迟到写入？怎样用 fencing 和业务幂等兜底？

回答检查点：租约过期、进程停顿、网络分区、owner 校验、单调 token、资源端条件写、唯一键与幂等结果。

追问：如果下游系统不支持 fencing token，还能把风险降低到什么程度？

## 九、掌握标准

- 能用数据流解释 Cache Aside，而不是只背“先更新还是先删除”。
- 能区分穿透、击穿、雪崩以及 Redis 整体故障。
- 能为回源设置容量边界、降级策略和恢复指标。
- 能解释版本化缓存键的正确性与失效粒度代价。
- 能说明 Redis 锁的 owner、TTL、续期和主从切换边界。
- 能区分互斥、幂等与 fencing 各自解决的问题。
