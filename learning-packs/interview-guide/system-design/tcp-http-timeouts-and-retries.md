# TCP、HTTP、连接复用、超时与重试

## 一、TCP 可靠不等于业务成功

TCP 用序号、确认、重传、滑动窗口和拥塞控制提供有序字节流。三次握手同步双方收发能力和初始序号；四次挥手源于双向关闭独立，TIME_WAIT 让迟到报文过期并能重发最后 ACK。TCP 连接成功只表示传输通道建立，不代表 HTTP 请求被业务提交。

粘包不是 TCP 错误，而是字节流没有消息边界；应用协议要用长度、分隔符或固定格式解帧。HTTP 已定义报文边界，但连接复用时仍要正确消费响应体，否则连接不能安全回池。

## 二、HTTP 版本与连接管理

HTTP/1.1 Keep-Alive 复用 TCP，但管线化受队头阻塞限制；HTTP/2 在单连接上多路复用流并压缩头部，丢包仍可能造成 TCP 层连接级阻塞；HTTP/3 基于 QUIC，把流隔离和握手优化移到 UDP 之上。版本升级不能消除服务端排队、连接池耗尽和业务超时。

连接池容量应结合目标主机数、并发、平均响应时间和下游限制。连接超时、读取超时、总请求截止时间含义不同；只有 socket read timeout 而没有端到端 deadline，排队、DNS、重试可能让总耗时失控。

## 三、超时、取消和未知结果

超时是调用方停止等待，不代表服务端停止执行。GET 等幂等读通常可有限重试；创建或扣款要携带幂等键并能恢复第一次结果。取消 Future 或断开 HTTP 也只是信号，下游是否收到、是否支持取消必须单独验证。

重试会放大流量，应有总预算、最大次数、指数退避和抖动，并只针对瞬时错误。各层独立重试会形成乘法放大，例如网关 3 次、服务 3 次、SDK 3 次可能产生 27 次调用。

## 四、SSE 与流式边界

SSE 基于 HTTP 单向推送，适合服务端持续输出文本事件，浏览器可自动重连；它不是双向协议，也不保证业务事件恰好一次。代理缓冲、空闲超时、断线和客户端重复事件都需要处理。重要状态仍应持久化，重连通过事件序号或查询接口恢复。

## 五、本项目网络调用映射

Embedding 导入明确按批次调用并关闭默认重试，单次失败后由导入补偿处理，避免 SDK 重试突破任务截止时间。RAG 回答设置端到端超时、并发舱壁和 SSE 完成事件；Dense/Sparse 使用独立线程池与 deadline，单路失败可降级并在响应中记录策略和原因。

这些机制不能证明 Provider 没有完成超时请求，也不能让非幂等模型调用任意重试。因此付费验收固定次数，超时后不自动追分；业务写请求使用 requestId/attempt 约束未知结果。

## 六、练习题

### 主问题 1｜方案可行性

为 Embedding、Chat 和 Qdrant 调用设计超时体系时，为什么需要端到端 deadline，而不只是 socket read timeout？

参考回答：总耗时还包含 DNS、建连、连接池排队、请求写入、服务端排队和重试。端到端 deadline 从业务入口分配预算，各阶段不得超过剩余时间；连接和读取超时是子边界。到期后停止等待、释放本地资源，并记录阶段耗时和未知结果。

回答检查点：阶段预算、连接池排队、重试、剩余时间、资源释放和未知结果。

追问：下游超时后为什么不能断言请求没有计费？

追问参考：调用方可能只丢失响应，下游已经接收甚至执行完成；需要 Provider 请求 ID、账单或幂等结果确认。

### 主问题 2｜容量、一致性与恢复

Dense 与 Sparse 并行检索时一条链路超时，系统如何降级而不把慢请求拖到总超时之后？

参考回答：两路使用独立有界执行器，共享明确 deadline；在剩余预算内收集结果，一路失败时使用另一路并标记 degraded 和原因，两路都失败才返回检索不可用。取消未完成任务并记录队列、执行、超时和策略指标，避免线程长期占用。

回答检查点：独立舱壁、共享 deadline、单路降级、双路失败、取消和可观测性。

追问：为什么给每一路完整 2 秒再串行等待可能让总耗时达到 4 秒？

追问参考：独立相对超时会累加；应从共同绝对截止时间计算每次剩余预算。

### 主问题 3｜取舍表达

哪些请求可以自动重试，哪些必须先具备幂等协议？如何避免重试风暴？

参考回答：无副作用读和明确幂等 PUT 可对瞬时网络错误有限重试；创建、扣费、生成任务等写操作先用稳定 requestId、唯一约束和结果恢复。重试要设置总预算、次数、退避与抖动，只在一层负责，并配合熔断、限流和 Retry-After。

回答检查点：操作语义、幂等键、未知结果、单层重试、退避抖动、熔断限流。

追问：为什么所有 5xx 都立即重试不合理？

追问参考：永久错误和过载不会因立即重试消失，反而放大压力；应按错误类型、服务提示和剩余预算判断。
